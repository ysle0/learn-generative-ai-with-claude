## 핵심 키워드 요약

| 키워드 | 정의 |
|--------|------|
| **RAG (Retrieval-Augmented Generation)** | 외부 지식을 검색하여 LLM의 프롬프트에 추가함으로써 정확한 답변을 생성하는 기법 |
| **벡터 데이터베이스 (Vector Database)** | 고차원 벡터를 저장하고 유사도 기반 검색을 지원하는 특수 목적 데이터베이스 |
| **임베딩 검색 (Embedding Search)** | 텍스트를 벡터로 변환한 후 의미적 유사도로 검색하는 방법 |
| **청킹 (Chunking)** | 긴 문서를 LLM이 처리할 수 있는 작은 단위로 분할하는 전략 |
| **리랭킹 (Reranking)** | 초기 검색 결과를 더 정교한 모델로 재정렬하여 관련성을 높이는 기법 |
| **하이브리드 검색 (Hybrid Search)** | 키워드 검색과 벡터 검색을 결합하여 검색 품질을 향상시키는 방법 |
| **환각 (Hallucination)** | LLM이 사실이 아닌 내용을 자신 있게 생성하는 현상 |
| **코사인 유사도 (Cosine Similarity)** | 두 벡터 간의 각도를 기반으로 유사도를 측정하는 수학적 방법 |
| **BM25** | 단어 빈도와 문서 길이를 고려한 전통적 키워드 기반 랭킹 알고리즘 |
| **에이전틱 RAG (Agentic RAG)** | AI 에이전트가 검색 여부와 방법을 스스로 판단하는 진화된 RAG 패턴 |

## 1. LLM의 한계: 환각과 지식 단절

### 1.1 왜 LLM은 없는 것을 지어낼까 (Hallucination)

LLM을 매일 사용하다 보면 한 번쯤 이런 경험을 해봤을 것입니다.
존재하지 않는 라이브러리 이름을 자신 있게 추천하거나, 실제로 없는 API 엔드포인트를
정확한 문법으로 설명하는 경우입니다.

이것이 바로 **환각(Hallucination)** 현상입니다. LLM이 거짓말을 "의도"하는 것이
아닙니다. 근본적인 원인은 LLM의 작동 방식에 있습니다.

```
LLM의 본질: "다음에 올 가장 그럴듯한 토큰을 예측하는 모델"

입력: "Python에서 날짜를 파싱하려면 ___ 라이브러리를 사용하면 됩니다"

모델이 하는 일:
  "dateutil"  → 확률 42%
  "datetime"  → 확률 35%
  "arrow"     → 확률 12%
  "chronos"   → 확률 3%    ← 이런 라이브러리는 없지만, 확률이 0은 아님
```

LLM은 **확률 분포에서 샘플링**할 뿐, "이것이 사실인가?"를 검증하는 메커니즘이
내장되어 있지 않습니다. 훈련 데이터에서 본 패턴을 기반으로 "그럴듯한" 텍스트를
생성하기 때문에, 때로는 그럴듯하지만 완전히 틀린 내용을 만들어냅니다.

### 1.2 왜 최신 정보를 모를까 (Knowledge Cutoff)

LLM은 특정 시점까지의 데이터로 훈련됩니다. 이 시점 이후의 정보는 알 수 없습니다.

```
+------------------+-------------------+---------------------------+
|   훈련 데이터     |   지식 단절점      |   모델이 모르는 영역        |
|   (학습 완료)     |   (Knowledge      |   (최신 정보, 사내 문서,   |
|                  |    Cutoff)        |    비공개 데이터)           |
+------------------+-------------------+---------------------------+
◄── 모델이 아는 것 ──►                  ◄── 모델이 모르는 것 ──────►
```

여러분 회사의 내부 위키, 어제 배포된 API 문서, 오늘 아침 발표된 기술 블로그 등은
LLM이 원천적으로 알 수 없는 정보입니다. 이 문제를 해결하는 것이 바로 RAG입니다.

## 2. RAG란 무엇인가

**RAG(Retrieval-Augmented Generation)** 는 LLM에게 "오픈북 시험"을 보게 하는
것과 같습니다. 학생(LLM)이 모든 것을 암기하는 대신, 시험 중에 참고 자료(외부 지식)를
찾아볼 수 있게 해주는 방식입니다.

### 2.1 기본 파이프라인

```
RAG 파이프라인 전체 흐름
========================

사용자 질문                     외부 지식 저장소
    |                          (Vector DB, 검색 엔진 등)
    |                                  |
    v                                  |
+----------+     질의      +-----------+-----------+
|  Query   | -----------> |    Retriever           |
|  처리    |              |    (검색기)             |
+----------+              +----------+-------------+
                                     |
                            관련 문서 Top-K개
                                     |
                                     v
                          +----------+-------------+
                          |   Augment Prompt       |
                          |   (프롬프트 증강)        |
                          |                        |
                          |  "아래 참고 자료를       |
                          |   기반으로 답변하세요:   |
                          |   [검색된 문서들]        |
                          |                        |
                          |   질문: {사용자 질문}"   |
                          +----------+-------------+
                                     |
                                     v
                          +----------+-------------+
                          |    LLM Generate        |
                          |    (답변 생성)           |
                          +------------------------+
                                     |
                                     v
                              최종 답변 출력
```

핵심 단계를 정리하면 다음과 같습니다.

1. **Query (질의)**: 사용자의 질문을 받습니다
2. **Retrieve (검색)**: 관련 문서를 외부 저장소에서 찾습니다
3. **Augment (증강)**: 검색된 문서를 프롬프트에 삽입합니다
4. **Generate (생성)**: LLM이 참고 자료를 기반으로 답변을 생성합니다

개발자에게 익숙한 코드로 보면:

```python
def rag_pipeline(user_query):
    # 1. 관련 문서 검색
    relevant_docs = vector_db.search(user_query, top_k=5)

    # 2. 프롬프트 증강
    context = "\n".join([doc.content for doc in relevant_docs])
    prompt = f"""아래 참고 자료를 기반으로 질문에 답변하세요.
    참고 자료를 벗어난 내용은 "알 수 없습니다"라고 답하세요.

    참고 자료:
    {context}

    질문: {user_query}"""

    # 3. LLM으로 답변 생성
    response = llm.generate(prompt)
    return response
```

## 3. 벡터 데이터베이스 (Vector Database)

### 3.1 벡터란 무엇인가

**벡터(Vector)** 는 텍스트의 "의미"를 숫자 배열로 표현한 것입니다.
임베딩 모델(Embedding Model)이 텍스트를 고차원 공간의 한 점으로 변환합니다.

```
임베딩 변환 예시
================

"Python 웹 프레임워크"  → [0.23, -0.45, 0.78, ..., 0.12]   (1536차원)
"Django 서버 개발"     → [0.25, -0.41, 0.80, ..., 0.15]   (1536차원)
"오늘 날씨가 좋다"     → [-0.67, 0.33, -0.12, ..., 0.89]  (1536차원)

              의미가 비슷하면 벡터도 가까움
              ↓
"Python 웹 프레임워크" ←→ "Django 서버 개발"     : 거리 가까움 (유사도 높음)
"Python 웹 프레임워크" ←→ "오늘 날씨가 좋다"     : 거리 멀음   (유사도 낮음)
```

### 3.2 유사도 측정 방법

두 벡터가 얼마나 비슷한지 측정하는 대표적인 방법은 다음과 같습니다.

**코사인 유사도 (Cosine Similarity)**: 두 벡터 사이의 각도를 측정합니다.
방향이 같으면 1, 반대면 -1, 직교하면 0입니다.

```
코사인 유사도 = (A · B) / (|A| × |B|)

직관적 이해:
  - 두 화살표가 같은 방향을 가리키면 → 유사도 ≈ 1.0 (매우 유사)
  - 두 화살표가 직각이면           → 유사도 ≈ 0.0 (관련 없음)
  - 두 화살표가 반대 방향이면       → 유사도 ≈ -1.0 (반대 의미)
```

**내적 (Dot Product)**: 벡터의 크기와 방향을 모두 반영합니다.
정규화된 벡터에서는 코사인 유사도와 동일한 결과를 냅니다.

```python
import numpy as np

def cosine_similarity(vec_a, vec_b):
    dot_product = np.dot(vec_a, vec_b)
    norm_a = np.linalg.norm(vec_a)
    norm_b = np.linalg.norm(vec_b)
    return dot_product / (norm_a * norm_b)

# 예시
query_vec = embed("Python 웹 개발 프레임워크")
doc1_vec  = embed("Flask와 Django 비교")       # 유사도: 0.89
doc2_vec  = embed("주말 등산 코스 추천")         # 유사도: 0.12
```

### 3.3 주요 벡터 데이터베이스 비교

```
+------------+----------+------------+-----------+---------------------------+
| 이름       | 유형     | 호스팅     | 언어      | 특징                      |
+------------+----------+------------+-----------+---------------------------+
| Pinecone   | 관리형   | 클라우드   | -         | 완전 관리형 서비스,        |
|            | SaaS     | (전용)     |           | 빠른 시작, 스케일링 용이   |
+------------+----------+------------+-----------+---------------------------+
| Weaviate   | 오픈소스 | 셀프/      | Go        | GraphQL API, 모듈식 구조, |
|            |          | 클라우드   |           | 멀티모달 지원             |
+------------+----------+------------+-----------+---------------------------+
| ChromaDB   | 오픈소스 | 셀프      | Python    | 경량, 로컬 개발에 최적,   |
|            |          | 호스팅     |           | Python 네이티브           |
+------------+----------+------------+-----------+---------------------------+
| pgvector   | 확장     | 셀프/     | C         | PostgreSQL 확장,          |
|            |          | 클라우드  |           | 기존 인프라 활용 가능      |
+------------+----------+------------+-----------+---------------------------+
| Qdrant     | 오픈소스 | 셀프/     | Rust      | 고성능, 풍부한 필터링,     |

+------------+----------+------------+-----------+---------------------------+
```

**어떤 것을 선택할까?**

- **빠른 프로토타입** → ChromaDB (pip install로 바로 시작)
- **이미 PostgreSQL을 쓰고 있다면** → pgvector (별도 인프라 불필요)
- **운영 환경에서 관리 부담을 줄이고 싶다면** → Pinecone
- **고성능과 세밀한 제어가 필요하다면** → Qdrant 또는 Weaviate

## 4. 문서 청킹 전략 (Document Chunking)

LLM의 컨텍스트 윈도우에는 한계가 있고, 벡터 검색의 정밀도를 높이려면
문서를 적절한 크기로 나눠야 합니다. 이것이 **청킹(Chunking)** 입니다.

### 4.1 고정 크기 청킹 (Fixed-Size Chunking)

가장 단순한 방법입니다. 일정한 토큰 수 또는 문자 수로 문서를 자릅니다.

```python
def fixed_size_chunk(text, chunk_size=500, overlap=50):
    chunks = []
    for i in range(0, len(text), chunk_size - overlap):
        chunks.append(text[i:i + chunk_size])
    return chunks
```

오버랩(overlap)을 두는 이유는 문맥이 청크 경계에서 끊기는 것을 방지하기 위함입니다.

### 4.2 의미 기반 청킹 (Semantic Chunking)

문장 간 의미적 유사도를 측정하여, 의미가 크게 바뀌는 지점에서 분할합니다.

```
문장1: "RAG는 검색 기반 생성 기법이다."        ─┐
문장2: "외부 지식을 LLM에 주입한다."           ─┤ 의미 유사 → 같은 청크
문장3: "이를 통해 환각을 줄일 수 있다."         ─┘
                                               ← 의미 전환점 (분할)
문장4: "벡터 DB는 임베딩을 저장한다."           ─┐
문장5: "Pinecone과 ChromaDB가 대표적이다."     ─┘ 의미 유사 → 같은 청크
```

### 4.3 재귀적 분할 (Recursive Splitting)

LangChain에서 널리 사용되는 방식입니다. 여러 구분자를 우선순위에 따라 적용합니다.

```
분할 우선순위:
  1순위: "\n\n" (문단 구분)
  2순위: "\n"   (줄바꿈)
  3순위: ". "   (문장 구분)
  4순위: " "    (단어 구분)

→ 큰 단위부터 시도하여 목표 크기에 맞출 때까지 점차 작은 단위로 분할
```

### 4.4 청크 크기의 트레이드오프

```
작은 청크 (100-200 토큰)          큰 청크 (1000-2000 토큰)
├─ 장점: 검색 정밀도 높음          ├─ 장점: 충분한 문맥 보존
├─ 장점: 관련 없는 내용 최소화     ├─ 장점: 의미 단절 적음
├─ 단점: 문맥 부족                ├─ 단점: 노이즈 포함 가능
└─ 단점: 여러 청크 필요           └─ 단점: 검색 정밀도 하락
```

실무에서는 **300-800 토큰** 범위에서 시작하여, 데이터와 사용 사례에 맞게
실험적으로 조정하는 것이 일반적입니다.

## 5. 임베딩 검색 vs 키워드 검색

### 5.1 키워드 검색 (Keyword Search)

전통적인 검색 방식입니다. 질의에 포함된 단어와 문서에 포함된 단어의 일치를 기반으로
결과를 반환합니다.

```
질의: "Python 메모리 누수 해결"

키워드 매칭:
  ✅ 문서 A: "Python에서 메모리 누수를 해결하는 5가지 방법"    → 정확한 키워드 매칭
  ❌ 문서 B: "파이썬 애플리케이션의 메모리 릭 디버깅 가이드"   → "메모리 누수" 불일치
  ❌ 문서 C: "가비지 컬렉션으로 힙 메모리 최적화하기"         → 관련 있지만 키워드 불일치
```

문서 B와 C는 분명히 관련이 있지만, 정확한 키워드가 일치하지 않아 누락됩니다.

### 5.2 임베딩 검색 (Embedding Search / Semantic Search)

텍스트를 벡터로 변환하여 **의미적 유사도**를 기반으로 검색합니다.

```
질의: "Python 메모리 누수 해결"  →  [0.23, -0.45, 0.78, ...]

의미적 유사도 비교:
  ✅ 문서 A: "Python에서 메모리 누수를 해결하는 5가지 방법"    → 유사도: 0.95
  ✅ 문서 B: "파이썬 애플리케이션의 메모리 릭 디버깅 가이드"   → 유사도: 0.88
  ✅ 문서 C: "가비지 컬렉션으로 힙 메모리 최적화하기"         → 유사도: 0.82
```

"메모리 누수"와 "메모리 릭", "Python"과 "파이썬"이 의미적으로 같다는 것을
임베딩이 포착합니다.

## 6. 하이브리드 검색 (Hybrid Search)

키워드 검색과 임베딩 검색은 각각의 강점이 다릅니다. 이 둘을 결합하면
더 나은 결과를 얻을 수 있습니다.

### 6.1 BM25 + 벡터 검색

**BM25**는 가장 널리 쓰이는 키워드 검색 알고리즘입니다.
TF-IDF의 발전형으로, 단어 빈도(Term Frequency)와 역문서 빈도(Inverse Document
Frequency), 그리고 문서 길이를 함께 고려합니다.

```
하이브리드 검색 흐름
====================

사용자 질의: "FastAPI 비동기 에러 핸들링"
         |
    +----+----+
    |         |
    v         v
+-------+  +--------+
| BM25  |  | Vector |
| 검색  |  | 검색   |
+---+---+  +---+----+
    |          |
    v          v
 [결과 A]   [결과 B]
    |          |
    +----+-----+
         |
         v
  +------+-------+
  | 점수 통합     |
  | (RRF 또는    |
  |  가중 합산)   |
  +--------------+
         |
         v
    최종 순위 결과
```

**RRF(Reciprocal Rank Fusion)** 는 각 검색 결과의 순위를 기반으로 점수를
통합하는 대표적인 방법입니다.

```python
def reciprocal_rank_fusion(results_lists, k=60):
    """여러 검색 결과 리스트를 RRF로 통합"""
    fused_scores = {}
    for results in results_lists:
        for rank, doc in enumerate(results):
            if doc.id not in fused_scores:
                fused_scores[doc.id] = 0
            fused_scores[doc.id] += 1 / (k + rank + 1)
    return sorted(fused_scores.items(), key=lambda x: x[1], reverse=True)
```

### 6.2 왜 하이브리드인가

| 상황 | 키워드 검색 | 임베딩 검색 | 하이브리드 |
|------|-----------|-----------|----------|
| 정확한 용어 검색 (에러 코드 등) | 강함 | 약함 | 강함 |
| 의미적 유사 문서 검색 | 약함 | 강함 | 강함 |
| 동의어/다국어 검색 | 약함 | 강함 | 강함 |
| 전문 용어 + 맥락 검색 | 보통 | 보통 | 강함 |

## 7. 리랭킹 (Reranking)

초기 검색(1차 검색)은 빠르지만 정밀도가 완벽하지 않습니다.
**리랭킹(Reranking)** 은 1차 검색 결과를 더 정교한 모델로 재평가하여
순위를 재조정하는 과정입니다.

### 7.1 크로스 인코더 리랭커 (Cross-Encoder Reranker)

1차 검색에 사용되는 **바이 인코더(Bi-Encoder)** 는 질의와 문서를 각각 독립적으로
벡터화합니다. 빠르지만 질의-문서 간의 세밀한 상호작용을 놓칠 수 있습니다.

**크로스 인코더(Cross-Encoder)** 는 질의와 문서를 함께 입력받아
관련성 점수를 직접 계산합니다. 느리지만 훨씬 정확합니다.

```
바이 인코더 (1차 검색 — 빠름, 대량 처리)
=========================================
질의 → [인코더] → 벡터A ─┐
                         ├─→ 유사도 계산
문서 → [인코더] → 벡터B ─┘


크로스 인코더 (리랭킹 — 느림, 정밀)
====================================
[질의 + 문서] → [인코더] → 관련성 점수 (0.0 ~ 1.0)
```

실제 파이프라인에서는 다음과 같이 2단계로 사용합니다.

```
1차 검색: 1000개 문서 중 → 상위 50개 후보 추출 (바이 인코더, 밀리초 단위)
    ↓
리랭킹: 50개 후보를 → 상위 5개로 재정렬 (크로스 인코더, 수십 밀리초)
    ↓
최종 결과: 가장 관련성 높은 5개 문서를 LLM 프롬프트에 삽입
```

## 8. RAG 파이프라인 설계 패턴

### 8.1 나이브 RAG (Naive RAG)

가장 기본적인 형태입니다. 질의를 받아 검색하고 바로 생성합니다.

```
질의 → 검색 → 프롬프트 증강 → LLM 생성
```

**한계점:**
- 질의가 모호하면 검색 품질이 낮음
- 검색된 문서가 항상 유용하지는 않음
- 청크 간 문맥 연결이 부족할 수 있음

### 8.2 고급 RAG (Advanced RAG)

검색 전후에 다양한 최적화 단계를 추가합니다.

```
[검색 전 최적화]
  - 질의 재작성 (Query Rewriting): 질의를 검색에 적합한 형태로 변환
  - 질의 확장 (Query Expansion): 동의어, 관련 용어를 추가
  - HyDE: 가상의 답변을 먼저 생성하여 그것으로 검색

[검색 중 최적화]
  - 하이브리드 검색
  - 메타데이터 필터링 (날짜, 카테고리 등)

[검색 후 최적화]
  - 리랭킹
  - 중복 제거
  - 압축 (관련 부분만 추출)
```

### 8.3 모듈러 RAG (Modular RAG)

검색, 생성, 라우팅 등 각 단계를 독립적인 모듈로 분리하여
필요에 따라 조합할 수 있는 유연한 아키텍처입니다.

```
+--------+     +--------+     +---------+     +--------+
| Router | --> | Search | --> | Reranker| --> |  LLM   |
| 모듈   |     | 모듈   |     | 모듈    |     | 모듈   |
+--------+     +--------+     +---------+     +--------+
    |              |
    |         +----+----+
    |         |         |
    v         v         v
 [캐시]   [벡터DB]  [웹검색]
```

### 8.4 에이전틱 RAG (Agentic RAG)

**에이전틱 RAG(Agentic RAG)** 는 AI 에이전트가 검색 도구를 "사용할지 말지"를
스스로 판단합니다. 단순한 인사에는 검색 없이 답하고, 사실 확인이 필요한 질문에만
검색을 수행합니다.

```python
# 에이전틱 RAG의 핵심 아이디어
def agentic_rag(user_query):
    # 에이전트가 먼저 판단
    plan = agent.decide(user_query)

    if plan.needs_retrieval:
        # 어떤 소스에서 검색할지도 에이전트가 결정
        if plan.source == "internal_docs":
            docs = internal_vector_db.search(plan.refined_query)
        elif plan.source == "web":
            docs = web_search(plan.refined_query)
        elif plan.source == "code":
            docs = code_search(plan.refined_query)

        # 검색 결과가 불충분하면 재검색
        if agent.evaluate(docs) == "insufficient":
            docs = agent.retry_with_different_strategy()

        return llm.generate(query=user_query, context=docs)
    else:
        return llm.generate(query=user_query)
```

에이전틱 RAG의 핵심 특징은 다음과 같습니다.

- **자율적 판단**: 검색이 필요한지 스스로 결정
- **다중 소스**: 여러 데이터 소스 중 적절한 것을 선택
- **반복 개선**: 검색 결과가 부족하면 전략을 바꿔 재시도
- **질의 분해**: 복잡한 질문을 하위 질문으로 나눠 각각 검색

## 9. RAG 시스템 평가 (Evaluation)

RAG 시스템이 잘 작동하는지 어떻게 측정할까요?
세 가지 핵심 지표가 있습니다.

### 9.1 충실도 (Faithfulness)

생성된 답변이 검색된 문서의 내용에 **충실한가**를 측정합니다.
검색된 문서에 없는 내용을 지어내면 충실도가 낮습니다.

```
검색된 문서: "Python 3.12에서 GIL 개선이 이루어졌다"

✅ 높은 충실도: "Python 3.12에서는 GIL이 개선되었습니다"
❌ 낮은 충실도: "Python 3.12에서 GIL이 완전히 제거되었습니다"  ← 문서에 없는 주장
```

### 9.2 관련성 (Relevance)

검색된 문서가 사용자의 질문과 **관련이 있는가**를 측정합니다.

```
질문: "Django ORM에서 N+1 쿼리 문제 해결 방법"

✅ 높은 관련성: select_related(), prefetch_related() 관련 문서
❌ 낮은 관련성: Django 설치 가이드 문서
```

### 9.3 재현율 (Recall)

정답을 포함하는 문서 중 **얼마나 많이 검색되었는가**를 측정합니다.

```
전체 관련 문서 10개 중 검색된 관련 문서 7개 → Recall = 70%
```

RAGAS, TruLens 같은 프레임워크를 사용하면 이러한 지표를 자동으로 측정할 수
있습니다. 이 도구들은 LLM 자체를 평가자(judge)로 활용하여 대규모 평가를
수행합니다.

## 10. 실무 적용 사례

### 10.1 사내 지식 챗봇

가장 흔한 RAG 활용 사례입니다. 회사 내부 문서(위키, Confluence, Notion 등)를
벡터 DB에 인덱싱하고, 직원들이 자연어로 질문하면 관련 문서를 기반으로 답변합니다.

```
[사내 문서]                    [챗봇 인터페이스]
  Confluence ──┐                    |
  Notion     ──┤── 인덱싱 ──→ Vector DB ──→ RAG 파이프라인
  Google Docs ─┘                    |
                                    v
                           "온보딩 절차는 다음과 같습니다..."
```

핵심 고려사항:
- 문서 업데이트 시 인덱스 동기화 파이프라인 필요
- 접근 권한 관리 (모든 직원이 모든 문서를 볼 수 있는 것은 아님)
- 답변에 출처 문서 링크를 반드시 포함

### 10.2 코드 검색 (Code Search)

대규모 코드베이스에서 관련 코드를 찾아주는 시스템입니다.

```python
# 코드 검색 RAG 예시
query = "사용자 인증 미들웨어는 어디에 있나요?"

# 코드를 함수/클래스 단위로 청킹
# 코드 + 주석 + 파일 경로를 함께 임베딩
results = code_vector_db.search(query)

# 결과: auth/middleware.py의 AuthenticationMiddleware 클래스
# + 관련 테스트 파일, 설정 파일 등
```

코드 검색에서의 특수한 고려사항:
- 코드의 청킹 단위: 함수, 클래스, 파일 등 의미 단위로 분할
- 파일 경로, import 관계 등 메타데이터 활용
- 코드와 자연어 설명을 함께 임베딩하여 검색 품질 향상

## 정리

RAG는 LLM의 가장 근본적인 한계인 환각과 지식 단절 문제를 해결하는 실용적인
아키텍처입니다. 핵심을 다시 정리하면 다음과 같습니다.

```
RAG의 핵심 구성 요소
====================

1. 문서 준비 단계
   문서 수집 → 청킹 → 임베딩 → 벡터 DB 저장

2. 질의 응답 단계
   질의 → (선택적 질의 최적화) → 검색 → (리랭킹) → 프롬프트 증강 → LLM 생성

3. 진화 방향
   Naive RAG → Advanced RAG → Modular RAG → Agentic RAG
```

개발자로서 RAG 시스템을 구축할 때 가장 중요한 것은 **각 단계를 독립적으로
실험하고 측정하는 것**입니다. 청킹 전략을 바꿔보고, 임베딩 모델을 교체해보고,
리랭킹을 추가해보면서 평가 지표가 어떻게 변하는지 관찰하세요. 은총알은 없습니다.
데이터와 사용 사례에 맞는 최적의 조합을 찾는 것이 실무에서의 핵심입니다.
