# Chapter 08: 추론 (Inference) — 모델이 답을 생성하는 과정

> **이 장의 대상 독자:** 매일 AI 도구를 사용하지만, "보내기" 버튼을 누른 뒤
> 모델 안에서 무슨 일이 벌어지는지 궁금했던 개발자

---

## 핵심 키워드 요약

| 키워드 | 정의 |
|--------|------|
| **Temperature** | 출력 확률 분포의 뾰족함을 조절하는 하이퍼파라미터. 낮으면 결정적, 높으면 창의적 |
| **Top-k** | 확률이 가장 높은 k개의 토큰만 후보로 고려하는 샘플링 기법 |
| **Top-p (Nucleus Sampling)** | 누적 확률이 p에 도달할 때까지의 토큰만 후보로 고려하는 샘플링 기법 |
| **Beam Search** | 여러 후보 경로를 동시에 탐색하여 최적의 시퀀스를 찾는 디코딩 전략 |
| **Greedy Decoding** | 매 단계에서 확률이 가장 높은 토큰 하나만 선택하는 가장 단순한 디코딩 방식 |
| **KV Cache** | 이전 토큰의 Key-Value 벡터를 저장하여 중복 계산을 제거하는 추론 가속 기법 |
| **Speculative Decoding** | 작은 모델이 초안을 작성하고, 큰 모델이 검증하여 추론 속도를 높이는 기법 |
| **Quantization** | 모델 가중치의 수치 정밀도를 낮춰 메모리 사용량과 연산량을 줄이는 기술 |
| **Batching** | 여러 요청을 묶어 GPU를 효율적으로 활용하는 처리 방식 |
| **Streaming** | 토큰이 생성되는 즉시 사용자에게 전송하는 실시간 출력 방식 |
| **Logits** | Softmax를 적용하기 전, 모델이 출력하는 각 토큰의 원시 점수 |

## 1. 프롬프트를 보내면 무슨 일이 일어나는가

여러분이 Claude에게 "서울의 인구는?"이라고 입력하고 전송 버튼을 누르는 순간,
모델 내부에서는 정교한 파이프라인이 작동합니다.

### 추론 파이프라인 전체 구조

```
  "서울의 인구는?"
       |
       v
  [1.Tokenize] --> [2.Embedding] --> [3.Forward Pass]
   텍스트->토큰      토큰->벡터      (Transformer Layers)
                                           |
                                           v
  [6.Detokenize] <-- [5.Sampling] <-- [4.Logits 계산]
   토큰->텍스트       토큰 선택       각 토큰별 점수 산출
       |
       v
  "약 970만 명입니다."

  * 위 과정을 토큰 하나마다 반복 (Autoregressive Generation)
```

### 단계별 상세 설명

**단계 1: 토큰화 (Tokenization)**

모델은 텍스트를 있는 그대로 읽지 못합니다. 먼저 텍스트를 **토큰(Token)** 이라는
작은 조각으로 쪼갭니다. BPE(Byte Pair Encoding) 같은 알고리즘이 사용됩니다.

```
입력: "서울의 인구는?"
토큰: ["서울", "의", " 인구", "는", "?"]
ID:   [ 8834,  1124,  29410,  1587, 136 ]
```

> **개발자 팁:** 토큰은 단어가 아닙니다. 영어에서 "unhappiness"는 ["un", "happiness"]
> 두 토큰이 되고, 한국어에서는 형태소 단위와 비슷하게 분리됩니다.

**단계 2: 임베딩 (Embedding)**

각 토큰 ID가 고차원 벡터로 변환됩니다. 이 벡터가 토큰의 "의미"를 담는 수학적 표현입니다.

```
토큰 "서울" (ID: 8834)  ->  [0.23, -0.87, 0.14, ..., 0.52]  (4096차원)
토큰 "의"  (ID: 1124)  ->  [0.11, -0.03, 0.98, ..., -0.21]  (4096차원)
```

**단계 3: 순전파 (Forward Pass)**

임베딩 벡터가 Transformer의 수십 개 레이어를 순차적으로 통과합니다.
각 레이어에서 Self-Attention과 Feed-Forward Network를 거치며,
토큰들 사이의 맥락이 점점 더 풍부하게 인코딩됩니다.

```
입력 벡터 -> [Layer 1] -> [Layer 2] -> ... -> [Layer N] -> 최종 은닉 상태
```

**단계 4: 로짓 계산 (Logits)**

최종 은닉 상태가 어휘 사전 크기의 벡터로 변환됩니다. 이 원시 점수가
**로짓(Logits)** 입니다. 어휘 사전에 100,000개의 토큰이 있다면,
100,000개의 점수가 나옵니다.

```
Logits 예시 (다음 토큰 예측):
  "약"   : 5.82    <-- 높은 점수
  "대략" : 4.17
  "서울" : 3.41
  "the"  : -1.33   <-- 낮은 점수
  (총 100,000개 토큰에 대한 점수)
```

**단계 5: 샘플링 (Sampling)**

로짓에 Softmax를 적용해 확률 분포로 변환한 뒤, 설정된 전략에 따라 하나의
토큰을 선택합니다. (Temperature, Top-k, Top-p 등이 이 단계에서 작동합니다.)

```
Softmax 적용 후:
  "약" : 0.42 (42%)  /  "대략" : 0.18 (18%)  /  "서울" : 0.12 (12%)  / ...
  --> 선택된 토큰: "약"
```

**단계 6: 디토큰화 (Detokenization)**

선택된 토큰 ID를 다시 텍스트로 변환합니다. 이 과정이 **종료 토큰(EOS)** 이
나올 때까지 반복되며, 한 번의 반복에서 **토큰 하나**만 생성됩니다.

## 2. 토큰 하나가 생성되는 과정: 단계별 워크스루

구체적인 예제로 정확히 한 토큰이 어떻게 탄생하는지 추적해 봅시다.

```
상황: 모델이 "서울의 인구는 약" 까지 생성한 상태. 다음 토큰을 예측해야 함.

[Step 1] 지금까지의 전체 시퀀스를 모델에 입력
         "서울의 인구는 약" -> [8834, 1124, 29410, 1587, 136, 8291]

[Step 2] Forward Pass 실행
         6개 토큰이 Transformer 레이어를 통과 -> 마지막 위치의 은닉 상태 추출

[Step 3] Logits 계산
         은닉 상태 x 어휘 행렬 = [2.1, -0.5, 8.7, ..., 3.2]  (100,000개 점수)

[Step 4] Temperature 적용 (T=0.7 가정)
         logits = logits / 0.7 -> 확률 분포가 더 뾰족해짐

[Step 5] Top-p 필터링 (p=0.9 가정)
         상위 토큰들의 누적 확률이 0.9에 도달할 때까지만 후보 유지

[Step 6] 확률 분포에서 샘플링
         "9":0.51 / "천만":0.22 / "1":0.14 / "970":0.08 ...
         -> 주사위를 굴림 -> "9" 선택!

[Step 7] "9"를 시퀀스에 추가 -> "서울의 인구는 약 9"
         -> Step 1로 돌아가서 다음 토큰 예측
```

## 3. 토큰 생성 전략 (Decoding Strategies)

같은 로짓이 주어져도, **어떤 전략으로 토큰을 선택하느냐**에 따라 결과가
완전히 달라집니다.

### 3.1 탐욕 디코딩 (Greedy Decoding)

매 단계에서 **확률이 가장 높은 토큰 하나**만 선택합니다.

```
단계 1: "약" (0.42) <-- 최고 확률만 선택
단계 2: "9"  (0.55) <-- 최고 확률만 선택
단계 3: "7"  (0.61) <-- 최고 확률만 선택
```

**장점:** 빠르고 결정적(deterministic). 같은 입력이면 항상 같은 출력.
**단점:** 반복적이고 지루한 텍스트가 생성되기 쉬움. 전체 시퀀스 관점에서 최적이 아닐 수 있음.

> **개발자 비유:** 길찾기에서 매 교차로마다 "지금 보이는 가장 짧은 길"만 선택하는 것.
> 전체 경로로 보면 최단 경로가 아닐 수 있습니다.

### 3.2 빔 서치 (Beam Search)

**빔 크기(beam size)** 만큼의 후보 경로를 동시에 추적하며, 각 단계에서
가장 유망한 경로들만 살려둡니다.

```
Beam Size = 3:

단계 1:  A: "약"(-0.87)  /  B: "대략"(-1.71)  /  C: "서울"(-2.12)

단계 2: 각 경로를 확장 -> 상위 3개만 유지
  A-1: "약 9"    (-1.45)  --> 유지
  A-2: "약 천"   (-2.10)  --> 유지
  B-1: "대략 9"  (-2.34)  --> 유지
  B-2: "대략 천" (-3.01)  --> 탈락
  C-1: "서울 인" (-3.88)  --> 탈락
```

**장점:** Greedy보다 더 좋은 전체 시퀀스를 찾을 가능성이 높음.
**단점:** 계산량이 빔 크기에 비례하여 증가. 번역 등 정확도 중심 작업에 적합.

### 3.3 샘플링 (Sampling)

확률 분포에서 **랜덤하게** 토큰을 뽑습니다. 확률이 높은 토큰이 더 자주
선택되지만, 낮은 확률의 토큰도 기회가 있습니다.

```
"약":0.42 ||||||||||||||||||||  "대략":0.18 |||||||||  "서울":0.12 ||||||
-> 주사위를 굴림: 42% 확률로 "약", 18% 확률로 "대략", ...
```

**장점:** 다양하고 창의적인 텍스트 생성 가능.
**단점:** 가끔 맥락에 맞지 않는 토큰이 선택될 수 있음.

## 4. Temperature -- 창의성 vs 정확성의 다이얼

**Temperature**는 추론에서 가장 자주 마주치는 하이퍼파라미터입니다.
Softmax 함수에 적용되어 확률 분포의 "뾰족함"을 조절합니다.

### 수학적 원리

```
표준 Softmax:          P(token_i) = exp(logit_i) / sum(exp(logit_j))
Temperature 적용:      P(token_i) = exp(logit_i / T) / sum(exp(logit_j / T))
```

**T**가 Temperature입니다. 로짓을 T로 **나누는** 것이 핵심입니다.

### Temperature 값에 따른 변화

```
로짓: "약"=5.8, "대략"=4.2, "한"=2.1, "거의"=1.5

Temperature = 0 (Greedy):
  "약":0.99 ||||||||||||||||||||||||||||||||||  "대략":0.01 |
  -> 항상 "약"이 선택됨. 결정적(deterministic).

Temperature = 0.7 (균형):
  "약":0.65 ||||||||||||||||||||||||  "대략":0.22 ||||||||  "한":0.08 |||
  -> "약"이 주로 선택되지만, 가끔 "대략"도 나옴.

Temperature = 1.0 (원래 분포):
  "약":0.52 |||||||||||||||||||  "대략":0.25 |||||||||  "한":0.13 |||||
  -> 골고루 선택될 가능성이 있음.

Temperature = 2.0 (혼돈):
  "약":0.33 ||||||||||||  "대략":0.27 ||||||||||  "한":0.21 ||||||||
  -> 거의 균등 분포. 예측 불가. 창의적이지만 혼란스러움.
```

### 실전 가이드: 언제 어떤 Temperature를 사용할까?

| 사용 사례 | 권장 Temperature | 이유 |
|-----------|-----------------|------|
| 코드 생성 | 0 ~ 0.2 | 정확한 구문이 필요. 창의성은 오히려 버그 |
| 수학 문제 풀이 | 0 | 정답이 하나. 변동이 없어야 함 |
| 기술 문서 작성 | 0.3 ~ 0.5 | 정확하되 약간의 표현 다양성 필요 |
| 일반 대화 | 0.7 ~ 0.9 | 자연스러운 대화를 위한 적절한 다양성 |
| 창작 글쓰기 | 0.9 ~ 1.2 | 예상치 못한 표현과 아이디어 필요 |
| 브레인스토밍 | 1.0 ~ 1.5 | 가능한 한 다양한 아이디어를 원함 |

> **핵심 원칙:** "정답이 있는 작업은 Temperature를 낮추고,
> 다양한 가능성을 탐색하는 작업은 Temperature를 높여라."

## 5. Top-k 샘플링

**Top-k 샘플링**은 확률 상위 **k개** 토큰만 후보로 남기고 나머지를 전부 제거합니다.

```
전체 분포 (상위 토큰):
  "약":0.42 / "대략":0.18 / "서울":0.12 / "거의":0.09 / "한":0.07
  "대략적":0.04 / "약간":0.03 / "바나나":0.001 / "TCP":0.0003

Top-k = 5 적용 후 (재정규화):
  "약":0.47 / "대략":0.20 / "서울":0.14 / "거의":0.10 / "한":0.09
  --- 여기서 컷. 나머지 전부 제거 ---
```

**문제점:** k가 고정이라 상황에 유연하게 대응하지 못합니다. 모델이 확신하는
경우에도, 불확실한 경우에도 항상 같은 개수의 후보를 유지합니다.

---

## 6. Top-p (Nucleus Sampling) -- 누적 확률 기반 필터링

**Top-p 샘플링**은 Top-k의 한계를 해결합니다. 고정된 개수가 아니라,
**누적 확률이 p에 도달할 때까지**의 토큰만 후보로 유지합니다.

```
확률을 내림차순 정렬 (Top-p = 0.9):
  "약"    : 0.42  -> 누적: 0.42
  "대략"  : 0.18  -> 누적: 0.60
  "서울"  : 0.12  -> 누적: 0.72
  "거의"  : 0.09  -> 누적: 0.81
  "한"    : 0.07  -> 누적: 0.88
  "대략적": 0.04  -> 누적: 0.92  <-- p=0.9 초과! 여기서 컷
```

**핵심 장점:** 모델이 확신할 때는 후보가 적고(2~3개), 불확실할 때는
후보가 많아지는(10개 이상) **적응적(adaptive)** 동작을 합니다.

```
확신하는 경우 (수학 문제):        불확실한 경우 (창작):
  "42" : 0.91 -> 누적 0.91 컷!    "밤":0.15 / "달":0.13 / "별":0.11
  (후보 1개)                       "바람":0.09 / "하늘":0.08 / "노을":0.07 ...
                                   (후보 10개 이상)
```

> **실전 팁:** 대부분의 API에서 Top-p=0.9~0.95가 좋은 기본값입니다.
> Temperature와 함께 사용하면 더 세밀한 제어가 가능합니다.

## 7. KV Cache -- 추론 속도의 핵심 비밀

### 문제: 왜 매번 처음부터 계산하면 안 되는가

자기 회귀(Autoregressive) 생성에서, 모델은 토큰 하나를 만들 때마다
**전체 시퀀스**를 입력으로 받습니다.

```
1번째 토큰 생성: 입력 = "서울의 인구는?"          (5 토큰)
2번째 토큰 생성: 입력 = "서울의 인구는? 약"       (6 토큰)  <- 5토큰 중복 계산!
3번째 토큰 생성: 입력 = "서울의 인구는? 약 9"     (7 토큰)  <- 6토큰 중복 계산!
```

### 해결: KV Cache

Transformer의 Self-Attention에서 각 토큰은 **Key(K)** 와 **Value(V)** 벡터를
생성합니다. KV Cache는 이전 단계에서 계산한 K, V를 메모리에 저장해두고,
새 토큰의 K, V만 추가로 계산합니다.

```
KV Cache 없이:
  토큰 1 생성: [서,울,의,인,구,는,?] 전체 계산
  토큰 2 생성: [서,울,의,인,구,는,?,약] 전체 계산  <- 7토큰 중복!
  계산량: O(n^2) per token, 총 O(n^3)

KV Cache 사용:
  토큰 1 생성: [서,울,의,인,구,는,?] 전체 계산 -> K,V 저장
  토큰 2 생성: [약] 만 새로 계산, 캐시에서 K1..K7 재사용  <- 빠름!
  토큰 3 생성: [9] 만 새로 계산, 캐시에서 K1..K8 재사용   <- 빠름!
  계산량: O(n) per token, 총 O(n^2)
```

### 메모리 비용

KV Cache의 대가는 **메모리**입니다. 모든 레이어의 K, V를 시퀀스 길이만큼
저장해야 합니다.

```
KV Cache 메모리 = 2 x 레이어 수 x 은닉 차원 x 시퀀스 길이 x 정밀도(bytes)

예시 (70B 모델, 4096 시퀀스, FP16):
= 2 x 80 x 8192 x 4096 x 2 bytes = 약 10.7 GB (단일 요청당!)
```

이것이 긴 컨텍스트 윈도우(128K, 200K 토큰)를 지원하는 모델에서
메모리 관리가 핵심 엔지니어링 과제인 이유입니다.

## 8. 추측 디코딩 (Speculative Decoding)

큰 모델일수록 정확하지만, 토큰 하나를 생성하는 데 시간이 더 걸립니다.
**추측 디코딩**은 이 문제를 영리하게 해결합니다.

### 핵심 아이디어

```
1. 작은 모델(Draft Model)이 빠르게 N개 토큰을 "초안" 생성
   Draft: "약 970만 명"  (빠르게 5토큰 생성)

2. 큰 모델(Target Model)이 한 번의 Forward Pass로 N개 토큰을 동시에 검증
   "약"  -> 수용 (큰 모델도 이걸 선택했을 것)
   "970" -> 수용
   "만"  -> 수용
   "명"  -> 거부! 큰 모델이 "여"로 교체

3. 결과: "약 970만 여" -> 3토큰이 한 번에 확정!
   큰 모델의 품질을 유지하면서 속도 2~3배 향상
```

**왜 작동하는가:** 대부분의 토큰은 "쉬운" 토큰이라 작은 모델과 큰 모델이
같은 선택을 하는 경우가 많습니다. 큰 모델은 **검증**만 하면 되고, 검증은
여러 토큰을 병렬로 할 수 있어 빠릅니다.

> **개발자 비유:** 주니어 개발자가 코드를 빠르게 작성하고,
> 시니어 개발자가 코드 리뷰로 검증하는 것과 같습니다.

## 9. 양자화 (Quantization) -- 모델을 가볍게 만드는 기술

### 정밀도와 모델 크기

모델의 가중치는 숫자로 저장됩니다. 각 숫자를 얼마나 정밀하게 표현하느냐가
모델의 크기와 속도를 결정합니다.

```
같은 70B 파라미터 모델의 크기 비교:

  정밀도   비트/파람   모델 크기    특징
  ------   --------   ---------   ---------------------------------
  FP32     32 bit     ~280 GB     학습 시 사용. 추론엔 과잉
  FP16     16 bit     ~140 GB     추론의 기본 정밀도
  INT8      8 bit      ~70 GB     품질 거의 유지, 크기 절반
  INT4      4 bit      ~35 GB     약간의 품질 저하, 크기 1/4

  FP32: |||||||||||||||||||||||||||||||||| 32비트
  FP16: |||||||||||||||||                  16비트
  INT8: ||||||||                            8비트
  INT4: ||||                                4비트
```

### 양자화가 작동하는 이유

대부분의 가중치는 좁은 범위(-0.5~0.5)에 집중 분포하므로,
더 적은 비트(4비트 = 16단계)로도 충분히 표현할 수 있습니다.

### 주요 양자화 포맷

| 포맷 | 설명 | 주요 사용처 |
|------|------|------------|
| **GPTQ** | GPU 최적화 Post-Training 양자화. 보정 데이터로 정확도 유지 | GPU 서버 배포 |
| **AWQ** | Activation-Aware 양자화. 중요한 가중치의 정밀도를 선택적으로 유지 | GPU 서버 (GPTQ 대비 개선) |
| **GGUF** | llama.cpp 포맷. CPU/GPU 혼합 추론. 개인 PC에서 모델 구동에 적합 | 로컬 PC / 엣지 디바이스 |

> **실전 팁:** 로컬에서 LLM을 돌려보고 싶다면, GGUF 포맷의 Q4_K_M 양자화가
> 품질과 크기의 좋은 균형점입니다. Ollama나 llama.cpp로 쉽게 사용할 수 있습니다.

## 10. 배칭 (Batching)과 처리량 최적화

GPU는 병렬 처리에 특화되어 있어, 요청 하나를 처리하든 여러 개를 동시에
처리하든 GPU 자원을 비슷하게 사용합니다. 배칭은 이 특성을 활용합니다.

```
배칭 없이 (Sequential):            배칭 적용 (Concurrent):
  요청 A =========> 완료              요청 A =========> 완료
  요청 B          =========> 완료     요청 B =========> 완료
  요청 C                   ========>  요청 C =========> 완료
  GPU: [30%]  [30%]  [30%]           GPU: [90%]
  총 시간: |||||||||||||||||||||||    총 시간: ||||||||
```

### 동적 배칭 (Continuous Batching)

실제 서비스에서는 요청이 동시에 시작/종료되지 않습니다. **Continuous Batching**은
완료된 요청의 자리에 새로운 요청을 즉시 넣어 GPU를 쉬지 않고 활용합니다.

```
시간 ->
Slot 1: [==요청A==][==요청D==][==요청F==]
Slot 2: [=요청B=][===요청E===][==요청G==]
Slot 3: [====요청C====][=요청H=][===...==]
```

> **개발자 비유:** 웹 서버의 커넥션 풀(Connection Pool)과 같은 개념입니다.

## 11. 스트리밍 (Streaming) -- 토큰이 하나씩 나타나는 이유

ChatGPT나 Claude를 사용할 때 답변이 한 글자씩 나타나는 것은 단순한 시각 효과가
아닙니다. **실제로 토큰이 하나씩 생성되기 때문**입니다.

```
Non-Streaming:                        Streaming (SSE):
  클라이언트 -> "서울 인구?"            클라이언트 -> "서울 인구?"
  [모든 토큰 생성 대기...]               <- "약"
  <- "약 970만 명입니다." (한번에)       <- " 970"
                                        <- "만"
  사용자 대기: |||||||||||||||||||       <- " 명입니다."
  첫 글자: ------------>|               <- [DONE]
                                       사용자 대기: ||
                                       첫 글자: ->|  (거의 즉시)
```

### 기술적 구현

스트리밍은 보통 **Server-Sent Events (SSE)** 프로토콜을 사용합니다.

```
// API 요청 예시 (Claude API)
POST /v1/messages
{
  "model": "claude-sonnet-4-20250514",
  "stream": true,          // <-- 스트리밍 활성화
  "messages": [{"role": "user", "content": "서울의 인구는?"}]
}

// 서버 응답 (SSE 형식)
event: content_block_delta
data: {"type": "content_block_delta", "delta": {"text": "약"}}

event: content_block_delta
data: {"type": "content_block_delta", "delta": {"text": " 970만"}}

event: message_stop
data: {"type": "message_stop"}
```

**스트리밍의 장점:**
- **체감 지연 감소:** 첫 토큰 출력 시간(TTFT)이 짧아 대기감이 줄어듦
- **조기 중단:** 원하지 않는 방향이면 생성을 중간에 멈출 수 있음
- **점진적 렌더링:** 프론트엔드에서 결과를 실시간으로 표시 가능

## 12. 실전 추론 설정 가이드

지금까지 배운 개념을 실전 시나리오에 적용해 봅시다.

```
+------------------------------------------------------------------+
|  코드 생성 (정확성 최우선)                                        |
|  Temperature: 0 / Top-p: 1.0 / Stream: true                     |
|  이유: 코드에서 "창의성"은 버그를 의미합니다.                     |
+------------------------------------------------------------------+
|  고객 지원 챗봇 (정확하되 자연스럽게)                             |
|  Temperature: 0.3 / Top-p: 0.9 / Stream: true                   |
|  이유: 사실 기반이되, 매번 같은 답을 하면 로봇처럼 보입니다.      |
+------------------------------------------------------------------+
|  소설/시 창작 (창의성 최우선)                                     |
|  Temperature: 1.0 / Top-p: 0.95 / Top-k: 50 / Stream: true     |
|  이유: 예측 불가능한 단어 조합이 문학적 가치를 만듭니다.          |
+------------------------------------------------------------------+
|  데이터 추출 / JSON 생성 (구조 엄수)                              |
|  Temperature: 0 / Top-p: 1.0 / Stream: false                    |
|  이유: 구조화된 출력에서 랜덤성은 파싱 에러를 유발합니다.         |
+------------------------------------------------------------------+
```

## 13. 요약: 추론 파이프라인 한눈에 보기

```
사용자 입력
    |
    v
[Tokenization] --- 텍스트를 토큰 ID로 변환
    |
    v
[Embedding] --- 토큰 ID를 고차원 벡터로 변환
    |
    v
[Forward Pass] --- Transformer 레이어 통과 (KV Cache로 재계산 방지)
    |
    v
[Logits] --- 어휘 전체에 대한 점수 산출
    |
    v
[Temperature] --- 확률 분포 조절 (logits / T)
    |
    v
[Top-k / Top-p] --- 후보 토큰 필터링
    |
    v
[Sampling] --- Greedy / Beam Search / Random 중 택1
    |
    v
[Detokenization + Streaming] --- 텍스트 변환 후 즉시 전송
    |
    v
  EOS? -- No --> 반복  /  Yes --> 완료
```

### 속도 최적화 기술 요약

| 기법 | 효과 | 비용 |
|------|------|------|
| KV Cache | 중복 계산 제거 | GPU 메모리 증가 |
| Quantization | 모델 크기 축소 | 약간의 품질 하락 |
| Speculative Decoding | 생성 속도 2~3배 | 추가 모델 필요 |
| Batching | 처리량 대폭 향상 | 개별 지연 미증가 |
| Continuous Batching | GPU 유휴 시간 제거 | 스케줄링 복잡도 |

---

## 핵심 정리

1. **추론은 토큰 단위로 일어난다.** Tokenize, Embed, Forward Pass, Logits,
   Sample, Detokenize 과정을 토큰 하나마다 반복합니다.

2. **Temperature는 가장 중요한 다이얼이다.** 0이면 결정적, 1이면 균형,
   1 이상이면 창의적이지만 혼란스러울 수 있습니다.

3. **Top-k는 고정 개수, Top-p는 적응적이다.** Top-p(Nucleus Sampling)가
   더 유연하여 실전에서 선호됩니다.

4. **KV Cache는 추론 속도의 핵심이다.** 이전 토큰의 Key-Value를 재사용하여
   중복 계산을 제거하지만, 메모리를 소비합니다.

5. **양자화는 모델 접근성을 민주화한다.** FP16에서 INT4로 양자화하면 모델 크기가
   1/4로 줄어, 개인 PC에서도 대형 모델을 실행할 수 있습니다.

6. **스트리밍은 UX이자 기술이다.** 자기 회귀 생성의 특성을 활용하여,
   사용자의 체감 대기 시간을 극적으로 줄입니다.
