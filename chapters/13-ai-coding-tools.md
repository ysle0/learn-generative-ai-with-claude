## 1. 당신이 매일 쓰는 도구의 정체

아침에 터미널을 열어 `claude`를 실행합니다. "이 함수 리팩토링해줘"라고 말하면 Claude Code가
파일을 읽고, 코드를 분석하고, 수정본을 만들어 적용합니다. VS Code에서는 Kilo Code가
프로젝트 구조를 파악하고 여러 파일을 동시에 수정합니다. 점심 후에는 Gemini에게
아키텍처 설계를 상담합니다.

이 도구들은 모두 LLM을 기반으로 동작하지만, 각각 접근 방식이 근본적으로 다릅니다.
이 장에서는 이 도구들을 분류하고, 내부 동작 원리를 해부하며, 코드를 이해하는 방법을 살펴봅니다.

## 2. AI 코딩 도구의 분류

AI 코딩 도구는 사용자와 상호작용하는 방식에 따라 네 가지로 분류할 수 있습니다.

```
+------------------------------------------------------------------+
|                    AI 코딩 도구의 네 가지 유형                      |
+------------------------------------------------------------------+
|                                                                    |
|  [자동완성형]          코드를 치는 도중 다음 줄을 예측              |
|  Copilot, Supermaven   Tab 한 번이면 끝. 가장 빠르고 가벼움        |
|  Codeium                                                           |
|                                                                    |
|  [에이전트형]          자연어 지시를 받아 자율적으로 코딩            |
|  Claude Code, Cursor   파일 탐색, 편집, 명령 실행까지 스스로 수행   |
|  Kilo Code, Windsurf                                               |
|  Cline                                                             |
|                                                                    |
|  [CLI형]               터미널에서 대화하며 코딩                     |
|  Aider, OpenCode        Git 연동, 최소한의 인터페이스               |
|                                                                    |
|  [채팅형]              대화를 통해 코드 생성과 설명                  |
|  ChatGPT, Gemini        범용 AI에 코딩 질문. 직접 적용은 수동       |
|                                                                    |
+------------------------------------------------------------------+
```

### 2.1 자동완성형 (Auto-completion)

**대표 도구:** GitHub Copilot, Supermaven, Codeium

코드를 타이핑하는 순간 다음에 올 코드를 예측합니다. 에디터에 유령 텍스트(ghost text)로
회색 글씨가 나타나고, Tab을 누르면 수락됩니다.

**동작 방식:**
- 현재 파일의 커서 주변 코드를 수집
- 열린 탭의 관련 코드를 추가 컨텍스트로 포함
- LLM에 보내 다음 토큰들을 예측
- 지연 시간(latency)이 핵심 - 200ms 이내에 응답해야 유용함

Supermaven은 자체 모델을 사용하여 300,000 토큰의 컨텍스트 윈도우를 제공하면서도
극도로 낮은 지연 시간을 달성합니다. GitHub Copilot은 OpenAI 모델을 기반으로 하며,
가장 넓은 사용자 기반을 보유하고 있습니다.

### 2.2 에이전트형 (Agent-type)

**대표 도구:** Claude Code, Kilo Code, Cursor, Windsurf, Cline

Chapter 11에서 다룬 AI 에이전트의 코딩 특화 버전입니다.
"관찰 - 사고 - 행동" 루프를 반복하며 자율적으로 코딩합니다.

```
사용자: "인증 시스템에 2FA를 추가해줘"
    │
    ▼
[관찰] 프로젝트 구조 탐색, 기존 인증 코드 읽기
    │
    ▼
[사고] 어떤 파일을 수정해야 하는지 계획 수립
    │
    ▼
[행동] 파일 생성/수정, 의존성 설치, 테스트 실행
    │
    ▼
[관찰] 테스트 결과 확인 → 실패 시 다시 [사고]로
    │
    ▼
완료: 여러 파일에 걸친 변경사항 적용
```

Claude Code는 터미널에서 동작하는 에이전트입니다. `bash` 명령을 직접 실행하고,
파일 시스템을 자유롭게 탐색하며, `git` 작업까지 수행합니다.
Cursor와 Windsurf는 VS Code 기반의 에디터에 에이전트를 통합한 형태입니다.
Kilo Code와 Cline은 VS Code 확장(Extension)으로 동작하여 기존 에디터 환경을 유지하면서
에이전트 기능을 추가합니다.

### 2.3 CLI형 (CLI-type)

**대표 도구:** Aider, OpenCode

터미널에서 대화하며 코딩합니다. 에이전트형과 비슷하지만 더 가볍고
Git 워크플로에 밀착되어 있습니다.

Aider는 변경사항을 자동으로 Git 커밋하고, 여러 LLM 백엔드(OpenAI, Anthropic, 로컬 모델)를
선택할 수 있습니다. OpenCode는 터미널 UI를 제공하는 Go 기반 도구로, 가볍고 빠른 것이 장점입니다.

### 2.4 채팅형 (Chat-type)

**대표 도구:** ChatGPT, Gemini

범용 AI 챗봇에 코딩 관련 질문을 하는 방식입니다. 코드를 생성해주지만,
프로젝트 파일에 직접 접근하거나 수정하지는 못합니다. 사용자가 코드를 복사하여
붙여넣어야 합니다.

그러나 최근 Gemini는 Google의 개발 생태계(Android Studio, Firebase)와
통합되기 시작했고, ChatGPT도 Canvas 기능으로 코드 편집 경험을 개선하고 있어
경계가 점차 흐려지고 있습니다.

## 3. 내부 동작 파이프라인

겉으로는 "AI에게 말하면 코드가 나온다"로 보이지만, 내부에서는 정교한 5단계
파이프라인이 동작합니다.

```
+------------------------------------------------------------------+
|              AI 코딩 도구 내부 파이프라인 (5단계)                    |
+------------------------------------------------------------------+
|                                                                    |
|  1단계: 코드 컨텍스트 수집 (Code Context Collection)                |
|  ┌─────────────────────────────────────────────────────┐          |
|  │  현재 파일  +  열린 탭들  +  import 추적  +  LSP 정보 │          |
|  │  프로젝트 구조  +  .gitignore  +  설정 파일           │          |
|  │  최근 편집 이력  +  터미널 출력  +  에러 메시지        │          |
|  └─────────────────────────────────────────────────────┘          |
|         │                                                          |
|         ▼                                                          |
|  2단계: 프롬프트 구성 (Prompt Construction)                         |
|  ┌─────────────────────────────────────────────────────┐          |
|  │  시스템 프롬프트  +  규칙 파일 (CLAUDE.md 등)         │          |
|  │  수집된 컨텍스트를 우선순위대로 배치                   │          |
|  │  사용자의 자연어 지시를 구조화                         │          |
|  │  컨텍스트 윈도우 한도 내에서 잘라내기 (truncation)     │          |
|  └─────────────────────────────────────────────────────┘          |
|         │                                                          |
|         ▼                                                          |
|  3단계: LLM API 호출 (LLM API Call)                                |
|  ┌─────────────────────────────────────────────────────┐          |
|  │  구성된 프롬프트를 LLM API에 전송                     │          |
|  │  스트리밍 응답 수신 (Server-Sent Events)              │          |
|  │  Tool Use 응답 처리 (파일 읽기, 명령 실행 등)         │          |
|  └─────────────────────────────────────────────────────┘          |
|         │                                                          |
|         ▼                                                          |
|  4단계: 응답 파싱 (Response Parsing)                               |
|  ┌─────────────────────────────────────────────────────┐          |
|  │  응답에서 코드 블록 추출                              │          |
|  │  diff 형식 파싱 (search/replace 블록)                 │          |
|  │  Tool Use 결과 파싱 (JSON 구조)                       │          |
|  │  파일 경로와 변경 내용 매핑                           │          |
|  └─────────────────────────────────────────────────────┘          |
|         │                                                          |
|         ▼                                                          |
|  5단계: 코드 적용 (Code Application)                               |
|  ┌─────────────────────────────────────────────────────┐          |
|  │  파일에 diff 적용 또는 새 파일 생성                   │          |
|  │  fuzzy matching으로 컨텍스트 변경 대응                │          |
|  │  적용 전 사용자 확인 (에이전트형의 경우)              │          |
|  │  적용 후 린트/테스트 자동 실행 (선택적)               │          |
|  └─────────────────────────────────────────────────────┘          |
|                                                                    |
+------------------------------------------------------------------+
```

### 3.1 코드 컨텍스트 수집

이 단계가 도구의 품질을 결정합니다. 같은 LLM을 사용해도 어떤 코드를
컨텍스트에 포함시키느냐에 따라 결과가 극적으로 달라집니다.

수집 대상:
- **현재 파일**: 편집 중인 파일 전체 또는 커서 주변
- **관련 파일**: import/require로 연결된 파일, 같은 디렉토리의 파일
- **타입 정보**: TypeScript의 `.d.ts` 파일, Python의 type stub
- **프로젝트 메타데이터**: `package.json`, `tsconfig.json`, `pyproject.toml`
- **최근 변경**: Git diff, 최근 편집된 파일
- **에러 정보**: 컴파일 에러, 린트 경고, 테스트 실패 메시지

### 3.2 프롬프트 구성

수집된 컨텍스트를 LLM이 이해할 수 있는 프롬프트로 조립합니다.
컨텍스트 윈도우에는 한계가 있으므로 우선순위를 정해야 합니다.

```
[시스템 프롬프트]                    ← 도구의 행동 규칙
[규칙 파일: CLAUDE.md 등]            ← 프로젝트별 커스텀 규칙
[사용자 메시지]                      ← "이 함수 리팩토링해줘"
[현재 파일 코드]                     ← 가장 높은 우선순위
[관련 파일 1: import된 모듈]         ← 의존성 순으로 정렬
[관련 파일 2: 타입 정의]
[관련 파일 3: 테스트 코드]
...
[잘라내기 경계]                      ← 윈도우 한계에 도달하면 여기서 끊김
```

### 3.3 LLM API 호출

구성된 프롬프트를 LLM API에 전송합니다. 에이전트형 도구는 단순한 텍스트 생성이 아니라
Tool Use(Function Calling)를 사용합니다. LLM이 "이 파일을 읽어야 합니다"라고 응답하면
도구가 실제로 파일을 읽어 다시 LLM에 전달하는 루프가 반복됩니다.

### 3.4 응답 파싱

LLM의 응답에서 실행 가능한 코드 변경사항을 추출합니다. 도구마다 다른 형식을 사용합니다.

- **Claude Code**: Tool Use 기반 - `write_file`, `edit_file` 등의 도구 호출로 구조화
- **Aider**: search/replace 블록 형식으로 diff를 표현
- **Cursor**: 커스텀 diff 형식으로 변경 부분만 전달

### 3.5 코드 적용

파싱된 변경사항을 실제 파일에 적용합니다. 이 과정에서 fuzzy matching이 중요합니다.
LLM이 코드를 생성하는 동안 사용자가 파일을 수정했을 수 있기 때문입니다.
정확히 일치하는 부분이 없으면, 유사한 부분을 찾아 적용합니다.

## 4. 코딩 도구가 코드를 이해하는 방법

LLM에 코드를 보내기 전에, 도구는 먼저 코드의 구조를 이해해야 합니다.
이를 위해 네 가지 핵심 기술이 사용됩니다.

### 4.1 AST (Abstract Syntax Tree)

소스 코드를 구조화된 트리로 변환한 것입니다.

```python
# 이 코드가:
def greet(name):
    return f"Hello, {name}!"

# AST로 변환되면:
#
#   FunctionDef
#   ├── name: "greet"
#   ├── args
#   │   └── arg: "name"
#   └── body
#       └── Return
#           └── JoinedStr (f-string)
#               ├── Constant: "Hello, "
#               ├── FormattedValue: name
#               └── Constant: "!"
```

AI 코딩 도구는 AST를 통해 단순 텍스트가 아닌 코드의 **의미 구조**를 파악합니다.
함수 경계, 클래스 계층, 변수 스코프 등을 정확히 이해할 수 있습니다.

### 4.2 LSP (Language Server Protocol)

Microsoft가 만든 에디터-언어 서버 간 통신 프로토콜입니다.
VS Code에서 "정의로 이동(Go to Definition)"을 누르면 LSP가 동작합니다.

```
+-------------------+         LSP         +-------------------+
|    에디터/도구     | <=================> |   언어 서버       |
|  (VS Code, Cursor |    JSON-RPC 통신    | (TypeScript,      |
|   Kilo Code)      |                     |  Python, Rust...) |
+-------------------+                     +-------------------+

LSP가 제공하는 정보:
- textDocument/definition     → 심볼의 정의 위치
- textDocument/references     → 심볼이 사용된 모든 위치
- textDocument/hover          → 타입 정보, 문서
- textDocument/completion     → 자동완성 후보
- textDocument/diagnostic     → 에러, 경고
```

AI 코딩 도구는 LSP를 활용하여 "이 함수를 호출하는 모든 곳"을 찾거나,
"이 변수의 타입이 무엇인지" 정확히 파악합니다.
Cursor, Windsurf, Kilo Code 같은 에디터 기반 도구들은
LSP 정보를 컨텍스트 수집에 적극 활용합니다.

### 4.3 Tree-sitter

GitHub이 개발한 고속 증분 파서(Incremental Parser)입니다.

```
기존 파서:        파일 수정 → 전체 다시 파싱 (느림)
Tree-sitter:     파일 수정 → 변경된 부분만 다시 파싱 (빠름)
```

Tree-sitter의 핵심 장점:
- **속도**: 키 입력마다 실시간 파싱 가능
- **범용성**: 하나의 프레임워크로 200개 이상의 언어 지원
- **정확성**: 구문 오류가 있어도 나머지 부분을 올바르게 파싱
- **증분 파싱**: 변경된 부분만 다시 파싱하여 효율적

Claude Code, Aider 등 많은 도구가 Tree-sitter를 사용하여 코드의 구조적 정보를
빠르게 추출합니다. 예를 들어 "이 파일의 모든 함수 시그니처"를 밀리초 단위로
가져올 수 있습니다.

### 4.4 심볼 인덱싱과 교차 참조 (Symbol Indexing and Cross-Reference)

프로젝트 전체의 심볼(함수, 클래스, 변수)을 인덱싱하여 빠르게 검색합니다.

```
인덱스 구축:
  프로젝트 전체 파일 스캔
       │
       ▼
  각 파일을 Tree-sitter로 파싱
       │
       ▼
  함수, 클래스, 타입 등 심볼 추출
       │
       ▼
  심볼 간 참조 관계 매핑 (호출 그래프)
       │
       ▼
  인덱스 저장 → 검색 시 즉시 조회
```

사용자가 "UserService 클래스를 수정해줘"라고 요청하면, 도구는 인덱스에서
`UserService`를 찾고, 관련된 모든 파일(정의, 사용처, 테스트)을
컨텍스트에 포함시킵니다.

## 5. 플러그인/확장 생태계

### 5.1 superclaude

superclaude는 Claude Code의 동작을 개선하는 커스텀 설정 시스템입니다.
`CLAUDE.md` 파일에 추가할 수 있는 규칙과 프롬프트 패턴을 제공합니다.

주요 기능:
- **구조화된 응답 형식**: Claude Code의 출력을 일관되게 정리
- **작업 유형별 최적화**: 리팩토링, 디버깅, 리뷰 등 작업에 맞는 지시 패턴
- **품질 체크리스트**: 코드 생성 시 확인해야 할 항목을 자동으로 포함
- **프로젝트 컨텍스트 강화**: 프로젝트 규칙과 컨벤션을 체계적으로 전달

### 5.2 opencode

opencode는 터미널 기반 AI 코딩 도구입니다.
Go로 작성되어 빠르고 가볍습니다.

주요 특징:
- TUI(Terminal User Interface) 제공
- 여러 LLM 백엔드 지원 (Anthropic, OpenAI 등)
- LSP 통합으로 정확한 코드 분석
- 세션 관리와 대화 이력 유지

### 5.3 커스텀 규칙 파일

각 도구마다 프로젝트별 규칙을 정의하는 파일이 있습니다.

```
도구별 규칙 파일:

  Claude Code     →  CLAUDE.md
  Cursor          →  .cursorrules
  Windsurf        →  .windsurfrules
  Cline           →  .clinerules
  Aider           →  .aider.conf.yml
  GitHub Copilot  →  .github/copilot-instructions.md
```

이 규칙 파일들은 시스템 프롬프트의 일부로 포함되어 LLM의 행동을 제어합니다.
예를 들어 `CLAUDE.md`에 다음과 같이 작성할 수 있습니다:

```markdown
# 프로젝트 규칙
- TypeScript strict mode 사용
- 모든 함수에 JSDoc 주석 필수
- 테스트는 Vitest로 작성
- 커밋 메시지는 Conventional Commits 형식
```

이 내용이 매 요청마다 프롬프트에 포함되어, AI가 프로젝트의 컨벤션을 일관되게
따르도록 합니다. 이것이 바로 프롬프트 엔지니어링(Chapter 9)의 실전 적용입니다.

## 6. 컨텍스트 관리 전략

컨텍스트 윈도우는 유한합니다. Claude의 200K 토큰이라 해도 대규모 프로젝트의
전체 코드를 담을 수는 없습니다. 도구들은 다양한 전략으로 이 한계를 관리합니다.

### 6.1 파일 관련성 순위 매기기 (File Relevance Ranking)

```
관련성 점수 계산:

  [최고] 현재 편집 중인 파일                    ← 항상 포함
  [높음] 사용자가 @-mention으로 명시한 파일      ← 명시적 지정
  [높음] import/require로 직접 연결된 파일       ← 의존성 그래프
  [중간] 같은 디렉토리의 파일                    ← 근접성
  [중간] 최근 편집된 파일                        ← 작업 흐름
  [중간] 에러 메시지에 언급된 파일               ← 문제 해결 맥락
  [낮음] 프로젝트의 나머지 파일                  ← 필요 시만
```

### 6.2 @-mention과 명시적 컨텍스트

많은 도구가 `@파일명` 문법으로 사용자가 직접 컨텍스트를 지정하는 방법을 제공합니다.

- **Claude Code**: 명시적으로 파일을 읽는 도구를 호출하거나 사용자가 경로를 언급
- **Cursor**: `@파일명`, `@폴더명`, `@웹`, `@문서` 등 다양한 @-mention
- **Kilo Code**: `@파일명`으로 파일을 컨텍스트에 추가

자동 수집에만 의존하면 중요한 파일을 놓칠 수 있습니다.
"이 타입 정의가 중요한데 왜 AI가 모르지?" 싶을 때는
명시적으로 해당 파일을 컨텍스트에 포함시키는 것이 효과적입니다.

### 6.3 청킹과 요약 (Chunking and Summarization)

파일이 너무 크면 전체를 포함할 수 없습니다. 이때 사용하는 전략들:

- **함수 단위 청킹**: AST/Tree-sitter로 파일을 함수 단위로 나누고 관련 함수만 포함
- **시그니처만 포함**: 함수 본문 대신 시그니처(이름, 매개변수, 반환 타입)만 포함
- **요약 생성**: LLM으로 파일의 요약을 미리 생성하여 캐싱
- **점진적 로딩**: 필요할 때마다 추가 파일을 읽어오는 에이전트 루프

## 8. 당신의 워크플로에서 일어나는 일

일상적으로 사용하는 도구의 동작을 파이프라인에 대입해봅시다.

### Claude Code에서 "이 함수 리팩토링해줘"라고 말할 때

```
1. [컨텍스트 수집]
   - CLAUDE.md 읽기 (프로젝트 규칙)
   - 대화 이력에서 이전에 언급된 파일 확인
   - 관련 파일 탐색을 위해 프로젝트 구조 파악

2. [프롬프트 구성]
   - 시스템 프롬프트 + CLAUDE.md 규칙
   - 사용자 메시지: "이 함수 리팩토링해줘"
   - 사용 가능한 도구 목록 (read_file, write_file, bash 등)

3. [LLM API 호출 - 에이전트 루프]
   - Claude: "먼저 파일을 읽겠습니다" → read_file 도구 호출
   - 파일 내용을 다시 Claude에 전달
   - Claude: 리팩토링 계획 수립 + edit_file 도구 호출
   - 수정 내용을 사용자에게 표시

4. [응답 파싱]
   - Tool Use 응답에서 파일 경로와 변경 내용 추출

5. [코드 적용]
   - 사용자 승인 후 파일에 변경 적용
   - (선택) 테스트 자동 실행
```

### Kilo Code에서 다중 파일 작업을 할 때

```
1. [컨텍스트 수집]
   - VS Code의 열린 파일, 워크스페이스 구조
   - LSP에서 타입 정보, 심볼 참조 수집
   - Tree-sitter로 코드 구조 빠르게 파싱

2. [프롬프트 구성]
   - 시스템 프롬프트 + 프로젝트 설정
   - 워크스페이스의 관련 파일들을 관련성 순으로 배치

3. [LLM API 호출]
   - 선택한 모델 (Claude, GPT 등)에 요청
   - 에이전트 루프로 필요한 파일을 추가로 읽기

4. [응답 파싱 + 적용]
   - 변경사항을 diff로 표시
   - 사용자가 파일별로 승인/거부
```

## 9. 미래: AI 코딩 도구가 향하는 곳

### 9.1 에이전트의 자율성 증가

현재 대부분의 도구는 파일 수정 전 사용자 확인을 요구합니다. 하지만 점점
자율 실행 범위가 넓어지고 있습니다. Claude Code의 `--dangerously-skip-permissions`
같은 옵션이 이미 존재하며, 신뢰 수준에 따라 자율성을 조절하는 방향으로 발전할 것입니다.

### 9.2 도구 간 경계의 소멸

자동완성, 에이전트, 채팅의 경계가 무너지고 있습니다. GitHub Copilot은 자동완성에서
시작했지만 이제 에이전트 모드를 추가했고, Cursor는 에이전트와 자동완성을 하나의
에디터에 통합했습니다. 궁극적으로 하나의 도구가 모든 유형의 코딩 지원을 제공하는
방향으로 수렴할 것입니다.

### 9.3 컨텍스트 이해의 진화

현재 도구들은 주로 텍스트 기반으로 코드를 이해합니다. 미래에는:
- **실행 시간 정보**: 디버거 연동, 런타임 타입 분석
- **프로젝트 전체 의미 그래프**: 코드베이스 전체의 의존성과 데이터 흐름 이해
- **팀 컨텍스트**: PR 리뷰 이력, 이슈 트래커, 문서까지 통합

### 9.4 MCP를 통한 도구 생태계 확장

Chapter 12에서 다룬 MCP가 코딩 도구의 확장성을 근본적으로 바꿀 것입니다.
데이터베이스 조회, API 테스트, 배포 파이프라인 등 개발 워크플로의 모든 단계를
AI 코딩 도구에서 직접 수행할 수 있게 됩니다.

### 9.5 로컬 모델의 부상

양자화 기술(Chapter 8)의 발전으로 강력한 코딩 모델이 로컬에서 실행 가능해지고
있습니다. 보안이 중요한 환경에서 코드를 외부 API로 보내지 않고도 AI 코딩 도구를
사용할 수 있는 시대가 다가오고 있습니다.

## 10. 정리: 매일 쓰는 도구를 이해한다는 것

```
+------------------------------------------------------------------+
|                         핵심 정리                                  |
+------------------------------------------------------------------+
|                                                                    |
|  1. AI 코딩 도구는 네 가지 유형으로 분류됩니다:                     |
|     자동완성형, 에이전트형, CLI형, 채팅형                           |
|                                                                    |
|  2. 내부적으로 5단계 파이프라인이 동작합니다:                       |
|     컨텍스트 수집 → 프롬프트 구성 → LLM 호출                      |
|     → 응답 파싱 → 코드 적용                                       |
|                                                                    |
|  3. AST, LSP, Tree-sitter가 코드의 구조적 이해를                  |
|     가능하게 합니다                                                |
|                                                                    |
|  4. 규칙 파일(CLAUDE.md 등)은 프롬프트 엔지니어링의               |
|     실전 적용입니다                                                |
|                                                                    |
|  5. 컨텍스트 관리가 도구 품질의 핵심입니다.                        |
|     같은 LLM이라도 어떤 코드를 보여주느냐가 결과를 결정합니다      |
|                                                                    |
+------------------------------------------------------------------+
```

이 장에서 다룬 내부 동작 원리를 이해하면, 도구를 더 효과적으로 사용할 수 있습니다.
AI가 엉뚱한 코드를 생성할 때 "컨텍스트가 부족한가?", "규칙 파일에 명시해야 하나?",
"@-mention으로 관련 파일을 직접 지정해야 하나?"를 판단할 수 있게 됩니다.

도구는 결국 도구입니다. 내부를 이해하는 개발자가 더 좋은 결과를 만들어냅니다.
