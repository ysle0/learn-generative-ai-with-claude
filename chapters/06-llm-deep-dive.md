## 6.1 들어가며

여러분은 매일 AI 도구를 사용합니다. 코드를 자동 완성하고, 이메일 초안을 작성하고, 복잡한 질문에 답을 구합니다. 하지만 이 도구들의 내부에서 실제로 무슨 일이 벌어지고 있는지 생각해 본 적이 있나요?

이 장에서는 대규모 언어 모델(Large Language Model, LLM)의 내부 작동 원리를 깊이 있게 살펴봅니다. "다음 단어를 예측하는 것뿐인데 어떻게 이렇게 똑똑할 수 있지?"라는 근본적인 질문에서 출발하여, 모델의 계보, 매개변수의 의미, 컨텍스트 윈도우의 진화, 그리고 규모가 만들어내는 놀라운 현상들까지 탐구합니다.

## 6.2 LLM의 핵심 원리 - "다음 토큰 예측" (Next Token Prediction)

### 6.2.1 놀랍도록 단순한 목표

LLM의 핵심 원리는 놀랍도록 단순합니다. **주어진 텍스트 다음에 올 가장 적절한 토큰(Token)을 예측하는 것**, 그것이 전부입니다.

```
입력: "오늘 서울의 날씨는"
예측: "맑고" (확률 0.23), "흐리고" (확률 0.18), "추우며" (확률 0.12), ...
```

토큰(Token)은 모델이 텍스트를 처리하는 최소 단위입니다. 하나의 단어일 수도 있고, 단어의 일부일 수도 있으며, 심지어 하나의 문자일 수도 있습니다. 예를 들어 영어 단어 "understanding"은 "under", "stand", "ing"처럼 여러 토큰으로 분리될 수 있습니다.

수학적으로 표현하면 다음과 같습니다:

```
P(x_t | x_1, x_2, ..., x_{t-1})

여기서:
- x_t: 예측할 다음 토큰
- x_1 ~ x_{t-1}: 이전까지의 모든 토큰 (컨텍스트)
```

모델은 이전에 등장한 모든 토큰을 고려하여, 다음에 올 토큰의 확률 분포를 계산합니다.

### 6.2.2 자기회귀 생성 (Autoregressive Generation)

LLM이 긴 문장을 생성하는 방식을 **자기회귀 생성(Autoregressive Generation)**이라고 합니다. 이 과정은 한 번에 하나의 토큰씩, 순차적으로 진행됩니다.

```
[단계 1] 입력: "인공지능은"
         예측: "인간의"

[단계 2] 입력: "인공지능은 인간의"
         예측: "지능을"

[단계 3] 입력: "인공지능은 인간의 지능을"
         예측: "모방하는"

[단계 4] 입력: "인공지능은 인간의 지능을 모방하는"
         예측: "기술입니다"
```

핵심은 **이전에 자신이 생성한 토큰이 다음 예측의 입력이 된다**는 점입니다. 마치 한 단어씩 글을 써 나가면서, 이미 쓴 내용을 계속 참고하는 작가와 같습니다.

이 방식의 중요한 특징은 다음과 같습니다:

| 특징 | 설명 |
|------|------|
| **순차적 생성** | 토큰이 반드시 왼쪽에서 오른쪽 순서로 생성됨 |
| **확률적 선택** | 매 단계마다 확률 분포에서 토큰을 선택 (항상 최고 확률을 고르지는 않음) |
| **누적적 컨텍스트** | 생성된 토큰이 계속 컨텍스트에 추가됨 |
| **온도 조절 가능** | Temperature 파라미터로 생성의 무작위성을 조절 |

### 6.2.3 왜 "다음 단어 예측"이 "이해"로 이어지는가?

이것은 LLM에 대한 가장 중요하고도 깊은 질문입니다. 단순히 다음 단어를 예측하는 훈련이 어떻게 언어에 대한 깊은 이해로 이어질까요?

**논리적 추론의 필요성**: "2 더하기 3은"이라는 문장 다음에 올 토큰을 정확히 예측하려면, 모델은 덧셈이라는 수학적 연산을 내부적으로 수행할 수 있어야 합니다.

**세계 지식의 필요성**: "대한민국의 수도는"이라는 문장을 올바르게 완성하려면, 모델은 지리적 사실을 알아야 합니다.

**맥락 이해의 필요성**: "그는 은행에 갔다. 거기서 돈을 인출했다"에서 "은행"이 금융 기관임을 파악하려면, 문맥을 이해해야 합니다.

**인과 관계의 필요성**: "비가 왔기 때문에 우산을"이라는 문장을 완성하려면, 원인과 결과의 관계를 파악해야 합니다.

> **핵심 통찰**: 충분히 큰 규모의 다음 토큰 예측은, 결국 세계에 대한 압축된 표현(Compressed Representation)을 학습하는 것과 같습니다. 모델은 언어의 통계적 패턴만 배우는 것이 아니라, 그 패턴을 만들어내는 기저의 구조 자체를 포착하게 됩니다.

### 6.3.2 GPT 시리즈 (OpenAI)

GPT(Generative Pre-trained Transformer)는 이름 그대로 **생성적(Generative)**, **사전 훈련된(Pre-trained)**, **트랜스포머(Transformer)** 기반 모델입니다.

| 모델 | 출시년도 | 매개변수 | 주요 특징 |
|------|----------|----------|-----------|
| GPT-1 | 2018 | 1.17억 | 트랜스포머 디코더를 언어 모델에 최초 적용 |
| GPT-2 | 2019 | 15억 | 제로샷 학습 가능성 입증, "너무 위험하다"며 공개 지연 |
| GPT-3 | 2020 | 1,750억 | 퓨샷 학습(Few-shot Learning)의 위력 입증 |
| GPT-3.5 | 2022 | 비공개 | ChatGPT의 기반, RLHF 적용 |
| GPT-4 | 2023 | 비공개 (추정 ~1.8조) | 멀티모달(텍스트+이미지), 전문가 수준 추론 |
| GPT-4o | 2024 | 비공개 | 옴니모달(텍스트+이미지+음성+영상), 실시간 대화 |

GPT 시리즈의 핵심 혁신은 **스케일링(Scaling)**이었습니다. 더 많은 데이터, 더 많은 매개변수, 더 많은 컴퓨팅으로 이전에 불가능했던 능력이 등장한다는 것을 반복적으로 증명했습니다.

### 6.3.3 BERT와 인코더 모델 (Encoder Models)

BERT(Bidirectional Encoder Representations from Transformers)는 GPT와 근본적으로 다른 접근법을 취합니다.

```
GPT (디코더, 단방향):
"인공지능은 [???]"  →  왼쪽 컨텍스트만 참조

BERT (인코더, 양방향):
"인공지능은 [MASK] 기술이다"  →  양쪽 컨텍스트 모두 참조
```

| 비교 항목 | GPT (디코더) | BERT (인코더) |
|-----------|-------------|--------------|
| 방향성 | 단방향 (왼쪽 → 오른쪽) | 양방향 (양쪽 모두) |
| 훈련 방식 | 다음 토큰 예측 | 마스크된 토큰 예측 (MLM) |
| 주요 용도 | 텍스트 생성 | 텍스트 이해/분류 |
| 대표 활용 | 챗봇, 글쓰기, 코딩 | 감정 분석, 검색, NER |

BERT는 텍스트 생성보다는 **텍스트 이해**에 특화되어 있습니다. 검색 엔진의 쿼리 이해, 감정 분석, 개체명 인식(Named Entity Recognition) 등에서 여전히 널리 사용됩니다.

### 6.3.4 T5 - 인코더-디코더 모델 (Encoder-Decoder)

T5(Text-to-Text Transfer Transformer)는 Google이 개발한 인코더-디코더 구조 모델로, **모든 NLP 태스크를 텍스트-투-텍스트 문제로 통일**한 것이 핵심 아이디어입니다.

```
번역:    "translate English to Korean: Hello"  →  "안녕하세요"
요약:    "summarize: [긴 텍스트]"              →  "[요약된 텍스트]"
분류:    "classify: This movie is great"       →  "positive"
```

이 접근법의 장점은 하나의 프레임워크로 다양한 태스크를 처리할 수 있다는 점이며, 이후 등장한 많은 모델에 영향을 미쳤습니다.

### 6.3.5 LLaMA - Meta의 오픈 소스 혁명

LLaMA(Large Language Model Meta AI)는 Meta가 공개한 오픈 소스 모델 시리즈로, LLM 생태계에 큰 변화를 가져왔습니다.

| 버전 | 출시년도 | 매개변수 | 주요 의의 |
|------|----------|----------|-----------|
| LLaMA 1 | 2023.02 | 7B, 13B, 33B, 65B | 작은 모델도 충분히 강력함을 입증 |
| LLaMA 2 | 2023.07 | 7B, 13B, 70B | 상업적 사용 허가, Chat 모델 포함 |
| LLaMA 3 | 2024.04 | 8B, 70B | 토크나이저 개선, 성능 대폭 향상 |
| LLaMA 3.1 | 2024.07 | 8B, 70B, 405B | 405B로 폐쇄형 모델에 근접 |

LLaMA의 가장 큰 기여는 **오픈 소스 생태계의 폭발적 성장**을 촉발한 것입니다. LLaMA를 기반으로 Alpaca, Vicuna, WizardLM 등 수많은 파생 모델이 탄생했으며, 개인 개발자와 소규모 기업도 LLM을 직접 활용할 수 있는 길이 열렸습니다.

### 6.3.6 Claude - Anthropic의 헌법적 AI 접근법

Claude는 Anthropic이 개발한 모델로, **헌법적 AI(Constitutional AI, CAI)** 라는 독특한 접근법이 특징입니다.

**헌법적 AI란?**

기존 RLHF(인간 피드백 기반 강화 학습)에서 한 단계 더 나아간 방법론입니다:

```
[기존 RLHF]
1. 모델이 응답 생성
2. 인간 평가자가 응답의 좋고 나쁨을 판단
3. 그 피드백으로 모델 개선

[Constitutional AI]
1. 모델이 응답 생성
2. 모델 스스로가 "헌법"(원칙 목록)에 비추어 자기 응답을 비판
3. 비판을 바탕으로 응답을 수정
4. 수정된 데이터로 모델 개선
```

이 방식의 장점은 인간 평가자의 편향을 줄이고, 명시적인 원칙에 기반한 일관된 행동을 이끌어낼 수 있다는 것입니다.

| 버전 | 출시 시기 | 주요 특징 |
|------|-----------|-----------|
| Claude 1 | 2023.03 | 헌법적 AI 최초 적용 |
| Claude 2 | 2023.07 | 100K 컨텍스트, 코딩 능력 향상 |
| Claude 3 Haiku/Sonnet/Opus | 2024.03 | 3단계 모델 라인업, 멀티모달 |
| Claude 3.5 Sonnet | 2024.06 | GPT-4o 수준의 성능, 코딩 특화 |
| Claude 3.5 Haiku/Opus | 2024~2025 | 경량/고성능 라인업 확장 |

Claude의 특징적인 강점은 **긴 컨텍스트 처리 능력**(최대 200K 토큰), **코딩 태스크에서의 우수한 성능**, 그리고 **안전성과 유용성의 균형**입니다.

### 6.3.7 Gemini - Google의 멀티모달 네이티브

Gemini는 Google DeepMind가 개발한 모델로, **설계 단계에서부터 멀티모달(Multimodal)을 핵심으로** 삼았다는 점이 차별점입니다.

기존 모델들이 텍스트 모델에 이미지 처리를 "추가"한 것과 달리, Gemini는 텍스트, 이미지, 오디오, 비디오, 코드를 통합적으로 처리하도록 처음부터 설계되었습니다.

| 버전 | 특징 |
|------|------|
| Gemini 1.0 (Ultra/Pro/Nano) | 멀티모달 네이티브, 3단계 크기 라인업 |
| Gemini 1.5 Pro | **100만 토큰 컨텍스트 윈도우** (혁신적 도약) |
| Gemini 1.5 Flash | 경량/고속 버전, 비용 효율적 |
| Gemini 2.0 | 에이전트 기능 강화, 실시간 멀티모달 |

특히 Gemini 1.5의 100만 토큰 컨텍스트 윈도우는 약 700,000 단어, 30,000줄의 코드, 또는 1시간 분량의 비디오를 한 번에 처리할 수 있는 획기적인 수준입니다.

### 6.3.8 기타 주요 모델들

#### DeepSeek (중국)

DeepSeek은 중국의 AI 연구소가 개발한 모델로, 특히 수학과 코딩 분야에서 뛰어난 성능을 보여줍니다.

- **DeepSeek-V2**: MoE(Mixture of Experts) 아키텍처로 효율성 극대화
- **DeepSeek-V3**: 오픈 소스 모델 중 최상위 성능
- **DeepSeek-R1**: 추론 특화 모델, "생각의 사슬"을 강화학습으로 자동 학습

#### Mistral (프랑스)

유럽에서 탄생한 강력한 오픈 소스 모델 시리즈입니다.

- **Mistral 7B**: 13B 모델에 필적하는 7B 모델로 효율성 입증
- **Mixtral 8x7B**: MoE 구조로 성능과 효율성 동시 달성
- **Mistral Large**: 폐쇄형 모델에 도전하는 고성능 라인업

#### Qwen (중국, Alibaba)

Alibaba Cloud에서 개발한 모델 시리즈로, 다국어 지원이 뛰어납니다.

- **Qwen 2.5**: 다양한 크기(0.5B~72B)로 출시, 오픈 소스
- 중국어와 영어 모두에서 강력한 성능
- 코드, 수학 특화 변종 모델도 함께 공개

## 6.4 매개변수 (Parameters) - 수십억 가중치의 의미

### 6.4.1 매개변수란 무엇인가?

매개변수(Parameter)는 모델이 학습 과정에서 조정하는 **숫자 값(가중치)**입니다. 인간의 뇌에 비유하자면 시냅스 연결 강도에 해당합니다.

```
뉴런 A ──[가중치: 0.73]──→ 뉴런 B
         ↑ 이것이 하나의 매개변수

트랜스포머 모델에서:
- 어텐션 행렬의 각 원소
- 피드포워드 네트워크의 각 가중치
- 임베딩 테이블의 각 값
→ 이 모든 숫자가 매개변수
```

### 6.4.2 7B, 13B, 70B, 405B - 이 숫자들의 의미

모델 이름 뒤에 붙는 "B"는 Billion(10억)을 의미합니다.

| 표기 | 매개변수 수 | 대략적인 모델 크기 (FP16) | 필요 GPU 메모리 (추론) |
|------|-------------|--------------------------|----------------------|
| 7B | 70억 개 | ~14 GB | 단일 GPU 가능 |
| 13B | 130억 개 | ~26 GB | 단일 고성능 GPU |
| 70B | 700억 개 | ~140 GB | 멀티 GPU 필요 |
| 405B | 4,050억 개 | ~810 GB | 대규모 GPU 클러스터 |

이 숫자를 직관적으로 이해해 봅시다:

- **7B (70억)**: 지구 전체 인구와 비슷한 수의 조절 가능한 다이얼이 있다고 상상하세요
- **70B (700억)**: 지구 인구의 10배
- **405B (4,050억)**: 은하계 별의 수에 근접
- **GPT-4 (추정 1.8조)**: 인간 뇌 시냅스 수의 약 1%

### 6.4.3 매개변수 수와 실제 능력의 관계

매개변수가 많다고 무조건 더 좋은 모델은 아닙니다. 여러 요소가 성능에 영향을 미칩니다.

```
모델 성능 = f(매개변수 수, 훈련 데이터 품질, 훈련 데이터 양, 아키텍처 설계, 훈련 기법)
```

**매개변수 효율성의 사례들:**

| 비교 | 결과 |
|------|------|
| Mistral 7B vs LLaMA 2 13B | 7B가 많은 벤치마크에서 13B에 필적 또는 우위 |
| LLaMA 3 8B vs LLaMA 2 70B | 일부 태스크에서 8B 최신 모델이 구형 70B에 근접 |
| MoE 모델 (예: Mixtral 8x7B) | 전체 파라미터는 46.7B이나, 추론 시 활성 파라미터는 12.9B |

이는 **아키텍처 혁신과 데이터 품질의 개선**이 단순한 크기 증가보다 더 효과적일 수 있음을 보여줍니다. 최근의 추세는 무작정 큰 모델을 만드는 대신, 같은 크기에서 최대 성능을 끌어내는 방향으로 이동하고 있습니다.

### 6.4.4 MoE (Mixture of Experts) - 효율성의 혁신

최근 주목받는 MoE(Mixture of Experts) 아키텍처는 매개변수 효율성에 대한 새로운 관점을 제시합니다.

```
전통적 모델:  모든 입력 → [전체 매개변수 활성화] → 출력
MoE 모델:    모든 입력 → [라우터가 일부 전문가만 선택] → 출력

예) Mixtral 8x7B:
- 총 매개변수: 46.7B
- 추론 시 활성: ~12.9B (8개 전문가 중 2개만 활성)
- 결과: 70B급 성능을 13B급 비용으로
```

## 6.5 컨텍스트 윈도우 (Context Window) - 시야의 범위

### 6.5.1 컨텍스트 윈도우란?

컨텍스트 윈도우(Context Window)는 모델이 **한 번에 처리할 수 있는 토큰의 최대 수**를 의미합니다. 이는 모델의 "작업 기억(Working Memory)"에 해당합니다.

```
컨텍스트 윈도우 = 입력 토큰 + 출력 토큰

예) 128K 컨텍스트 모델:
[    입력 프롬프트: ~100K 토큰    |  응답: ~28K 토큰  ]
└────────── 총 128K 토큰 ──────────────────────────┘
```

### 6.5.2 컨텍스트 윈도우의 진화

컨텍스트 윈도우는 불과 몇 년 사이에 극적으로 성장했습니다.

```
토큰 수 (로그 스케일)

1,000,000+ ┤                                              ★ Gemini 1.5
           │
  200,000  ┤                                         ★ Claude 3
           │
  128,000  ┤                                    ★ GPT-4 Turbo
           │
   32,000  ┤                              ★ GPT-4
           │
    8,000  ┤                        ★ GPT-3.5
           │
    4,000  ┤                  ★ GPT-3
           │
    2,048  ┤            ★ GPT-2
           │
      512  ┤      ★ BERT
           ┼──────┴──────┴──────┴──────┴──────┴──────┴
          2018   2019   2020   2022   2023   2024   연도
```

| 컨텍스트 크기 | 대략적 분량 | 가능한 작업 |
|-------------|------------|-------------|
| 4K 토큰 | 문서 3~4페이지 | 간단한 질의응답 |
| 8K 토큰 | 짧은 논문 1편 | 요약, 번역 |
| 32K 토큰 | 소설 중편 | 긴 문서 분석 |
| 128K 토큰 | 책 1권 분량 | 코드 리포지토리 분석 |
| 200K 토큰 | 책 1~2권 | 대규모 코드베이스 이해 |
| 1M+ 토큰 | 책 여러 권 / 영상 1시간 | 전체 프로젝트 분석, 영상 이해 |

### 6.5.3 긴 컨텍스트가 중요한 이유

개발자 관점에서 긴 컨텍스트 윈도우는 실질적인 차이를 만듭니다:

**1. 코드 리뷰와 리팩토링**
```
짧은 컨텍스트: 파일 하나씩 분석 → 전체 구조 파악 어려움
긴 컨텍스트:   전체 코드베이스를 한 번에 → 일관된 리팩토링 가능
```

**2. 문서 기반 질의응답 (RAG 없이)**
```
짧은 컨텍스트: 문서를 청크로 분할 → 검색 → 관련 부분만 전달
긴 컨텍스트:   전체 문서를 통째로 → 맥락 손실 없는 정확한 답변
```

**3. 복잡한 멀티턴 대화**
```
짧은 컨텍스트: 대화가 길어지면 초반 내용 잊음
긴 컨텍스트:   긴 대화에서도 처음 언급한 세부사항 기억
```

> **실무 팁**: 컨텍스트 윈도우가 크다고 해서 항상 꽉 채워 사용하는 것이 좋은 것은 아닙니다. 입력이 길어질수록 비용이 증가하고, 일부 모델에서는 중간 부분의 정보를 놓치는 "Lost in the Middle" 현상이 발생할 수 있습니다. 필요한 정보를 선별하여 효율적으로 사용하는 것이 중요합니다.

## 6.6 스케일링 법칙 (Scaling Laws) - 크면 무조건 좋은가?

### 6.6.1 Kaplan et al.의 발견

2020년, OpenAI의 Jared Kaplan 등은 신경망 언어 모델의 성능이 세 가지 요소에 의해 **예측 가능한 멱법칙(Power Law)**을 따른다는 것을 발견했습니다.

```
Loss ∝ 1/N^α  (N = 매개변수 수)
Loss ∝ 1/D^β  (D = 데이터셋 크기)
Loss ∝ 1/C^γ  (C = 컴퓨팅 예산)

여기서 α, β, γ는 양의 상수
```

이것이 의미하는 바는 명확합니다:

- 모델을 **10배 크게** 만들면, 성능이 일정한 비율로 향상됨
- 데이터를 **10배 늘리면**, 성능이 일정한 비율로 향상됨
- 컴퓨팅을 **10배 투입하면**, 성능이 일정한 비율로 향상됨

그리고 이 관계는 놀라울 정도로 **매끄럽고 예측 가능**합니다.

### 6.6.2 Chinchilla 법칙 - 최적의 균형

2022년, DeepMind의 Hoffmann et al.은 "Chinchilla" 논문에서 기존 스케일링 접근에 중요한 수정을 가했습니다.

**핵심 발견**: 대부분의 기존 대형 모델들은 **매개변수에 비해 훈련 데이터가 부족**했습니다.

```
기존 접근 (Kaplan):
"컴퓨팅 예산이 있으면 → 모델을 최대한 크게"

Chinchilla 접근:
"컴퓨팅 예산이 있으면 → 모델 크기와 데이터를 동시에 균형 있게 증가"

최적 비율: 토큰 수 ≈ 매개변수 수 × 20
```

| 모델 | 매개변수 | 훈련 토큰 | 비율 | 최적 여부 |
|------|----------|-----------|------|-----------|
| GPT-3 | 175B | 300B | 1.7x | 부족 (Under-trained) |
| Chinchilla | 70B | 1.4T | 20x | 최적 (Compute-optimal) |
| LLaMA 1 | 65B | 1.4T | 21.5x | 최적에 근접 |
| LLaMA 3 | 8B | 15T+ | 1,875x | 의도적 과투자 (Over-trained) |

최근에는 Chinchilla 최적 비율을 넘어, **더 작은 모델에 훨씬 더 많은 데이터를 투입**하는 전략이 주류가 되고 있습니다. 이유는 간단합니다: 훈련 비용은 한 번이지만, 추론 비용은 매 사용마다 발생하기 때문입니다. 작지만 많이 훈련된 모델이 배포 비용 측면에서 유리합니다.

### 6.6.3 스케일링의 한계에 대한 논쟁

"크기를 계속 키우면 AGI에 도달하는가?"라는 질문은 AI 커뮤니티에서 가장 뜨거운 논쟁 중 하나입니다.

**낙관적 견해:**
- 스케일링 법칙은 아직 천장을 보여주지 않았다
- 새로운 창발적 능력이 규모와 함께 계속 등장한다
- 데이터와 아키텍처 개선이 스케일링의 효과를 더 증폭시킨다

**회의적 견해:**
- 고품질 훈련 데이터가 고갈되고 있다
- 특정 유형의 추론(예: 진정한 인과적 추론)은 단순 스케일링으로 해결되지 않을 수 있다
- 비용 대비 수익이 체감하고 있으며, 에너지 제약이 현실적 한계

## 6.7 창발적 능력 (Emergent Abilities) - 규모가 만드는 질적 변화

### 6.7.1 창발적 능력이란?

창발적 능력(Emergent Abilities)이란, 작은 모델에서는 전혀 보이지 않다가 **모델의 규모가 특정 임계점을 넘어서면 갑자기 나타나는 능력**을 말합니다.

```
성능
 │
 │                              ╭──── 갑작스러운 향상
 │                             /
 │                            /
 │  ........................./
 │  (무작위 수준의 성능)
 │
 └──────────────────────────────── 모델 크기
        10B    50B   100B  500B
```

이것은 연속적이고 점진적인 개선이 아닙니다. 마치 물의 온도를 올리면 어느 순간 갑자기 끓기 시작하는 **상전이(Phase Transition)**와 유사합니다.

### 6.7.2 대표적인 창발적 능력들

| 능력 | 설명 | 대략적 등장 규모 |
|------|------|----------------|
| 퓨샷 학습 (Few-shot Learning) | 몇 가지 예시만으로 새로운 태스크 수행 | ~100B+ |
| 사고의 연쇄 (Chain-of-Thought) | 단계별 추론을 통한 문제 해결 | ~100B+ |
| 지시 따르기 (Instruction Following) | 자연어 지시를 정확히 이해하고 수행 | ~50B+ |
| 코드 생성 (Code Generation) | 자연어 설명에서 작동하는 코드 생성 | ~50B+ |
| 다국어 전이 (Multilingual Transfer) | 영어로 배운 능력을 다른 언어에 적용 | ~100B+ |
| 유머 이해 | 농담의 의미와 뉘앙스를 파악 | ~100B+ |
| 자기 교정 (Self-correction) | 자신의 실수를 인식하고 수정 | ~100B+ |

### 6.7.3 창발적 능력에 대한 논쟁

2023년, Stanford 연구진은 "창발적 능력은 평가 지표의 선택에 따른 착시일 수 있다"는 도발적인 주장을 제기했습니다. 비선형적 평가 지표(예: 정확히 맞춤/틀림의 이진 평가)를 사용하면 급격한 변화처럼 보이지만, 연속적인 지표(예: 토큰 단위 정확도)로 측정하면 능력이 점진적으로 향상되는 것처럼 보인다는 것입니다.

이 논쟁은 현재 진행 중이며, 진실은 아마 중간 어딘가에 있을 것입니다. 중요한 것은, **규모의 증가가 양적 변화에 그치지 않고 질적으로 다른 결과를 만들어낸다**는 실용적 관찰은 여전히 유효하다는 점입니다.

## 6.8 평가 지표 (Evaluation Metrics) - 혼란도와 그 너머

### 6.8.1 혼란도 (Perplexity)

혼란도(Perplexity)는 언어 모델의 가장 기본적인 평가 지표입니다. **모델이 다음 토큰을 예측할 때 얼마나 "당황"하는지**를 수치화한 것입니다.

```
Perplexity = 2^(-평균 로그 확률)

직관적 해석:
- Perplexity = 10 → 매 토큰마다 10개 선택지 중 고민
- Perplexity = 100 → 매 토큰마다 100개 선택지 중 고민
- 낮을수록 좋음 (모델이 더 확신을 가지고 예측)
```

| 모델 수준 | 대략적 Perplexity | 의미 |
|-----------|-------------------|------|
| 무작위 추측 | 어휘 크기 (수만) | 전혀 예측 불가 |
| 기본 n-gram | 200+ | 매우 기초적 |
| 초기 신경망 | 50~100 | 기본적 패턴 학습 |
| GPT-2 수준 | 15~30 | 합리적 텍스트 생성 가능 |
| 최신 LLM | 5~15 | 인간에 근접한 예측 |

### 6.8.2 주요 벤치마크 (Benchmarks)

현대 LLM은 다양한 벤치마크로 평가됩니다.

| 벤치마크 | 측정 대상 | 특징 |
|----------|-----------|------|
| MMLU | 57개 학문 분야 지식 | 대학 수준 지식 종합 평가 |
| HumanEval | 코드 생성 능력 | Python 함수 작성 정확도 |
| GSM8K | 수학적 추론 | 초등 수학 문제 풀이 |
| HellaSwag | 상식 추론 | 상황에 맞는 다음 행동 예측 |
| TruthfulQA | 사실 정확성 | 잘못된 통념에 빠지지 않는지 |
| MT-Bench | 대화 능력 | 멀티턴 대화의 질 (GPT-4가 평가) |
| GPQA | 전문가 수준 추론 | 대학원 수준 과학 문제 |
| ARC-AGI | 추상적 추론 | 패턴 인식과 일반화 능력 |

> **주의**: 벤치마크 점수가 높다고 해서 실제 사용에서 항상 더 좋은 것은 아닙니다. 벤치마크는 특정 측면만 측정하며, 모델이 벤치마크에 과적합(Overfitting)될 수도 있습니다. 여러 벤치마크를 종합적으로 보되, 직접 사용해 보는 것이 가장 좋은 평가 방법입니다.

## 6.9 오픈 소스 vs 폐쇄형 생태계 (Open Source vs Closed Source)

### 6.9.1 종합 비교

| 비교 항목 | 오픈 소스 (Open Source) | 폐쇄형 (Closed Source) |
|-----------|----------------------|---------------------|
| **대표 모델** | LLaMA, Mistral, Qwen, DeepSeek | GPT-4, Claude, Gemini |
| **가중치 접근** | 다운로드 및 수정 가능 | API를 통한 접근만 가능 |
| **커스터마이징** | 파인튜닝, 양자화, 구조 변경 가능 | 제한적 (API 파라미터 조정 정도) |
| **배포 자유도** | 자체 서버, 에지 디바이스 배포 가능 | 제공사의 클라우드에 의존 |
| **비용 구조** | GPU 인프라 비용 (고정) | API 사용량 기반 과금 (변동) |
| **최고 성능** | 상위권이나 최상위에는 미달 (격차 축소 중) | 일반적으로 최상위 성능 |
| **데이터 프라이버시** | 데이터가 외부로 나가지 않음 | 제공사 서버로 데이터 전송 |
| **업데이트 속도** | 커뮤니티 기여로 빠른 혁신 | 제공사의 업데이트 일정에 의존 |
| **지원/SLA** | 커뮤니티 지원, 공식 SLA 없음 | 엔터프라이즈 지원, SLA 보장 |
| **투명성** | 아키텍처, 훈련 과정 공개 | 대부분 비공개 |

### 6.9.2 선택 가이드

**오픈 소스가 적합한 경우:**
- 데이터 보안이 최우선인 환경 (의료, 금융, 군사)
- 특정 도메인에 맞춘 파인튜닝이 필요한 경우
- 추론 비용을 최적화하고 싶은 대규모 서비스
- 모델의 동작을 완전히 이해하고 통제해야 하는 경우
- 인터넷 연결이 제한되는 환경 (에지, 온프레미스)

**폐쇄형이 적합한 경우:**
- 최고 수준의 성능이 필요한 경우
- ML 인프라 운영 역량이 부족한 팀
- 빠르게 프로토타이핑하고 제품을 출시해야 하는 경우
- 소규모 사용량으로 인프라 투자가 비효율적인 경우
- 엔터프라이즈 수준의 지원과 SLA가 필요한 경우

### 6.9.3 생태계의 수렴

흥미로운 점은 두 생태계가 점차 **수렴**하고 있다는 것입니다:

- **오픈 소스의 발전**: LLaMA 3.1 405B, DeepSeek-V3 등이 폐쇄형 모델의 성능에 근접
- **폐쇄형의 개방**: OpenAI의 GPT 모델 파인튜닝 API, Anthropic의 Claude 파인튜닝
- **중간 지대의 등장**: "오픈 웨이트(Open Weight)"이지만 훈련 데이터는 비공개인 모델 (예: LLaMA)

## 6.10 실무자를 위한 핵심 요약

### 모델 선택의 의사결정 트리

```
모델을 선택해야 한다면:

1. 데이터가 외부로 나갈 수 없는가?
   ├─ Yes → 오픈 소스 (LLaMA, Mistral, Qwen)
   └─ No  → 2번으로

2. 최고 수준의 추론/코딩 성능이 필요한가?
   ├─ Yes → GPT-4o, Claude 3.5 Opus, Gemini Ultra
   └─ No  → 3번으로

3. 매우 긴 문서를 처리해야 하는가?
   ├─ Yes → Claude (200K), Gemini (1M+)
   └─ No  → 4번으로

4. 비용 효율이 최우선인가?
   ├─ Yes → Claude Haiku, GPT-4o mini, 오픈 소스 소형 모델
   └─ No  → 용도에 맞는 최적 모델 선택
```

### 이 장에서 기억해야 할 것들

1. **다음 토큰 예측(Next Token Prediction)**이라는 단순한 목표가 놀라운 능력을 만들어냅니다. 그 단순함의 깊이를 과소평가하지 마세요.

2. **매개변수 수가 전부가 아닙니다.** 아키텍처, 데이터 품질, 훈련 기법이 모두 중요합니다. 작지만 잘 훈련된 모델이 크고 덜 훈련된 모델을 이길 수 있습니다.

3. **컨텍스트 윈도우는 급격히 확장 중**이며, 이는 RAG, 문서 처리, 코드 분석 등 실무 활용 방식을 근본적으로 바꾸고 있습니다.

4. **스케일링 법칙**은 강력한 경험적 관찰이지만, 한계가 없는 것은 아닙니다. 데이터 고갈과 비용 문제가 현실적 제약입니다.

5. **오픈 소스와 폐쇄형의 격차는 줄어들고 있습니다.** 상황에 맞는 유연한 선택이 중요합니다.

6. **벤치마크는 참고 자료일 뿐**, 실제 사용 환경에서의 평가가 가장 중요합니다.
