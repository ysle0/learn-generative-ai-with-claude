# Chapter 11: AI 에이전트 (AI Agent)

> **이 장의 대상 독자:** Claude Code, Kilo Code 같은 AI 도구를 매일 사용하지만,
> 그것이 왜 "에이전트"인지, 내부에서 어떤 일이 벌어지는지 궁금했던 개발자

---

## 핵심 키워드 요약

| 키워드 | 정의 |
|--------|------|
| **AI 에이전트 (AI Agent)** | LLM이 외부 환경을 관찰하고, 판단하고, 행동까지 수행하는 자율적 시스템 |
| **도구 사용 (Tool Use)** | LLM이 외부 함수나 API를 호출하여 실제 작업을 수행하는 메커니즘 |
| **함수 호출 (Function Calling)** | 모델이 구조화된 JSON 형태로 어떤 함수를 어떤 인자로 호출할지 결정하는 기능 |
| **에이전트 루프 (Agent Loop)** | 관찰 -> 사고 -> 행동 -> 반복의 순환 구조 |
| **계획 수립 (Planning)** | 복잡한 작업을 하위 단계로 분해하여 순차적으로 실행하는 능력 |
| **메모리 (Memory)** | 에이전트가 맥락을 유지하고 과거 정보를 활용하는 메커니즘 |
| **멀티 에이전트 (Multi-Agent)** | 여러 에이전트가 역할을 나누어 협업하는 시스템 |
| **LangChain** | LLM 기반 애플리케이션 개발을 위한 프레임워크 |
| **LangGraph** | 상태 기반의 멀티 에이전트 워크플로우를 구성하는 프레임워크 |
| **CrewAI** | 역할 기반 멀티 에이전트 협업 프레임워크 |
| **휴먼 인 더 루프 (Human-in-the-Loop)** | 중요한 결정에서 사람의 승인을 요구하는 안전 메커니즘 |

## 1. 에이전트란 무엇인가

### 1.1 챗봇과 에이전트의 결정적 차이

여러분이 ChatGPT 웹에서 "이 코드를 리팩터링해줘"라고 요청하면, 챗봇은 **텍스트로
리팩터링된 코드를 보여줍니다.** 여러분이 그 코드를 복사해서 에디터에 붙여넣어야 합니다.

반면 Claude Code에서 같은 요청을 하면? Claude Code는 **직접 파일을 읽고, 수정하고,
터미널 명령을 실행합니다.** 여러분은 결과를 확인만 하면 됩니다.

```
+-------------------------------------------------------------------+
|                         챗봇 (Chatbot)                             |
|                                                                   |
|   사용자 --> [질문] --> LLM --> [텍스트 답변] --> 사용자            |
|                                                                   |
|   "이렇게 하시면 됩니다..." (말만 해줌)                            |
+-------------------------------------------------------------------+

+-------------------------------------------------------------------+
|                       에이전트 (Agent)                              |
|                                                                   |
|   사용자 --> [목표] --> LLM --> [파일 읽기] --> [코드 수정]         |
|                            --> [테스트 실행] --> [결과 확인]        |
|                            --> [추가 수정]  --> 사용자에게 보고     |
|                                                                   |
|   "직접 해드리겠습니다." (실제로 행동함)                            |
+-------------------------------------------------------------------+
```

이 차이가 핵심입니다. **에이전트(Agent)는 세상에 "행동(Act)"하는 LLM 시스템**입니다.

### 1.2 에이전트의 핵심 구성 요소

에이전트가 단순한 챗봇과 구별되는 세 가지 요소가 있습니다.

1. **인식(Perception):** 환경의 상태를 관찰합니다 -- 파일 시스템, 터미널 출력, 검색 결과 등
2. **추론(Reasoning):** 관찰한 정보를 바탕으로 다음에 무엇을 할지 판단합니다
3. **행동(Action):** 도구를 사용하여 환경을 실제로 변경합니다 -- 파일 편집, 명령 실행 등

개발자에게 친숙한 비유를 들자면, 챗봇은 Stack Overflow에서 답변을 읽어주는 사람이고,
에이전트는 여러분 옆에 앉아서 직접 키보드를 잡고 코드를 고치는 페어 프로그래머입니다.

## 2. 도구 사용과 함수 호출 (Tool Use / Function Calling)

### 2.1 LLM은 어떻게 "행동"하는가

LLM 자체는 텍스트를 생성할 뿐입니다. 파일을 읽거나 명령을 실행하는 능력이 내장되어
있지 않습니다. 그렇다면 Claude Code는 어떻게 파일을 수정하고 `git commit`을 실행할까요?

답은 **도구 사용(Tool Use)** 입니다. 에이전트 시스템은 LLM에게 사용 가능한 도구 목록을
제공하고, LLM은 어떤 도구를 어떤 인자로 호출할지를 **구조화된 형태로 출력**합니다.
그러면 에이전트 런타임이 실제로 그 도구를 실행합니다.

```
+-----------------------------------------------------------------+
|  에이전트 런타임 (Claude Code)                                    |
|                                                                   |
|  1. 사용자 요청 + 도구 목록  --> [ LLM (Claude) ]                 |
|                                                                   |
|  2. LLM 출력: "Read 도구를 호출하겠습니다"                         |
|     { "tool": "Read", "params": { "path": "src/main.ts" } }      |
|                                                                   |
|  3. 런타임이 실제 파일을 읽어서 결과를 LLM에게 전달                |
|                                                                   |
|  4. LLM이 결과를 보고 다음 행동을 결정                             |
+-----------------------------------------------------------------+
```

### 2.2 함수 정의의 JSON 스키마

LLM에게 도구를 알려줄 때는 JSON Schema 형태로 정의합니다. Claude Code가 사용하는
도구들을 단순화하면 이런 구조입니다.

```json
{
  "name": "Read",
  "description": "파일의 내용을 읽어옵니다",
  "parameters": {
    "type": "object",
    "properties": {
      "file_path": {
        "type": "string",
        "description": "읽을 파일의 절대 경로"
      },
      "offset": {
        "type": "number",
        "description": "읽기 시작할 줄 번호 (선택)"
      },
      "limit": {
        "type": "number",
        "description": "읽을 줄 수 (선택)"
      }
    },
    "required": ["file_path"]
  }
}
```

```json
{
  "name": "Edit",
  "description": "파일에서 특정 문자열을 찾아 교체합니다",
  "parameters": {
    "type": "object",
    "properties": {
      "file_path": { "type": "string" },
      "old_string": { "type": "string", "description": "교체할 기존 문자열" },
      "new_string": { "type": "string", "description": "새로운 문자열" }
    },
    "required": ["file_path", "old_string", "new_string"]
  }
}
```

```json
{
  "name": "Bash",
  "description": "터미널에서 명령을 실행합니다",
  "parameters": {
    "type": "object",
    "properties": {
      "command": { "type": "string", "description": "실행할 bash 명령" }
    },
    "required": ["command"]
  }
}
```

개발자라면 이 구조가 익숙할 것입니다. API의 엔드포인트 정의, OpenAPI(Swagger) 스펙과
본질적으로 같은 패턴입니다. LLM에게 "이런 함수들을 쓸 수 있어"라고 알려주는 것입니다.

### 2.3 모델은 어떻게 도구를 선택하는가

LLM은 도구 선택을 "학습"합니다. 훈련 과정에서 수많은 도구 사용 예시를 학습했기 때문에,
사용자의 요청과 현재 맥락을 보고 **어떤 도구를 어떤 인자로 호출해야 하는지**를
추론할 수 있습니다.

예를 들어 여러분이 Claude Code에 이렇게 말한다고 합시다.

> "src/utils.ts에서 calculateTotal 함수의 버그를 고쳐줘"

Claude의 내부 추론 과정은 대략 이렇습니다.

```
1. 사용자가 특정 파일의 특정 함수를 수정하길 원한다
2. 먼저 해당 파일의 내용을 봐야 한다
   --> Read 도구 호출: { "file_path": "src/utils.ts" }

3. 파일 내용을 읽었다. calculateTotal 함수를 찾았다. 버그를 발견했다.
4. 수정해야 한다
   --> Edit 도구 호출: { "file_path": "src/utils.ts",
                        "old_string": "return price * count",
                        "new_string": "return price * count * (1 - discount)" }

5. 수정이 완료되었다. 테스트를 실행해서 확인하자
   --> Bash 도구 호출: { "command": "npm test" }
```

이 과정이 바로 여러분이 매일 Claude Code에서 경험하는 것입니다. Claude가 파일을 읽고,
수정하고, 테스트를 실행하는 그 흐름 하나하나가 **도구 호출(Function Calling)** 입니다.

## 3. 에이전트 루프 (The Agent Loop)

### 3.1 관찰 -> 사고 -> 행동 -> 반복

에이전트의 핵심은 **루프(Loop)** 입니다. 한 번의 도구 호출로 끝나는 것이 아니라,
결과를 관찰하고, 다시 생각하고, 다시 행동하는 과정을 **목표가 달성될 때까지** 반복합니다.

```
    +----------------------------------------------------------+
    |                   에이전트 루프 (Agent Loop)                |
    +----------------------------------------------------------+
    |                                                            |
    |         +-------------+                                    |
    |         |   사용자    |                                    |
    |         |   목표 설정 |                                    |
    |         +------+------+                                    |
    |                |                                           |
    |                v                                           |
    |   +---> [ 관찰 (Observe) ]                                 |
    |   |      환경 상태 파악:                                    |
    |   |      파일 내용, 에러 메시지,                             |
    |   |      터미널 출력 등                                     |
    |   |            |                                           |
    |   |            v                                           |
    |   |    [ 사고 (Think) ]                                    |
    |   |      다음 행동 결정:                                    |
    |   |      "테스트가 실패했으니                                |
    |   |       에러 원인을 찾아보자"                              |
    |   |            |                                           |
    |   |            v                                           |
    |   |    [ 행동 (Act) ]                                      |
    |   |      도구 호출:                                         |
    |   |      파일 읽기, 코드 수정,                               |
    |   |      명령 실행 등                                       |
    |   |            |                                           |
    |   |            v                                           |
    |   |    { 목표 달성? }-----예-----> [ 완료: 결과 보고 ]       |
    |   |            |                                           |
    |   +---아니오---+                                            |
    |                                                            |
    +----------------------------------------------------------+
```

### 3.2 개발자를 위한 비유: REPL과의 비교

개발자라면 REPL(Read-Eval-Print Loop)에 익숙할 것입니다. Python이나 Node.js의
인터랙티브 셸을 떠올려 보세요.

```
REPL (Read-Eval-Print Loop)          Agent Loop
================================     ================================
Read   : 사용자 입력을 읽는다        Observe : 환경 상태를 관찰한다
Eval   : 코드를 실행한다             Think   : 다음 행동을 추론한다
Print  : 결과를 출력한다             Act     : 도구를 실행한다
Loop   : 반복한다                    Repeat  : 목표까지 반복한다
```

결정적 차이는 REPL에서는 **사람이** 매번 입력을 제공하지만, 에이전트 루프에서는
**LLM이 스스로** 다음 입력을 결정한다는 점입니다. 에이전트는 자율적인 REPL입니다.

### 3.3 Claude Code에서 실제로 일어나는 일

여러분이 Claude Code에 "이 프로젝트에 ESLint를 설정해줘"라고 요청하면 다음과 같은
에이전트 루프가 실행됩니다.

```
[루프 1] 관찰: 프로젝트 구조를 모른다
         사고: 먼저 package.json을 확인하자
         행동: Read("package.json")

[루프 2] 관찰: React + TypeScript 프로젝트임을 확인
         사고: ESLint와 관련 플러그인을 설치하자
         행동: Bash("npm install -D eslint @typescript-eslint/parser ...")

[루프 3] 관찰: 패키지 설치 완료
         사고: 설정 파일을 생성하자
         행동: Write(".eslintrc.json", { ... })

[루프 4] 관찰: 설정 파일 생성 완료
         사고: package.json에 lint 스크립트를 추가하자
         행동: Edit("package.json", ...)

[루프 5] 관찰: 스크립트 추가 완료
         사고: lint를 실행해서 잘 동작하는지 확인하자
         행동: Bash("npm run lint")

[루프 6] 관찰: lint가 정상 실행됨 (경고 3개, 에러 0개)
         사고: 설정이 완료되었다. 사용자에게 결과를 보고하자
         행동: 완료 보고
```

6번의 루프가 자동으로 돌면서, 여러분이 일일이 지시하지 않아도 Claude Code가
알아서 다음 단계를 판단하고 실행합니다. 이것이 에이전트의 힘입니다.

## 4. 계획 수립 (Planning)

### 4.1 복잡한 작업의 분해

"이 모듈을 리팩터링해줘"라는 요청은 단순한 한 단계 작업이 아닙니다. 에이전트는
이를 실행 가능한 하위 작업으로 **분해(Decompose)** 해야 합니다.

```
사용자 요청: "UserService 모듈을 리팩터링해줘"

에이전트의 내부 계획:
+---------------------------------------------------------------+
| 1단계: 현재 코드 분석                                           |
|   - UserService.ts 파일 읽기                                    |
|   - 의존 관계 파악 (import 추적)                                 |
|   - 테스트 파일 확인                                             |
|                                                                 |
| 2단계: 문제점 식별                                               |
|   - God class 패턴 (하나의 클래스가 너무 많은 일을 함)           |
|   - 인증 로직과 프로필 로직이 혼재                                |
|                                                                 |
| 3단계: 리팩터링 실행                                             |
|   - AuthService.ts 분리                                          |
|   - ProfileService.ts 분리                                       |
|   - UserService.ts를 Facade 패턴으로 변경                        |
|                                                                 |
| 4단계: 검증                                                      |
|   - 기존 테스트 실행                                              |
|   - import 경로 업데이트                                          |
|   - 빌드 확인                                                    |
+---------------------------------------------------------------+
```

### 4.2 계획 수립의 두 가지 방식

에이전트가 계획을 세우는 방식은 크게 두 가지입니다.

**사전 계획 (Plan-then-Execute):**
전체 계획을 먼저 세우고 순차적으로 실행합니다. 명확한 작업에 적합합니다.

**적응형 계획 (Adaptive Planning):**
한 단계를 실행한 후 결과를 보고 다음 계획을 조정합니다. Claude Code는 주로 이
방식을 사용합니다. 테스트가 실패하면 계획을 수정하고, 예상치 못한 의존성을 발견하면
접근 방식을 바꿉니다.

실제로 여러분이 Claude Code를 사용할 때 "먼저 코드를 살펴보겠습니다"라는 메시지를
자주 보셨을 것입니다. 이것이 바로 적응형 계획의 첫 단계 -- 환경을 관찰한 후
구체적인 실행 계획을 세우는 과정입니다.

## 5. 메모리 관리 (Memory Management)

### 5.1 에이전트의 세 가지 메모리

사람에게 단기 기억, 장기 기억, 작업 기억이 있듯이, 에이전트에게도 세 가지 유형의
메모리가 있습니다.

```
+---------------------------------------------------------------+
|                    에이전트 메모리 체계                          |
+---------------------------------------------------------------+
|                                                                 |
|  [ 단기 메모리 (Short-term Memory) ]                            |
|    = 대화 컨텍스트 (Conversation Context)                       |
|    현재 대화에서 주고받은 메시지와 도구 호출 결과                  |
|    Claude Code의 현재 세션에 해당                                |
|    제한: 컨텍스트 윈도우 크기 (예: 200K 토큰)                    |
|                                                                 |
|  [ 장기 메모리 (Long-term Memory) ]                             |
|    = 세션 간 유지되는 정보                                       |
|    벡터 데이터베이스에 저장된 과거 대화 요약                      |
|    프로젝트 구조, 코딩 스타일 선호도 등                           |
|    Claude Code의 CLAUDE.md 파일이 이 역할을 수행                 |
|                                                                 |
|  [ 작업 메모리 (Working Memory) ]                               |
|    = 스크래치패드 (Scratchpad)                                   |
|    현재 작업 진행 상황, 중간 계산 결과                             |
|    "지금까지 3개 파일을 수정했고, 2개가 남았다"                    |
|    에이전트 내부의 상태 추적에 사용                                |
|                                                                 |
+---------------------------------------------------------------+
```

### 5.2 컨텍스트 윈도우의 한계와 대응

LLM의 컨텍스트 윈도우는 크지만 무한하지 않습니다. 긴 대화를 나누다 보면 초기 내용이
밀려나가는 문제가 발생합니다. 이를 해결하는 전략들이 있습니다.

**요약 (Summarization):**
오래된 대화 내용을 LLM이 요약하여 압축합니다. 100개의 메시지를 핵심 내용 요약
하나로 대체하면 토큰을 절약할 수 있습니다.

**벡터 저장소 (Vector Storage):**
과거 대화나 문서를 임베딩(Embedding)으로 변환하여 벡터 데이터베이스에 저장합니다.
필요할 때 의미적으로 유사한 정보를 검색하여 컨텍스트에 포함시킵니다.
이것이 RAG(Retrieval-Augmented Generation)의 핵심이기도 합니다.

**스크래치패드 패턴 (Scratchpad Pattern):**
에이전트가 중간 결과나 작업 상태를 명시적으로 기록하는 패턴입니다. 개발자의
TODO 리스트와 비슷합니다. Claude Code가 복잡한 리팩터링 중에 "수정할 파일 목록"을
내부적으로 추적하는 것이 이에 해당합니다.

### 5.3 Claude Code에서의 메모리

Claude Code를 사용할 때 경험하는 메모리 메커니즘을 정리하면 다음과 같습니다.

- **세션 내 기억:** 현재 대화에서 수정한 파일, 실행한 명령의 결과를 기억합니다
- **CLAUDE.md:** 프로젝트별 지침과 규칙을 담는 파일로, 장기 메모리 역할을 합니다
- **파일 시스템 자체:** 에이전트가 파일을 읽어서 정보를 얻으므로, 코드베이스
  자체가 일종의 외부 메모리 역할을 합니다

## 6. 멀티 에이전트 시스템 (Multi-Agent Systems)

### 6.1 왜 여러 에이전트가 필요한가

하나의 에이전트로 모든 것을 처리할 수 있지만, 작업이 복잡해지면 **역할 분담**이
효율적입니다. 소프트웨어 개발에서 한 사람이 설계, 구현, 테스트, 배포를 모두 하는
것보다 팀으로 나누는 것이 효과적인 것과 같은 원리입니다.

### 6.2 오케스트레이터-워커 패턴 (Orchestrator-Worker Pattern)

가장 일반적인 멀티 에이전트 패턴입니다. 하나의 오케스트레이터 에이전트가 작업을
분배하고, 여러 워커 에이전트가 각자의 작업을 수행합니다.

```
                    [ 오케스트레이터 에이전트 ]
                     "전체 작업을 관리한다"
                    /          |          \
                   /           |           \
                  v            v            v
        [ 워커 A ]      [ 워커 B ]      [ 워커 C ]
        "프론트엔드     "백엔드 API     "데이터베이스
         UI 수정"        구현"           스키마 설계"
                  \           |           /
                   \          |          /
                    v         v         v
                    [ 오케스트레이터가 결과 통합 ]
```

이 패턴을 실제 개발 워크플로우에 적용하면, 코드 리뷰 에이전트, 테스트 작성 에이전트,
문서화 에이전트가 각각 독립적으로 동작하면서 오케스트레이터가 전체를 조율합니다.

### 6.3 토론/논쟁 패턴 (Debate/Discussion Pattern)

여러 에이전트가 같은 문제에 대해 서로 다른 관점에서 토론하는 패턴입니다.

```
[ 에이전트 A: 찬성 입장 ]  <--논쟁-->  [ 에이전트 B: 반대 입장 ]
          \                                /
           \                              /
            v                            v
            [ 판정 에이전트: 최종 결론 도출 ]
```

예를 들어 아키텍처 결정에서 "마이크로서비스를 도입해야 한다"와 "모놀리스를
유지해야 한다"는 두 관점을 에이전트가 각각 대변하며 논쟁합니다. 이를 통해
한쪽으로 치우친 결론을 피하고 균형 잡힌 판단을 내릴 수 있습니다.

### 6.4 멀티 에이전트의 현실적 도전

멀티 에이전트 시스템은 매력적이지만 현실적인 문제도 있습니다.

- **비용:** 에이전트마다 LLM API를 호출하므로 비용이 배수로 증가합니다
- **조율 복잡성:** 에이전트 간 메시지 전달과 상태 동기화가 까다롭습니다
- **디버깅 난이도:** 어떤 에이전트가 잘못된 판단을 내렸는지 추적하기 어렵습니다

## 7. 에이전트 프레임워크 (Agent Frameworks)

직접 에이전트를 처음부터 만드는 대신, 검증된 프레임워크를 사용하면 개발 속도를
높일 수 있습니다. 주요 프레임워크를 비교합니다.

### 7.1 LangChain

가장 널리 알려진 LLM 애플리케이션 프레임워크입니다. 도구, 메모리, 체인(Chain)
등의 추상화를 제공합니다.

```python
from langchain.agents import create_tool_calling_agent
from langchain_anthropic import ChatAnthropic

# 도구 정의
tools = [file_read_tool, file_write_tool, bash_tool]

# 에이전트 생성
llm = ChatAnthropic(model="claude-sonnet-4-20250514")
agent = create_tool_calling_agent(llm, tools, prompt)
```

**장점:** 생태계가 넓고 문서가 풍부합니다
**단점:** 추상화 레이어가 많아 디버깅이 어려울 수 있습니다

### 7.2 LangGraph

LangChain 팀이 만든 상태 기반 워크플로우 프레임워크입니다. 에이전트의 행동을
**그래프(Graph)** 형태로 정의합니다.

```python
from langgraph.graph import StateGraph

# 상태 그래프 정의
workflow = StateGraph(AgentState)
workflow.add_node("analyze", analyze_code)
workflow.add_node("modify", modify_code)
workflow.add_node("test", run_tests)

# 노드 간 연결
workflow.add_edge("analyze", "modify")
workflow.add_conditional_edges("test", should_retry)
```

**장점:** 복잡한 워크플로우를 시각적으로 설계할 수 있습니다
**단점:** 단순한 작업에는 과한 설계일 수 있습니다

### 7.3 CrewAI

역할 기반의 멀티 에이전트 프레임워크입니다. 각 에이전트에게 역할(Role)과
목표(Goal)를 부여합니다.

```python
from crewai import Agent, Task, Crew

# 에이전트 역할 정의
code_reviewer = Agent(
    role="코드 리뷰어",
    goal="코드 품질 문제를 찾아 개선점을 제안한다",
    backstory="10년 경력의 시니어 개발자"
)

test_writer = Agent(
    role="테스트 작성자",
    goal="누락된 테스트 케이스를 식별하고 작성한다",
    backstory="TDD 전문가"
)

crew = Crew(agents=[code_reviewer, test_writer], tasks=[...])
```

### 7.4 AutoGen (Microsoft)

Microsoft가 개발한 멀티 에이전트 대화 프레임워크입니다. 에이전트 간의 대화를
통해 작업을 수행하는 패턴에 특화되어 있습니다.

### 7.5 Semantic Kernel (Microsoft)

Microsoft의 또 다른 프레임워크로, 기존 애플리케이션에 AI 기능을 통합하는 데
초점을 맞추고 있습니다. C#과 Python을 모두 지원하며, 엔터프라이즈 환경에
적합합니다.

### 7.6 프레임워크 선택 가이드

```
+----------------------------------------------------------------+
| 사용 사례                    | 추천 프레임워크                   |
|------------------------------|----------------------------------|
| 단일 에이전트, 빠른 프로토타입  | LangChain                       |
| 복잡한 워크플로우, 상태 관리   | LangGraph                       |
| 역할 기반 멀티 에이전트       | CrewAI                           |
| 에이전트 간 대화 중심         | AutoGen                          |
| 엔터프라이즈 통합             | Semantic Kernel                  |
+----------------------------------------------------------------+
```

## 8. Claude Code와 Kilo Code는 왜 에이전트인가

### 8.1 매일 쓰는 도구의 정체

여러분이 매일 사용하는 Claude Code와 Kilo Code는 단순한 챗봇이 아닙니다.
이 장에서 다룬 모든 에이전트 개념이 적용된 **완전한 AI 에이전트**입니다.

### 8.2 Claude Code의 에이전트 루프

Claude Code가 작업을 수행하는 과정을 에이전트 루프로 분석해 봅시다.

```
+------------------------------------------------------------------+
|  Claude Code 에이전트 아키텍처                                     |
+------------------------------------------------------------------+
|                                                                    |
|  [ 사용자 ] --요청--> [ 에이전트 런타임 ]                           |
|                           |                                        |
|                    +------v------+                                  |
|                    |   Claude    |                                  |
|                    |   (LLM)    |                                   |
|                    +------+------+                                  |
|                           |                                        |
|                    도구 호출 결정                                    |
|                    /    |    |    \                                  |
|                   v     v    v     v                                |
|               [Read] [Edit] [Bash] [Grep]                          |
|               [Write][Glob] [WebFetch] ...                         |
|                   \     |    |     /                                |
|                    v    v    v    v                                  |
|                    결과를 Claude에게 반환                            |
|                           |                                        |
|                    다음 행동 결정 또는 완료                          |
|                           |                                        |
|  [ 사용자 ] <--결과-- [ 에이전트 런타임 ]                           |
|                                                                    |
+------------------------------------------------------------------+
```

### 8.3 Claude Code가 사용하는 도구들

Claude Code는 다양한 도구를 통해 개발 환경과 상호작용합니다.

| 도구 | 역할 | 에이전트 관점 |
|------|------|--------------|
| **Read** | 파일 내용 읽기 | 환경 관찰 (Observe) |
| **Glob** | 파일 패턴 검색 | 환경 탐색 (Explore) |
| **Grep** | 코드 내용 검색 | 정보 수집 (Gather) |
| **Edit** | 파일 내용 수정 | 환경 변경 (Act) |
| **Write** | 새 파일 생성 | 환경 변경 (Act) |
| **Bash** | 터미널 명령 실행 | 환경 변경 + 관찰 (Act + Observe) |

여러분이 Claude Code에서 보는 모든 행동은 위 도구들의 조합입니다.
"파일을 읽겠습니다" -> Read, "검색하겠습니다" -> Grep, "수정하겠습니다" -> Edit,
"테스트를 실행하겠습니다" -> Bash. 이 도구 호출이 에이전트 루프 안에서 반복됩니다.

### 8.4 Kilo Code도 같은 원리

Kilo Code 역시 같은 에이전트 패턴을 따릅니다. VS Code 확장으로 동작하며,
에디터의 파일 시스템과 터미널에 접근하는 도구들을 LLM에게 제공합니다.
사용자의 요청을 받으면 에이전트 루프를 돌며 코드를 읽고, 분석하고, 수정합니다.

핵심은 동일합니다: **LLM + 도구 + 루프 = 에이전트**

## 9. 안전과 통제 (Safety and Control)

### 9.1 에이전트에게 권한을 주는 것의 위험

에이전트는 파일을 수정하고 명령을 실행합니다. 이는 강력하지만 위험하기도 합니다.
잘못된 판단 한 번이 프로덕션 데이터베이스를 삭제하거나, 민감한 정보를 외부에
전송할 수 있습니다.

### 9.2 휴먼 인 더 루프 (Human-in-the-Loop)

가장 기본적인 안전 장치는 **중요한 행동 전에 사람의 승인을 요구하는 것**입니다.

```
에이전트: "다음 명령을 실행하려고 합니다:"
         rm -rf build/ && npm run build
         [승인] [거부]

사용자:  [승인 클릭]

에이전트: (명령 실행)
```

Claude Code를 사용할 때 파일 수정이나 명령 실행 전에 확인을 요청하는 것이
바로 이 패턴입니다. 여러분이 "y"를 누르거나 승인 버튼을 클릭해야 에이전트가
행동을 수행합니다.

### 9.3 샌드박싱 (Sandboxing)

에이전트의 행동 범위를 제한하는 방법입니다.

- **파일 시스템 제한:** 프로젝트 디렉토리 밖의 파일에 접근하지 못하게 합니다
- **네트워크 제한:** 외부 네트워크 요청을 차단하거나 허용 목록으로 관리합니다
- **명령 제한:** 실행할 수 있는 셸 명령의 종류를 제한합니다
- **리소스 제한:** CPU, 메모리, 실행 시간에 상한을 둡니다

Claude Code는 이러한 샌드박싱 기법을 조합하여, 에이전트가 의도치 않게
시스템에 해를 끼치는 것을 방지합니다.

### 9.4 권한 수준 설계

실제 에이전트 시스템에서는 행동의 위험도에 따라 권한 수준을 나눕니다.

```
+----------------------------------------------------------------+
| 위험도  | 행동 예시              | 필요한 통제                   |
|---------|----------------------|-------------------------------|
| 낮음    | 파일 읽기, 검색       | 자동 승인 (사용자 확인 불필요)  |
| 중간    | 파일 수정, 패키지 설치  | 사용자 확인 후 실행            |
| 높음    | 시스템 명령, 네트워크   | 명시적 승인 + 샌드박싱         |
| 최고    | 프로덕션 배포, 삭제     | 다중 승인 + 감사 로그          |
+----------------------------------------------------------------+
```

## 10. 실전 정리: 에이전트를 이해하면 도구를 더 잘 쓸 수 있다

이 장에서 배운 개념들이 여러분의 일상적인 도구 사용에 어떻게 도움이 되는지
정리합니다.

### 에이전트 루프를 이해하면

Claude Code가 왜 때때로 "돌아가는" 느낌이 드는지 알 수 있습니다. 에이전트가
여러 번의 루프를 돌며 문제를 해결하고 있는 것입니다. 첫 번째 시도에서 실패해도
결과를 관찰하고 다른 접근법을 시도합니다.

### 도구 사용을 이해하면

에이전트에게 더 효과적으로 지시할 수 있습니다. "src 폴더의 모든 TypeScript 파일에서
deprecated API 호출을 찾아줘"라고 구체적으로 말하면, 에이전트가 Grep 도구를
효율적으로 사용할 수 있습니다.

### 메모리 한계를 이해하면

왜 긴 대화 끝에 에이전트가 초반 내용을 "잊어버리는" 것처럼 보이는지 이해할 수
있습니다. 새로운 세션을 시작하거나, 중요한 맥락을 다시 상기시켜 주는 것이
효과적입니다. CLAUDE.md에 프로젝트 규칙을 적어두면 매 세션마다 장기 메모리가
작동합니다.

### 계획 수립을 이해하면

복잡한 작업을 요청할 때 에이전트가 한 번에 완벽하게 처리하기 어렵다는 것을
인정하고, 단계별로 나누어 요청하거나, 에이전트의 중간 결과를 확인하며
방향을 조정할 수 있습니다.

|     JSON Schema로 정의된 함수를 LLM이 호출한다                    |
|                                                                  |
|  3. 에이전트 루프: 관찰 -> 사고 -> 행동 -> 반복                   |
|     목표 달성까지 자율적으로 반복하는 REPL이다                     |
|                                                                  |
|  4. Claude Code와 Kilo Code는 완전한 AI 에이전트다                |
|     파일 읽기, 수정, 명령 실행이 모두 도구 호출이다                |
|                                                                  |
|  5. 안전 장치(Human-in-the-Loop)가 필수다                         |
|     에이전트에게 권한을 주되, 통제를 유지해야 한다                  |
|                                                                  |
+================================================================+
