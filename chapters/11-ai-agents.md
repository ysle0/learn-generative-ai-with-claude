> 그것이 왜 "에이전트"인지, 내부에서 어떤 일이 벌어지는지 궁금했던 개발자

## 핵심 키워드 요약

| 키워드 | 정의 |
|--------|------|
| **AI 에이전트 (AI Agent)** | LLM이 외부 환경을 관찰하고, 판단하고, 행동까지 수행하는 자율적 시스템 |
| **도구 사용 (Tool Use)** | LLM이 외부 함수나 API를 호출하여 실제 작업을 수행하는 메커니즘 |
| **함수 호출 (Function Calling)** | 모델이 구조화된 JSON으로 어떤 함수를 어떤 인자로 호출할지 결정하는 기능 |
| **에이전트 루프 (Agent Loop)** | 관찰 -> 사고 -> 행동 -> 반복의 순환 구조 |
| **계획 수립 (Planning)** | 복잡한 작업을 하위 단계로 분해하여 순차 실행하는 능력 |
| **메모리 (Memory)** | 에이전트가 맥락을 유지하고 과거 정보를 활용하는 메커니즘 |
| **멀티 에이전트 (Multi-Agent)** | 여러 에이전트가 역할을 나누어 협업하는 시스템 |
| **LangChain / LangGraph** | LLM 애플리케이션 및 상태 기반 워크플로우 프레임워크 |
| **CrewAI** | 역할 기반 멀티 에이전트 협업 프레임워크 |
| **휴먼 인 더 루프 (Human-in-the-Loop)** | 중요한 결정에서 사람의 승인을 요구하는 안전 메커니즘 |

## 1. 에이전트란 무엇인가

### 1.1 챗봇과 에이전트의 결정적 차이

ChatGPT 웹에서 "이 코드를 리팩터링해줘"라고 요청하면, 챗봇은 **텍스트로 코드를
보여줍니다.** 여러분이 복사해서 에디터에 붙여넣어야 합니다.

Claude Code에서 같은 요청을 하면? **직접 파일을 읽고, 수정하고, 터미널 명령을
실행합니다.** 여러분은 결과를 확인만 하면 됩니다.

```
+---------------------------------------------------------------+
|  챗봇 (Chatbot)                                                |
|  사용자 --> [질문] --> LLM --> [텍스트 답변] --> 사용자          |
|  "이렇게 하시면 됩니다..." (말만 해줌)                          |
+---------------------------------------------------------------+
|  에이전트 (Agent)                                               |
|  사용자 --> [목표] --> LLM --> [파일 읽기] --> [코드 수정]       |
|                           --> [테스트 실행] --> [결과 확인]      |
|                           --> [추가 수정]  --> 사용자에게 보고   |
|  "직접 해드리겠습니다." (실제로 행동함)                          |
+---------------------------------------------------------------+
```

**에이전트(Agent)는 세상에 "행동(Act)"하는 LLM 시스템**입니다. 에이전트를 구성하는
세 가지 핵심 요소는 다음과 같습니다.

1. **인식(Perception):** 환경을 관찰합니다 -- 파일 시스템, 터미널 출력, 검색 결과
2. **추론(Reasoning):** 관찰 결과를 바탕으로 다음 행동을 판단합니다
3. **행동(Action):** 도구를 사용하여 환경을 실제로 변경합니다

개발자에게 친숙한 비유로, 챗봇은 Stack Overflow에서 답변을 읽어주는 사람이고,
에이전트는 옆에 앉아 직접 키보드를 잡고 코드를 고치는 페어 프로그래머입니다.

## 2. 도구 사용과 함수 호출 (Tool Use / Function Calling)

### 2.1 LLM은 어떻게 "행동"하는가

LLM 자체는 텍스트를 생성할 뿐입니다. 파일을 읽거나 명령을 실행하는 능력이 내장되어
있지 않습니다. 비결은 **도구 사용(Tool Use)** 입니다. 에이전트 시스템이 LLM에게
사용 가능한 도구 목록을 제공하면, LLM은 어떤 도구를 어떤 인자로 호출할지를
**구조화된 JSON으로 출력**하고, 에이전트 런타임이 실제로 실행합니다.

```
+---------------------------------------------------------------+
|  에이전트 런타임 (예: Claude Code)                               |
|                                                                 |
|  1. 사용자 요청 + 도구 목록  -->  [ LLM (Claude) ]              |
|  2. LLM 출력: { "tool": "Read", "path": "src/main.ts" }        |
|  3. 런타임이 실제 파일을 읽어서 결과를 LLM에게 전달              |
|  4. LLM이 결과를 보고 다음 행동을 결정                           |
+---------------------------------------------------------------+
```

### 2.2 함수 정의의 JSON 스키마

LLM에게 도구를 알려줄 때는 JSON Schema로 정의합니다. Claude Code의 Read 도구를
단순화하면 이런 구조입니다.

```json
{
  "name": "Read",
  "description": "파일의 내용을 읽어옵니다",
  "parameters": {
    "type": "object",
    "properties": {
      "file_path": { "type": "string", "description": "읽을 파일의 절대 경로" },
      "offset":    { "type": "number", "description": "시작 줄 번호 (선택)" },
      "limit":     { "type": "number", "description": "읽을 줄 수 (선택)" }
    },
    "required": ["file_path"]
  }
}
```

Edit, Bash, Grep, Write 등 모든 도구가 같은 패턴입니다. OpenAPI(Swagger) 스펙과
본질적으로 동일한 구조입니다 -- LLM에게 인터페이스를 선언하는 것입니다.

### 2.3 모델은 어떻게 도구를 선택하는가

LLM은 훈련 과정에서 수많은 도구 사용 예시를 학습했기 때문에, 사용자의 요청과
현재 맥락을 보고 어떤 도구를 어떤 인자로 호출할지 추론합니다. 예를 들어:

> "src/utils.ts에서 calculateTotal 함수의 버그를 고쳐줘"

```
1. 먼저 파일 내용을 봐야 한다
   --> Read("src/utils.ts")

2. 함수를 찾았고 버그를 발견했다. 수정한다
   --> Edit("src/utils.ts", "return price * count",
            "return price * count * (1 - discount)")

3. 테스트로 확인한다
   --> Bash("npm test")
```

이 흐름이 바로 여러분이 매일 Claude Code에서 경험하는 것입니다.

## 3. 에이전트 루프 (The Agent Loop)

### 3.1 관찰 -> 사고 -> 행동 -> 반복

에이전트의 핵심은 **루프(Loop)** 입니다. 한 번의 도구 호출로 끝나는 것이 아니라,
결과를 관찰하고, 다시 생각하고, 다시 행동하는 과정을 목표 달성까지 반복합니다.

```
    +-------------------------------------------------------+
    |              에이전트 루프 (Agent Loop)                  |
    +-------------------------------------------------------+
    |       [ 사용자: 목표 설정 ]                              |
    |               |                                         |
    |               v                                         |
    |  +---> [ 관찰 Observe ]  파일, 에러, 터미널 출력 확인    |
    |  |            |                                         |
    |  |            v                                         |
    |  |     [ 사고 Think ]  다음 행동 결정                    |
    |  |            |                                         |
    |  |            v                                         |
    |  |     [ 행동 Act ]  도구 호출로 환경 변경                |
    |  |            |                                         |
    |  |            v                                         |
    |  |     { 목표 달성? }---예---> [ 완료: 결과 보고 ]       |
    |  |            |                                         |
    |  +--아니오----+                                          |
    +-------------------------------------------------------+
```

### 3.2 개발자를 위한 비유: REPL과의 비교

```
REPL (Read-Eval-Print Loop)          Agent Loop
================================     ================================
Read   : 사용자 입력을 읽는다        Observe : 환경 상태를 관찰한다
Eval   : 코드를 실행한다             Think   : 다음 행동을 추론한다
Print  : 결과를 출력한다             Act     : 도구를 실행한다
Loop   : 반복한다                    Repeat  : 목표까지 반복한다
```

결정적 차이: REPL에서는 **사람이** 매번 입력을 제공하지만, 에이전트 루프에서는
**LLM이 스스로** 다음 입력을 결정합니다. 에이전트는 자율적인 REPL입니다.

### 3.3 Claude Code에서 실제로 일어나는 일

"이 프로젝트에 ESLint를 설정해줘"라고 요청하면:

```
[루프 1] 관찰: 프로젝트 구조를 모른다
         행동: Read("package.json") --> React + TypeScript 확인

[루프 2] 사고: ESLint와 플러그인을 설치하자
         행동: Bash("npm install -D eslint @typescript-eslint/parser ...")

[루프 3] 사고: 설정 파일을 생성하자
         행동: Write(".eslintrc.json", { ... })

[루프 4] 사고: package.json에 lint 스크립트 추가
         행동: Edit("package.json", ...)

[루프 5] 사고: 동작 확인
         행동: Bash("npm run lint") --> 정상 실행 확인, 완료 보고
```

5번의 루프가 자동으로 돌면서, 일일이 지시하지 않아도 다음 단계를 판단하고
실행합니다. 이것이 에이전트의 힘입니다.

## 4. 계획 수립 (Planning)

### 4.1 복잡한 작업의 분해

"UserService 모듈을 리팩터링해줘"는 단순한 한 단계 작업이 아닙니다. 에이전트는
이를 실행 가능한 하위 작업으로 **분해(Decompose)** 합니다.

```
에이전트의 내부 계획:
+---------------------------------------------------------------+
| 1단계: 현재 코드 분석                                           |
|   - UserService.ts 읽기, 의존 관계 파악, 테스트 파일 확인        |
| 2단계: 문제점 식별                                               |
|   - God class 패턴, 인증/프로필 로직 혼재                        |
| 3단계: 리팩터링 실행                                             |
|   - AuthService.ts 분리, ProfileService.ts 분리                  |
|   - UserService.ts를 Facade 패턴으로 변경                        |
| 4단계: 검증                                                      |
|   - 기존 테스트 실행, import 경로 업데이트, 빌드 확인             |
+---------------------------------------------------------------+
```

### 4.2 계획 수립의 두 가지 방식

**사전 계획 (Plan-then-Execute):** 전체 계획을 먼저 세우고 순차 실행합니다.
명확한 작업에 적합합니다.

**적응형 계획 (Adaptive Planning):** 한 단계를 실행한 후 결과를 보고 다음 계획을
조정합니다. Claude Code는 주로 이 방식을 사용합니다. 테스트가 실패하면 계획을
수정하고, 예상치 못한 의존성을 발견하면 접근 방식을 바꿉니다.

여러분이 Claude Code에서 "먼저 코드를 살펴보겠습니다"라는 메시지를 자주 보셨을
것입니다. 이것이 적응형 계획의 첫 단계 -- 환경을 관찰한 후 구체적인 실행
계획을 세우는 과정입니다.

## 5. 메모리 관리 (Memory Management)

### 5.1 에이전트의 세 가지 메모리

```
+---------------------------------------------------------------+
|                    에이전트 메모리 체계                          |
+---------------------------------------------------------------+
|  [ 단기 메모리 (Short-term Memory) ]                            |
|    = 대화 컨텍스트. 현재 세션의 메시지와 도구 호출 결과           |
|    Claude Code의 현재 세션에 해당                                |
|    제한: 컨텍스트 윈도우 크기 (예: 200K 토큰)                    |
|                                                                 |
|  [ 장기 메모리 (Long-term Memory) ]                             |
|    = 세션 간 유지되는 정보. 벡터 DB에 저장된 과거 대화 요약       |
|    Claude Code의 CLAUDE.md 파일이 이 역할을 수행                 |
|                                                                 |
|  [ 작업 메모리 (Working Memory) ]                               |
|    = 스크래치패드(Scratchpad). 현재 작업 진행 상황 추적           |
|    "지금까지 3개 파일을 수정했고, 2개가 남았다"                    |
+---------------------------------------------------------------+
```

### 5.2 컨텍스트 윈도우의 한계와 대응

LLM의 컨텍스트 윈도우는 크지만 무한하지 않습니다. 이를 해결하는 전략들:

**요약 (Summarization):** 오래된 대화를 LLM이 요약하여 압축합니다.

**벡터 저장소 (Vector Storage):** 과거 대화나 문서를 임베딩(Embedding)으로 변환하여
벡터 DB에 저장하고, 필요할 때 의미적으로 유사한 정보를 검색합니다.
이것이 RAG(Retrieval-Augmented Generation)의 핵심이기도 합니다.

**스크래치패드 패턴 (Scratchpad Pattern):** 에이전트가 중간 결과나 작업 상태를
명시적으로 기록합니다. 개발자의 TODO 리스트와 같은 역할입니다.

### 5.3 Claude Code에서의 메모리

- **세션 내 기억:** 수정한 파일, 실행한 명령의 결과를 현재 대화에서 기억합니다
- **CLAUDE.md:** 프로젝트별 지침과 규칙을 담아 장기 메모리 역할을 합니다
- **파일 시스템:** 에이전트가 파일을 읽어 정보를 얻으므로, 코드베이스 자체가
  일종의 외부 메모리입니다

## 6. 멀티 에이전트 시스템 (Multi-Agent Systems)

### 6.1 오케스트레이터-워커 패턴 (Orchestrator-Worker)

작업이 복잡해지면 **역할 분담**이 효율적입니다. 하나의 오케스트레이터가 작업을
분배하고, 워커 에이전트가 각자의 작업을 수행합니다.

```
               [ 오케스트레이터 에이전트 ]
               /          |          \
              v           v           v
    [ 워커 A ]     [ 워커 B ]     [ 워커 C ]
    "프론트엔드    "백엔드 API    "DB 스키마
     UI 수정"       구현"         설계"
              \          |          /
               --> [ 결과 통합 ] <--
```

### 6.2 토론/논쟁 패턴 (Debate/Discussion)

여러 에이전트가 같은 문제에 대해 다른 관점에서 토론합니다. 예를 들어
"마이크로서비스 도입 vs 모놀리스 유지"를 두 에이전트가 각각 대변하며
논쟁하고, 판정 에이전트가 최종 결론을 도출합니다.

### 6.3 멀티 에이전트의 현실적 도전

- **비용:** 에이전트마다 LLM API를 호출하므로 비용이 배수로 증가합니다
- **조율 복잡성:** 에이전트 간 메시지 전달과 상태 동기화가 까다롭습니다
- **디버깅 난이도:** 어떤 에이전트가 잘못된 판단을 했는지 추적하기 어렵습니다

## 7. 에이전트 프레임워크 (Agent Frameworks)

### 7.1 주요 프레임워크 비교

**LangChain** -- 가장 널리 알려진 LLM 프레임워크. 도구, 메모리, 체인(Chain) 추상화 제공.

```python
from langchain.agents import create_tool_calling_agent
from langchain_anthropic import ChatAnthropic

tools = [file_read_tool, file_write_tool, bash_tool]
llm = ChatAnthropic(model="claude-sonnet-4-20250514")
agent = create_tool_calling_agent(llm, tools, prompt)
```

**LangGraph** -- LangChain 팀의 상태 기반 워크플로우 프레임워크. 에이전트 행동을
그래프(Graph)로 정의하여 복잡한 워크플로우를 설계합니다.

**CrewAI** -- 역할 기반 멀티 에이전트 프레임워크. 각 에이전트에게 역할과 목표를 부여.

```python
from crewai import Agent, Task, Crew

reviewer = Agent(role="코드 리뷰어", goal="코드 품질 개선점 제안")
tester = Agent(role="테스트 작성자", goal="누락된 테스트 케이스 작성")
crew = Crew(agents=[reviewer, tester], tasks=[...])
```

**AutoGen** (Microsoft) -- 에이전트 간 대화를 통해 작업을 수행하는 패턴에 특화.

**Semantic Kernel** (Microsoft) -- 기존 앱에 AI 기능 통합. C#/Python 지원.

### 7.2 프레임워크 선택 가이드

```
+--------------------------------------------------------------+
| 사용 사례                   | 추천 프레임워크                  |
|-----------------------------|--------------------------------|
| 단일 에이전트, 빠른 프로토타입 | LangChain                     |
| 복잡한 워크플로우, 상태 관리  | LangGraph                      |
| 역할 기반 멀티 에이전트      | CrewAI                          |
| 에이전트 간 대화 중심        | AutoGen                         |
| 엔터프라이즈 통합            | Semantic Kernel                 |
+--------------------------------------------------------------+
```

## 8. Claude Code와 Kilo Code는 왜 에이전트인가

여러분이 매일 사용하는 Claude Code와 Kilo Code는 단순한 챗봇이 아닙니다.
이 장에서 다룬 모든 에이전트 개념이 적용된 **완전한 AI 에이전트**입니다.

```
+--------------------------------------------------------------+
|  [ 사용자 ] --요청--> [ 에이전트 런타임 ]                      |
|                            |                                   |
|                     [ Claude (LLM) ]                           |
|                            |                                   |
|                     도구 호출 결정                               |
|                    /   |    |   \                               |
|               [Read] [Edit] [Bash] [Grep]                      |
|               [Write] [Glob] [WebFetch]                        |
|                    \   |    |    /                              |
|                  결과 반환 --> 다음 행동 또는 완료               |
+--------------------------------------------------------------+
```

### 8.2 Claude Code가 사용하는 도구들

| 도구 | 역할 | 에이전트 관점 |
|------|------|--------------|
| **Read** | 파일 내용 읽기 | 환경 관찰 (Observe) |
| **Glob / Grep** | 파일/내용 검색 | 정보 수집 (Gather) |
| **Edit** | 파일 내용 수정 | 환경 변경 (Act) |
| **Write** | 새 파일 생성 | 환경 변경 (Act) |
| **Bash** | 터미널 명령 실행 | 변경 + 관찰 (Act + Observe) |

"파일을 읽겠습니다" -> Read, "검색하겠습니다" -> Grep, "수정하겠습니다" -> Edit,
"테스트를 실행하겠습니다" -> Bash. 이 도구 호출이 에이전트 루프 안에서 반복됩니다.

### 8.3 Kilo Code도 같은 원리

Kilo Code도 동일한 에이전트 패턴을 따릅니다. VS Code 확장으로 동작하며,
에디터의 파일 시스템과 터미널에 접근하는 도구들을 LLM에게 제공합니다.
요청을 받으면 에이전트 루프를 돌며 코드를 읽고, 분석하고, 수정합니다.

핵심 공식: **LLM + 도구 + 루프 = 에이전트**

## 9. 안전과 통제 (Safety and Control)

### 9.1 에이전트에게 권한을 주는 것의 위험

에이전트는 파일을 수정하고 명령을 실행합니다. 잘못된 판단 한 번이 프로덕션
데이터베이스를 삭제하거나, 민감한 정보를 외부에 전송할 수 있습니다.

### 9.2 휴먼 인 더 루프 (Human-in-the-Loop)

가장 기본적인 안전 장치는 **중요한 행동 전에 사람의 승인을 요구하는 것**입니다.

```
에이전트: "다음 명령을 실행하려고 합니다:"
         rm -rf build/ && npm run build
         [승인] [거부]
사용자:  [승인]
에이전트: (명령 실행)
```

Claude Code에서 파일 수정이나 명령 실행 전에 확인을 요청하는 것이 바로 이
패턴입니다. "y"를 누르거나 승인해야 에이전트가 행동합니다.

### 9.3 샌드박싱 (Sandboxing)

에이전트의 행동 범위를 제한하는 방법입니다.

- **파일 시스템 제한:** 프로젝트 디렉토리 밖의 파일에 접근 차단
- **네트워크 제한:** 외부 요청을 차단하거나 허용 목록으로 관리
- **명령 제한:** 실행 가능한 셸 명령의 종류를 제한
- **리소스 제한:** CPU, 메모리, 실행 시간에 상한 설정

### 9.4 권한 수준 설계

```
+--------------------------------------------------------------+
| 위험도 | 행동 예시              | 필요한 통제                   |
|--------|----------------------|-------------------------------|
| 낮음   | 파일 읽기, 검색       | 자동 승인                      |
| 중간   | 파일 수정, 패키지 설치 | 사용자 확인 후 실행             |
| 높음   | 시스템 명령, 네트워크  | 명시적 승인 + 샌드박싱          |
| 최고   | 프로덕션 배포, 삭제    | 다중 승인 + 감사 로그           |
+--------------------------------------------------------------+
```

## 10. 실전 정리: 에이전트를 이해하면 도구를 더 잘 쓸 수 있다

**에이전트 루프를 이해하면** -- Claude Code가 여러 번의 루프를 돌며 문제를
해결한다는 것을 알 수 있습니다. 첫 시도에서 실패해도 결과를 관찰하고 다른
접근법을 시도합니다.

**도구 사용을 이해하면** -- 에이전트에게 더 효과적으로 지시할 수 있습니다.
"src 폴더의 모든 TypeScript 파일에서 deprecated API를 찾아줘"라고 구체적으로
말하면, Grep 도구를 효율적으로 활용합니다.

**메모리 한계를 이해하면** -- 긴 대화 끝에 초반 내용을 "잊어버리는" 이유를 알 수
있습니다. CLAUDE.md에 프로젝트 규칙을 적어두면 매 세션마다 장기 메모리가 작동합니다.

**계획 수립을 이해하면** -- 복잡한 작업은 단계별로 나누어 요청하거나, 중간 결과를
확인하며 방향을 조정하는 것이 효과적입니다.
