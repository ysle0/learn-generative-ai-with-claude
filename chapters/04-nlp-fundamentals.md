# Chapter 04: 자연어처리 (NLP) 기초

> **"컴퓨터는 글자를 모릅니다. 오직 숫자만 압니다."**

> | **Attention** | 입력의 각 부분에 서로 다른 가중치를 부여하는 메커니즘 |
> | **Encoder-Decoder** | 입력을 압축하고 출력을 생성하는 구조 |

## 4.1 컴퓨터는 텍스트를 어떻게 이해할까 - 결국 전부 숫자입니다

여러분이 ChatGPT에 "오늘 날씨 어때?"라고 입력하면, 컴퓨터 내부에서는 어떤 일이 벌어질까요? 정답부터 말하면: **글자는 즉시 숫자로 변환됩니다.** CPU와 GPU는 덧셈, 곱셈, 행렬 연산만 할 수 있고, "사과"라는 단어를 직접 처리할 방법이 없습니다. 그래서 NLP(Natural Language Processing)의 첫 번째 과제는 항상 같습니다:

> **"어떻게 하면 텍스트를 숫자로 잘 바꿀 수 있을까?"**

이 질문에 대한 답이 바로 **토큰화(Tokenization)** 와 **임베딩(Embedding)** 입니다.

```
텍스트 처리 파이프라인 (간략화)

  "오늘 날씨 어때?"
        |
  [ 토큰화 Tokenization ]  -->  [49592, 234, 8834, ...]   숫자 ID
        |
  [ 임베딩 Embedding ]     -->  [[0.12, -0.34, 0.78, ...],  벡터
                                 [0.56,  0.11, -0.23, ...]]
```

## 4.2 토큰화 (Tokenization): 텍스트를 조각내는 기술

### 왜 토큰화가 필요한가

모델에 문장을 넣으려면 먼저 일정한 단위로 쪼개야 합니다. 가장 단순한 방법은 공백 기준으로 나누는 것입니다:

```
입력: "I love natural language processing"
결과: ["I", "love", "natural", "language", "processing"]
```

하지만 문제가 있습니다:

1. **한국어**는 공백만으로 분리가 어렵습니다 ("자연어처리" = 자연어 + 처리)
2. **어휘 폭발**: 모든 단어를 사전에 넣으면 수십만 개가 됩니다
3. **미등록어(OOV)**: "ChatGPT"처럼 사전에 없는 단어를 처리할 수 없습니다

이 문제를 해결하기 위해 **서브워드 토큰화(Subword Tokenization)** 가 등장했습니다.

### BPE (Byte Pair Encoding)

**BPE**는 GPT, Claude, LLaMA 등 대부분의 LLM이 사용하는 토큰화 알고리즘입니다. 핵심 아이디어는 단순합니다: **"자주 함께 등장하는 문자 쌍을 반복적으로 병합한다."**

```
[BPE 학습 과정]

훈련 데이터: "low lower lowest"

Step 0: 개별 문자로 시작
  l, o, w, e, r, s, t  (기본 어휘)

Step 1: (l, o) = 3번 출현 -> 병합 -> "lo" 추가
Step 2: (lo, w) = 3번 출현 -> 병합 -> "low" 추가
Step 3: (low, e) = 2번 출현 -> 병합 -> "lowe" 추가
... (원하는 어휘 크기까지 반복)
```

실제로 "Hello world"를 GPT 계열 토크나이저에 넣으면:

```
입력: "Hello world"
토큰: ["Hello", " world"]
ID:   [15496, 995]        <-- 단 2개의 숫자!
```

한국어는 더 잘게 쪼개집니다:

```
입력: "안녕하세요 세계"
토큰: ["안녕", "하", "세요", " 세계"]
ID:   [31495, 168, 233, 44980, 29119]
```

이것이 **한국어로 질문하면 토큰을 더 많이 소모하는 이유**입니다. API 비용이 토큰 수에 비례하므로, 같은 의미라도 한국어가 더 비쌀 수 있습니다.

### WordPiece

**WordPiece**는 Google의 BERT에서 사용하는 방식입니다. BPE와 유사하지만, 병합 기준이 **빈도** 대신 **훈련 데이터의 우도(likelihood)를 가장 크게 높이는 쌍**입니다.

```
입력:  "unbelievable"
결과:  ["un", "##believ", "##able"]
       ("##"은 이전 토큰에 이어지는 부분이라는 표시)
```

### SentencePiece

**SentencePiece**는 언어에 독립적인(language-agnostic) 토큰화 라이브러리입니다. 공백도 하나의 문자로 처리하므로 어떤 언어든 동일하게 다룹니다. T5, LLaMA 등에서 사용합니다.

```
입력:  "자연어 처리는 재미있다"
결과:  ["▁자연", "어", "▁처리", "는", "▁재미", "있다"]
       ("▁"은 공백 위치를 표시)
```

### 토큰화 방식 비교

```
              BPE             WordPiece        SentencePiece
사용 모델     GPT, Claude     BERT             T5, LLaMA, ALBERT
병합 기준     빈도 기반       우도 기반         빈도/우도 선택 가능
공백 처리     별도 처리       별도 처리         통합 처리
한국어        보통            보통              높은 친화도
```

## 4.3 임베딩 (Embedding): 단어를 벡터로 바꾸기

토큰화로 텍스트를 숫자 ID로 변환했습니다. 하지만 단순한 ID만으로는 단어 사이의 **의미적 관계**를 표현할 수 없습니다. "고양이"가 ID 3847이고 "강아지"가 ID 9102여도, 이 숫자 사이에 "둘 다 반려동물"이라는 정보는 없습니다.

> **임베딩(Embedding)은 단어를 의미를 담은 고차원 벡터(숫자 배열)로 변환하는 것입니다.**

### Word2Vec - "비슷한 맥락의 단어는 비슷한 벡터를 갖는다"

2013년 Google의 Tomas Mikolov가 발표한 **Word2Vec**은 임베딩 분야의 혁명이었습니다. 핵심 아이디어는 이렇습니다:

> **"한 단어의 의미는, 그 단어가 어떤 단어들과 함께 쓰이는지로 결정된다."**
> (You shall know a word by the company it keeps. - J.R. Firth, 1957)

Word2Vec에는 두 가지 학습 방식이 있습니다:

```
[CBOW] 주변 단어 -> 중심 단어 예측
  "나는 ____ 에서 커피를 마셨다"  -->  "카페" 예측

[Skip-gram] 중심 단어 -> 주변 단어 예측
  "카페"  -->  "나는", "에서", "커피를", "마셨다" 예측
```

### "King - Man + Woman = Queen" 예제

Word2Vec이 세상을 놀라게 한 실험입니다:

```
vector("King") - vector("Man") + vector("Woman") ≈ vector("Queen")
```

이것을 벡터 공간에서 시각화하면:

```
  (성별 축)
    ^
    |   Queen -------> King
    |     ^              ^
    |     |   같은       |
    |     |   방향!      |
    |   Woman -------> Man
    |
    +-------------------------> (왕족/평민 축)

  "King - Man"의 벡터 = "Queen - Woman"의 벡터
  즉, "남성->여성" 변환이 벡터 공간에서 동일한 방향으로 인코딩됩니다.
```

"King"과 "Queen"은 비슷한 맥락(왕관, 왕좌, 통치)에 등장하고, "King"은 "he"와, "Queen"은 "she"와 함께 등장하는 차이가 벡터의 성별 방향으로 학습됩니다.

다른 관계도 벡터 연산으로 표현됩니다:

```
Paris - France + Japan      ≈ Tokyo      (수도 관계)
walked - walking + swimming ≈ swam       (시제 관계)
서울 - 한국 + 일본           ≈ 도쿄       (한국어도 가능!)
```

### GloVe - 전역 통계를 활용한 임베딩

**GloVe(Global Vectors)** 는 2014년 Stanford에서 발표한 방법입니다. Word2Vec이 로컬 문맥(주변 단어)만 보는 반면, GloVe는 **전체 말뭉치의 동시출현 행렬(co-occurrence matrix)** 을 활용합니다.

```
동시출현 행렬 (간략화):
            ice    steam    water    fashion
  solid      8       0        2        0
  gas        0       7        3        0
  water      2       3        0        1

-> "ice"와 "solid", "steam"과 "gas"가 자주 함께 등장
-> 이 전역 통계를 벡터로 압축하면 임베딩이 됩니다
```

### 임베딩 벡터의 실제 모습

```
"고양이" = [0.21, -0.45, 0.78, 0.12, -0.33, ...]  (300차원)
"강아지" = [0.19, -0.41, 0.72, 0.15, -0.29, ...]  (300차원)
"자동차" = [0.82,  0.15, -0.34, 0.67, 0.44, ...]  (300차원)

코사인 유사도:
  similarity("고양이", "강아지") = 0.92  (매우 유사!)
  similarity("고양이", "자동차") = 0.15  (관련 없음)
```

2차원으로 축소해서 시각화하면:

```
             (의미 공간의 2D 투영)

    고양이 *  * 강아지
              * 햄스터                   * 비행기
    토끼 *                          * 자동차
                                  * 버스
    사과 *
         * 바나나                       * 컴퓨터
    포도 *                         * 스마트폰

  -> 의미가 비슷한 단어들이 벡터 공간에서 가까이 모입니다!
```

## 4.4 전통적 텍스트 표현: Bag of Words와 TF-IDF

임베딩 이전에는 어떻게 텍스트를 숫자로 바꿨을까요?

### Bag of Words (BoW)

가장 단순한 방법입니다. 단어의 **출현 빈도**만 세고, 순서는 무시합니다.

```
문장 1: "나는 고양이를 좋아한다"     -> [1, 1, 1, 0, 0, 0]
문장 2: "나는 강아지를 좋아한다"     -> [1, 0, 1, 1, 0, 0]
문장 3: "고양이는 강아지를 싫어한다" -> [0, 0, 0, 1, 1, 1]
       어휘: [나는, 고양이를, 좋아한다, 강아지를, 고양이는, 싫어한다]
```

문제점: "나는 고양이를 좋아한다"와 "고양이를 나는 좋아한다"가 동일한 벡터가 되고, 단어의 의미적 관계를 전혀 파악할 수 없으며, 어휘가 커지면 대부분 0인 희소 벡터(sparse vector)가 됩니다.

### TF-IDF (Term Frequency - Inverse Document Frequency)

BoW를 개선한 방법입니다. **모든 문서에 나타나는 흔한 단어는 덜 중요하고, 특정 문서에만 나타나는 단어가 더 중요하다**는 아이디어입니다.

```
TF-IDF = TF(단어 빈도) x IDF(역문서 빈도)
IDF(t) = log(전체 문서 수 / 단어 t가 등장한 문서 수)

예시 (문서 3개):
  문서1: "파이썬 프로그래밍 기초"
  문서2: "파이썬 머신러닝 실전"
  문서3: "자바 프로그래밍 기초"

  "파이썬":  IDF = log(3/2) = 0.41  (2개 문서에 등장)
  "머신러닝": IDF = log(3/1) = 1.10  (1개 문서에만 -> 더 중요!)
  "기초":    IDF = log(3/2) = 0.41  (2개 문서에 등장 -> 덜 특별)
```

TF-IDF는 검색 엔진에서 오랫동안 핵심 알고리즘이었고, 지금도 키워드 추출에 활용됩니다.

### 전통적 방법의 한계

```
전통적 방법 (BoW, TF-IDF)     현대적 방법 (Embedding)
------------------------------------------------------
단어 순서 무시                 순서 정보 보존
의미 관계 파악 불가            유사 단어 인식 가능
고정된 표현                    문맥에 따라 달라지는 표현
희소 벡터 (대부분 0)           밀집 벡터 (정보 압축)
```

## 4.5 Seq2Seq와 Encoder-Decoder 구조

기계 번역처럼 입력과 출력의 길이가 다른 문제가 있습니다:

```
입력: "나는 학생입니다"  (3 토큰)  ->  출력: "I am a student"  (4 토큰)
```

이 문제를 해결하는 것이 **Seq2Seq(Sequence-to-Sequence)** 모델입니다.

### Encoder-Decoder 구조

```
  입력: "나는 학생입니다"

  ┌──────── Encoder ────────┐
  │ "나는"   -> [RNN] -> h1 │
  │ "학생"   -> [RNN] -> h2 │
  │ "입니다" -> [RNN] -> h3 │
  └────────────|────────────┘
         Context Vector
    (입력 전체를 하나의 벡터로 압축)
               |
  ┌────────────|────────────┐
  │ [RNN] + Context -> "I"       │
  │ [RNN] + "I"    -> "am"      │
  │ [RNN] + "am"   -> "a"       │
  │ [RNN] + "a"    -> "student" │
  │ [RNN] + "student" -> [END]  │
  └──────── Decoder ────────┘

  출력: "I am a student"
```

**인코더(Encoder)** 는 입력 문장을 **문맥 벡터(Context Vector)** 하나로 압축하고, **디코더(Decoder)** 는 이 벡터를 받아 한 단어씩 출력을 생성합니다.

### 병목 현상

여기서 심각한 문제가 발생합니다. **긴 문장의 모든 정보를 고정 길이 벡터 하나에 담는 것은 무리입니다.**

```
짧은 문장: "감사합니다" -> [0.2, 0.8, -0.1, ...]  (OK!)
긴 문장:   "어제 서울역 근처 카페에서 오랜만에 만난 친구와
            아이스 아메리카노를 마시며 인공지능에 대해 대화했다"
            -> [0.5, 0.3, -0.4, ...]  (같은 크기 벡터에? 정보 손실!)
```

문장이 길수록 번역 품질이 급격히 떨어졌습니다. 이 문제를 해결한 것이 **어텐션(Attention)** 입니다.

## 4.6 Attention 메커니즘의 탄생 - "모든 것을 똑같이 볼 필요는 없다"

2014년 Bahdanau 등은 획기적인 아이디어를 제안했습니다:

> **"디코더가 출력 단어를 생성할 때, 인코더의 모든 위치를 직접 참조하되,**
> **관련 있는 부분에 더 높은 가중치를 부여하자."**

```
[Attention 시각화]

인코더 출력:  h1("나는")   h2("학생")   h3("입니다")

"I" 생성 시:        [0.85]     [0.10]     [0.05]   <- "나는"에 집중!
"student" 생성 시:  [0.05]     [0.90]     [0.05]   <- "학생"에 집중!
```

기존 Seq2Seq는 항상 같은 문맥 벡터 하나만 참조했지만, Attention이 있으면 매 출력마다 입력의 다른 부분에 선택적으로 집중합니다:

```
[기존 Seq2Seq]
인코더 -> [단일 문맥 벡터] -> 디코더 (항상 같은 벡터만 참조)

[Attention Seq2Seq]
인코더:  "나는"   "학생"   "입니다"
           \       |       /       <- 매번 다른 가중치로 참조
디코더:  "I"     "am"    "a"     "student"
```

### Attention 가중치 계산

```
1. Query(디코더 현재 상태)와 Key(인코더 각 위치)의 유사도를 계산
2. softmax로 확률 변환
3. 확률을 가중치로 Value(인코더 각 위치 값)를 가중합

   Score  = similarity(Query, Key_i)
   Weight = softmax(Scores)
   Output = sum(Weight_i * Value_i)
```

이 Query, Key, Value 개념은 이후 **Transformer**의 **Self-Attention**으로 발전합니다.

### Attention이 혁명적인 이유

1. **정보 병목 해소** - 긴 문장도 정보 손실 없이 처리
2. **해석 가능성** - 모델이 "어디를 보는지" 시각화 가능
3. **성능 향상** - 특히 긴 문장 번역에서 극적 개선
4. **Transformer의 기반** - 2017년 "Attention is All You Need"의 직접적 영감

## 4.7 단어에서 서브워드로 - 현대 LLM이 BPE를 선택한 이유

초기 NLP 모델은 단어 단위로 토큰화했지만 심각한 문제가 있었습니다:

```
[단어 수준]  어휘 50만+, "ChatGPT" -> [UNK], "play/plays/played" 관계 단절
[문자 수준]  어휘 작지만, 시퀀스가 너무 김 -> 계산 비용 폭발
[서브워드]   최적의 균형점!

문자 수준  <---------|---------->  단어 수준
                     ^
                서브워드 수준
                (BPE, WordPiece)

"the"       -> ["the"]                     (자주 쓰는 단어: 유지)
"unhappily" -> ["un", "happi", "ly"]       (드문 단어: 분할)
"ChatGPT"   -> ["Chat", "G", "PT"]        (미등록어: 처리 가능!)
```

### 현대 LLM들의 토큰화 전략

```
모델             방식            어휘 크기
-----------------------------------------------
GPT-4            BPE             ~100,000
Claude           BPE (추정)      ~100,000
BERT             WordPiece       30,522
T5               SentencePiece   32,000
LLaMA 2          BPE             32,000
Gemini           SentencePiece   256,000
```

BPE가 선택받는 이유: (1) 구현이 단순, (2) 미등록어 없음, (3) 어휘 크기 자유 조절, (4) 다국어 처리에 유리.

## 4.8 이 기초가 LLM 이해에 왜 중요한가

```
[NLP 기초 -> LLM 연결 지도]

토큰화 (BPE)
  └─> API 비용이 토큰 수에 비례하는 이유
      한국어가 영어보다 토큰을 많이 쓰는 이유
      최대 컨텍스트 길이가 토큰 단위인 이유

임베딩
  └─> LLM의 첫 번째 레이어에서 토큰이 벡터로 변환
      RAG에서 유사도 검색이 가능한 이유
      의미 검색(Semantic Search)의 원리

Seq2Seq / Encoder-Decoder
  └─> GPT = Decoder-only, BERT = Encoder-only, T5 = 둘 다 사용

Attention
  └─> Self-Attention으로 발전 -> Transformer의 핵심
      LLM이 긴 문맥을 처리할 수 있는 이유
```

## 4.9 핵심 요약

1. **컴퓨터는 텍스트를 직접 처리할 수 없다** - 반드시 숫자로 변환해야 합니다.
2. **토큰화(Tokenization)** 는 텍스트를 조각으로 나눕니다. BPE(GPT, Claude), WordPiece(BERT), SentencePiece(T5, LLaMA)가 대표적입니다.
3. **임베딩(Embedding)** 은 단어를 의미 벡터로 변환합니다. Word2Vec과 GloVe 덕분에 "King - Man + Woman = Queen" 같은 벡터 연산이 가능해졌습니다.
4. **전통적 방법(BoW, TF-IDF)** 은 단어 순서를 무시하는 한계가 있었습니다.
5. **Seq2Seq와 Encoder-Decoder** 는 가변 길이 입출력 문제를 해결했지만, 긴 문장에서 정보 병목이 발생했습니다.
6. **Attention** 은 "중요한 부분에 집중"하는 능력으로 병목을 해소했고, Transformer와 현대 LLM의 직접적 기반이 되었습니다.
7. **서브워드 토큰화(BPE)** 는 어휘 크기와 표현력의 최적 균형을 제공합니다.
