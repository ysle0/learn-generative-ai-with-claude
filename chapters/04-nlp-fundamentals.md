## 4.1 컴퓨터는 텍스트를 어떻게 이해할까 - 결국 전부 숫자입니다

여러분이 ChatGPT에 "오늘 날씨 어때?"라고 입력하면, 컴퓨터 내부에서는
어떤 일이 벌어질까요?

정답부터 말하면: **글자는 즉시 숫자로 변환됩니다.**

컴퓨터의 CPU와 GPU는 덧셈, 곱셈, 행렬 연산만 할 수 있습니다.
"사과"라는 단어를 직접 처리할 방법이 없습니다.
그래서 자연어처리(Natural Language Processing, NLP)의 첫 번째 과제는
항상 같습니다:

> **"어떻게 하면 텍스트를 숫자로 잘 바꿀 수 있을까?"**

이 질문에 대한 답이 바로 **토큰화(Tokenization)** 와 **임베딩(Embedding)** 입니다.
이번 장에서는 이 두 가지를 중심으로, LLM을 이해하기 위한
NLP의 핵심 기초 개념들을 살펴보겠습니다.

```
텍스트 처리 파이프라인 (간략화)

  "오늘 날씨 어때?"
        |
        v
  [ 토큰화 (Tokenization) ]     <-- 텍스트를 조각으로 나눈다
        |
        v
  [49592, 234, 8834, 102, ...]  <-- 각 조각에 숫자 ID를 부여한다
        |
        v
  [ 임베딩 (Embedding) ]        <-- 숫자 ID를 벡터로 변환한다
        |
        v
  [[0.12, -0.34, 0.78, ...],    <-- 모델이 처리할 수 있는 형태
   [0.56,  0.11, -0.23, ...],
   ...]
```

## 4.2 토큰화 (Tokenization): 텍스트를 조각내는 기술

### 4.2.1 왜 토큰화가 필요한가

모델에 문장을 넣으려면 먼저 문장을 일정한 단위로 쪼개야 합니다.
이 "쪼개는 행위"를 **토큰화(Tokenization)** 라고 합니다.

가장 단순한 방법은 **공백 기준**으로 나누는 것입니다:

```
입력: "I love natural language processing"
결과: ["I", "love", "natural", "language", "processing"]
```

영어에서는 어느 정도 작동합니다. 하지만 문제가 있습니다:

1. **한국어**는 공백만으로 분리가 어렵습니다 ("자연어처리" = 자연어 + 처리)
2. **어휘 폭발**: 모든 단어를 사전에 넣으면 수십만 개가 됩니다
3. **미등록어(OOV)**: "ChatGPT"처럼 사전에 없는 새 단어를 처리할 수 없습니다

이 문제를 해결하기 위해 등장한 것이 **서브워드 토큰화(Subword Tokenization)** 입니다.

### 4.2.2 BPE (Byte Pair Encoding)

**BPE**는 현재 GPT 시리즈, Claude, LLaMA 등 대부분의 LLM이 사용하는
토큰화 알고리즘입니다.

핵심 아이디어는 단순합니다:

> **"자주 함께 등장하는 문자 쌍을 반복적으로 병합한다."**

BPE의 작동 과정을 단계별로 살펴보겠습니다:

```
[BPE 학습 과정 예시]

훈련 데이터: "low lower lowest"

Step 0: 개별 문자로 시작
  l, o, w, e, r, s, t  (기본 어휘)

Step 1: 가장 빈번한 문자 쌍을 찾는다
  (l, o) = 3번 출현  <-- 가장 빈번!
  (o, w) = 3번 출현
  (l, o)를 병합 -> "lo" 를 어휘에 추가

Step 2: 다음으로 빈번한 쌍을 찾는다
  (lo, w) = 3번 출현  <-- 가장 빈번!
  병합 -> "low" 를 어휘에 추가

Step 3: 계속 반복...
  (low, e) = 2번 출현
  병합 -> "lowe" 를 어휘에 추가

... (원하는 어휘 크기에 도달할 때까지 반복)
```

실제로 "Hello world"를 GPT 계열 토크나이저에 넣으면 다음과 같은 결과가 나옵니다:

```
입력: "Hello world"
토큰: ["Hello", " world"]
ID:   [15496, 995]
```

단 2개의 숫자로 변환되었습니다!

한국어의 경우는 조금 더 흥미롭습니다:

```
입력: "안녕하세요 세계"
토큰: ["안녕", "하", "세요", " 세계"]
ID:   [31495, 168, 233, 44980, 29119]

(실제 토크나이저에 따라 결과가 다를 수 있습니다)
```

한국어는 영어보다 더 잘게 쪼개지는 경향이 있습니다.
이것이 바로 **한국어로 질문하면 영어보다 토큰을 더 많이 소모하는 이유**입니다.
API 비용이 토큰 수에 비례하므로, 같은 의미라도 한국어가 더 비쌀 수 있습니다.

### 4.2.3 WordPiece

**WordPiece**는 Google의 BERT 모델에서 사용하는 토큰화 방식입니다.
BPE와 유사하지만, 병합 기준이 다릅니다:

- **BPE**: 가장 빈번한 쌍을 병합
- **WordPiece**: 병합했을 때 **훈련 데이터의 우도(likelihood)를 가장 크게 높이는** 쌍을 병합

```
WordPiece 토큰화 예시:

입력:  "unbelievable"
결과:  ["un", "##believ", "##able"]

"##" 접두사는 "이 토큰은 단어의 시작이 아니라 이전 토큰에 이어지는
부분"이라는 표시입니다.
```

### 4.2.4 SentencePiece

**SentencePiece**는 Google에서 개발한 토큰화 라이브러리로,
언어에 독립적인(language-agnostic) 방식입니다.

핵심 특징:

- 공백을 특별하게 취급하지 않습니다 (공백도 하나의 문자로 처리)
- 어떤 언어든 동일한 방식으로 처리할 수 있습니다
- T5, LLaMA 등에서 사용합니다

```
SentencePiece 토큰화 예시:

입력:  "자연어 처리는 재미있다"
결과:  ["▁자연", "어", "▁처리", "는", "▁재미", "있다"]

"▁"(밑줄)은 공백 위치를 나타냅니다.
```

### 4.2.5 토큰화 방식 비교

```
                    BPE          WordPiece      SentencePiece
사용 모델       GPT, Claude,    BERT           T5, LLaMA,
                LLaMA                          ALBERT
병합 기준       빈도 기반       우도 기반       빈도/우도 선택가능
공백 처리       별도 처리       별도 처리       통합 처리
한국어 친화도   보통            보통            높음
```

## 4.3 임베딩 (Embedding): 단어를 벡터로 바꾸기

토큰화로 텍스트를 숫자 ID로 변환했습니다. 하지만 단순한 ID 번호만으로는
단어 사이의 **의미적 관계**를 표현할 수 없습니다.

"고양이"가 ID 3847이고 "강아지"가 ID 9102라고 해서,
이 두 숫자 사이에 "둘 다 반려동물"이라는 정보가 담겨있지 않습니다.

이 문제를 해결하는 것이 **임베딩(Embedding)** 입니다.

> **임베딩이란, 단어를 의미를 담은 고차원 벡터(숫자 배열)로 변환하는 것입니다.**

### 4.3.1 Word2Vec - "비슷한 맥락의 단어는 비슷한 벡터를 갖는다"

2013년 Google의 Tomas Mikolov가 발표한 **Word2Vec**은
임베딩 분야의 혁명이었습니다.

핵심 아이디어:

> **"한 단어의 의미는, 그 단어가 어떤 단어들과 함께 쓰이는지로 결정된다."**
> (You shall know a word by the company it keeps. - J.R. Firth, 1957)

예를 들어, "커피"라는 단어는 "마시다", "카페", "아메리카노" 등과 자주 함께
등장합니다. 이 패턴을 학습하면 "커피"의 의미를 벡터로 표현할 수 있습니다.

Word2Vec의 두 가지 방식:

```
[CBOW: Continuous Bag of Words]
주변 단어들로부터 중심 단어를 예측

  "나는 ____ 에서 커피를 마셨다"
     |    |           |      |
     v    v           v      v
  [ 주변 단어 벡터들의 평균 ]
              |
              v
         "카페" (예측)


[Skip-gram]
중심 단어로부터 주변 단어들을 예측

         "카페"
           |
           v
  [ 신경망 ]
     |    |    |    |
     v    v    v    v
   "나는" "에서" "커피를" "마셨다" (예측)
```

### 4.3.2 "King - Man + Woman = Queen" 예제

Word2Vec이 세상을 놀라게 한 것은 바로 이 실험입니다:

```
벡터 연산:
  vector("King") - vector("Man") + vector("Woman") ≈ vector("Queen")
```

이것이 의미하는 바를 벡터 공간에서 시각화하면:

```
  (성별 축)
    ^
    |
    |   Queen ------>  King
    |     ^              ^
    |     |              |
    |     | Woman->Man   |
    |     |   방향       |
    |   Woman ------>  Man
    |
    +-------------------------> (왕족/평민 축)

  "King"과 "Man"의 차이 = "Queen"과 "Woman"의 차이
  즉, "남성->여성" 변환이 벡터 공간에서 동일한 방향으로 표현됩니다!
```

이런 관계가 학습되는 이유가 무엇일까요?

"King"이 등장하는 맥락과 "Queen"이 등장하는 맥락은 매우 유사합니다
(왕관, 왕좌, 통치 등). 다만 "King"은 "he"와, "Queen"은 "she"와 함께
등장하는 차이가 있습니다. 이 미묘한 차이가 벡터에 성별 방향으로 인코딩됩니다.

실제로 다양한 관계가 벡터 연산으로 표현됩니다:

```
Paris - France + Japan     ≈ Tokyo      (수도 관계)
walked - walking + swimming ≈ swam       (시제 관계)
서울 - 한국 + 일본          ≈ 도쿄       (수도 관계, 한국어)
```

### 4.3.3 GloVe - 전역 통계를 활용한 임베딩

**GloVe(Global Vectors for Word Representation)** 는
2014년 Stanford에서 발표한 임베딩 방법입니다.

Word2Vec이 **로컬 문맥**(주변 단어)만 보는 반면,
GloVe는 **전체 말뭉치의 동시출현 행렬(co-occurrence matrix)** 을 활용합니다.

```
동시출현 행렬 (간략화):

            ice    steam    water   fashion
  solid      8       0        2       0
  gas        0       7        3       0
  water      2       3        0       1
  style      0       0        1       9

-> "ice"와 "solid"는 자주 함께 등장 (높은 값)
-> "steam"과 "gas"는 자주 함께 등장 (높은 값)
-> 이 통계를 벡터로 압축하면 임베딩이 됩니다
```

Word2Vec과 GloVe의 차이:

```
              Word2Vec              GloVe
학습 방식     예측 기반             통계 기반
              (주변 단어 예측)      (동시출현 행렬 분해)
문맥 범위     로컬 윈도우           전체 말뭉치
장점          빠른 학습             안정적인 성능
```

### 4.3.4 임베딩 벡터의 실제 모습

실제 Word2Vec이나 GloVe에서 만들어진 벡터는 이런 모습입니다:

```
"고양이" = [0.21, -0.45, 0.78, 0.12, -0.33, 0.56, ...]  (300차원)
"강아지" = [0.19, -0.41, 0.72, 0.15, -0.29, 0.61, ...]  (300차원)
"자동차" = [0.82, 0.15, -0.34, 0.67, 0.44, -0.12, ...]  (300차원)

코사인 유사도:
  similarity("고양이", "강아지") = 0.92  (매우 유사!)
  similarity("고양이", "자동차") = 0.15  (관련 없음)
```

이 벡터들을 2차원으로 축소해서 시각화하면:

```
                    (의미 공간의 2D 투영)

         고양이 *  * 강아지
                  * 햄스터
     토끼 *

                                    * 비행기
                              * 자동차
                         * 버스
                    * 기차

     사과 *
          * 바나나                     * 컴퓨터
     포도 *                       * 스마트폰

  -> 의미가 비슷한 단어들이 가까운 위치에 모여있습니다!
```

## 4.4 전통적 텍스트 표현 방법: Bag of Words와 TF-IDF

임베딩 이전에는 어떻게 텍스트를 숫자로 바꿨을까요?
전통적인 방법들도 알아두면 LLM의 발전 과정을 이해하는 데 도움이 됩니다.

### 4.4.1 Bag of Words (BoW)

가장 단순한 방법입니다. 문장에 등장하는 단어의 **빈도**만 세는 것입니다.
단어의 순서는 완전히 무시합니다.

```
문장 1: "나는 고양이를 좋아한다"
문장 2: "나는 강아지를 좋아한다"
문장 3: "고양이는 강아지를 싫어한다"

어휘 사전: [나는, 고양이를, 좋아한다, 강아지를, 고양이는, 싫어한다]

BoW 벡터:
문장 1: [1, 1, 1, 0, 0, 0]
문장 2: [1, 0, 1, 1, 0, 0]
문장 3: [0, 0, 0, 1, 1, 1]
```

문제점:
- **"나는 고양이를 좋아한다"** 와 **"고양이를 나는 좋아한다"** 가 동일한 벡터
- 단어의 의미적 관계를 전혀 파악할 수 없음
- 어휘가 커지면 대부분이 0인 희소 벡터(sparse vector)가 됨

### 4.4.2 TF-IDF (Term Frequency - Inverse Document Frequency)

BoW를 개선한 방법입니다. 핵심 아이디어:

> **"모든 문서에 나타나는 단어(예: '은', '는', '의')는 덜 중요하고,**
> **특정 문서에만 나타나는 단어가 더 중요하다."**

```
TF-IDF = TF(단어 빈도) x IDF(역문서 빈도)

TF(t, d)  = 문서 d에서 단어 t가 등장한 횟수
IDF(t)    = log(전체 문서 수 / 단어 t가 등장한 문서 수)

예시 (3개 문서):

문서1: "파이썬 프로그래밍 기초"
문서2: "파이썬 머신러닝 실전"
문서3: "자바 프로그래밍 기초"

단어 "파이썬":
  TF  = 1 (각 문서에서 1회 등장)
  IDF = log(3/2) = 0.41  (3개 문서 중 2개에 등장)

단어 "머신러닝":
  TF  = 1
  IDF = log(3/1) = 1.10  (3개 문서 중 1개에만 등장 -> 더 중요!)

단어 "기초":
  TF  = 1
  IDF = log(3/2) = 0.41  (2개 문서에 등장 -> 덜 특별함)
```

TF-IDF는 검색 엔진에서 오랫동안 핵심 알고리즘으로 사용되었습니다.
지금도 간단한 텍스트 유사도 계산이나 키워드 추출에 활용됩니다.

### 4.4.3 전통적 방법의 한계

```
전통적 방법          vs.          현대적 방법 (임베딩)
---------------------------------------------------------
단어 순서 무시                    순서 정보 보존
의미 관계 파악 불가               유사 단어 인식 가능
고정된 표현                       문맥에 따라 달라지는 표현
희소 벡터 (대부분 0)              밀집 벡터 (정보가 압축됨)
```

## 4.5 Seq2Seq와 Encoder-Decoder 구조

### 4.5.1 문제: 입력과 출력의 길이가 다르다

기계 번역을 생각해 보겠습니다:

```
입력:  "나는 학생입니다"         (3 토큰)
출력:  "I am a student"         (4 토큰)
```

입력 길이와 출력 길이가 다릅니다. 이런 문제를 **시퀀스-투-시퀀스
(Sequence-to-Sequence, Seq2Seq)** 모델로 해결합니다.

### 4.5.2 Encoder-Decoder 구조

2014년 Google의 Sutskever 등이 제안한 이 구조는
NLP의 패러다임을 바꿨습니다:

```
[Encoder-Decoder 구조]

  입력: "나는 학생입니다"

  ┌─────────── Encoder ───────────┐
  │                               │
  │  "나는" -> [RNN] -> h1        │
  │                  ↓            │
  │  "학생" -> [RNN] -> h2        │
  │                  ↓            │
  │  "입니다" -> [RNN] -> h3      │
  │                  |            │
  └──────────────────|────────────┘
                     |
              Context Vector (문맥 벡터)
              = 입력 문장 전체를 하나의
                벡터로 압축한 것
                     |
  ┌──────────────────|────────────┐
  │                  |            │
  │  [RNN] <- Context  -> "I"    │
  │    ↓                         │
  │  [RNN] <- "I"      -> "am"   │
  │    ↓                         │
  │  [RNN] <- "am"     -> "a"    │
  │    ↓                         │
  │  [RNN] <- "a"    -> "student"│
  │    ↓                         │
  │  [RNN] <- "student" -> [END] │
  │                               │
  └─────────── Decoder ───────────┘

  출력: "I am a student"
```

**인코더(Encoder)** 는 입력 문장을 읽고 **문맥 벡터(Context Vector)** 라는
하나의 고정 길이 벡터로 압축합니다.

**디코더(Decoder)** 는 이 문맥 벡터를 받아 한 단어씩 출력을 생성합니다.

### 4.5.3 병목 현상: 모든 정보를 하나의 벡터에 넣을 수 있을까?

여기서 심각한 문제가 발생합니다:

> **긴 문장의 모든 정보를 고정 길이 벡터 하나에 담는 것은 무리입니다.**

```
짧은 문장: "고맙습니다" -> [0.2, 0.8, -0.1, ...]  (OK!)

긴 문장:   "어제 서울역 근처 카페에서 오랜만에 만난 친구와
            함께 아이스 아메리카노를 마시면서 최근 인공지능
            기술의 발전에 대해 깊은 대화를 나누었다"
            -> [0.5, 0.3, -0.4, ...]  (같은 크기 벡터에? 정보 손실!)
```

문장이 길어질수록 번역 품질이 급격히 떨어졌습니다.
이 문제를 해결하기 위해 등장한 것이 바로 **어텐션(Attention)** 입니다.

## 4.6 Attention 메커니즘의 탄생

### 4.6.1 핵심 아이디어: "모든 것을 똑같이 볼 필요는 없다"

2014년 Bahdanau 등은 획기적인 아이디어를 제안했습니다:

> **"디코더가 출력 단어를 생성할 때, 인코더의 모든 위치를 직접 참조하되,**
> **현재 생성하는 단어와 관련 있는 부분에 더 높은 가중치를 부여하자."**

이것이 **어텐션 메커니즘(Attention Mechanism)** 입니다.

```
[Attention 메커니즘 시각화]

인코더 출력:  h1("나는")   h2("학생")   h3("입니다")

디코더가 "I"를 생성할 때:
  어텐션 가중치:  [0.85]       [0.10]       [0.05]
                   ↑ "나는"에 집중!

디코더가 "student"를 생성할 때:
  어텐션 가중치:  [0.05]       [0.90]       [0.05]
                               ↑ "학생"에 집중!
```

기존 Seq2Seq와의 차이를 비교하면:

```
[기존 Seq2Seq]

인코더: "나는" -> "학생" -> "입니다" -> [단일 문맥 벡터]
                                           |
디코더:                                    +-> "I" -> "am" -> ...
        (항상 같은 벡터만 참조)


[Attention이 있는 Seq2Seq]

인코더: "나는" -> "학생" -> "입니다"
          |         |         |
          v         v         v
디코더: --+---------+---------+--> "I"     (나는에 주목)
          |         |         |
          v         v         v
        --+---------+---------+--> "am"    (입니다에 주목)
          |         |         |
          v         v         v
        --+---------+---------+--> "a"     (...)
          |         |         |
          v         v         v
        --+---------+---------+--> "student" (학생에 주목)

  (매 출력마다 입력의 다른 부분에 선택적으로 집중)
```

### 4.6.2 Attention 가중치 계산

Attention의 수학적 원리를 직관적으로 설명하면:

```
1. 디코더의 현재 상태(Query)와
   인코더의 각 위치 상태(Key)의 유사도를 계산한다

2. 유사도를 확률로 변환한다 (softmax)

3. 이 확률을 가중치로 사용하여
   인코더의 각 위치 값(Value)을 가중합한다

              Query: "지금 생성하려는 단어는 뭐지?"
                |
                v
   Score = similarity(Query, Key_i)   각 위치별 유사도
                |
                v
   Weight = softmax(Scores)           확률로 변환
                |
                v
   Output = sum(Weight_i * Value_i)   가중합
```

이 Query, Key, Value 개념은 이후 **Transformer(트랜스포머)** 의
**Self-Attention** 으로 발전하게 됩니다. (다음 장에서 자세히 다룹니다!)

### 4.6.3 Attention은 왜 혁명적이었나

```
1. 정보 병목 해소
   - 긴 문장도 정보 손실 없이 처리 가능
   - 문맥 벡터 하나에 의존하지 않음

2. 해석 가능성 (Interpretability)
   - 어텐션 가중치를 시각화하면 모델이 "어디를 보고 있는지" 확인 가능
   - 번역에서 어떤 입력 단어가 어떤 출력 단어에 대응되는지 보임

3. 성능 향상
   - 기계 번역의 BLEU 점수가 크게 향상
   - 특히 긴 문장에서의 성능이 극적으로 개선

4. Transformer의 기반
   - 2017년 "Attention is All You Need" 논문의 직접적 영감
   - 현대 LLM의 핵심 구성 요소
```

## 4.7 단어 수준에서 서브워드로 - 현대 LLM이 BPE를 선택한 이유

### 4.7.1 단어 수준 토큰화의 문제

초기 NLP 모델은 단어 단위로 토큰화했습니다. 하지만 심각한 문제가 있었습니다:

```
[단어 수준 토큰화의 문제]

1. 어휘 크기 폭발
   영어만 해도 50만 개 이상의 단어
   + 한국어, 일본어, 중국어, ...
   = 수백만 개의 어휘가 필요

2. 미등록어 (OOV: Out of Vocabulary)
   "ChatGPT"라는 새로운 단어가 등장하면?
   -> [UNK] (Unknown) 토큰으로 처리
   -> 의미 정보 완전 손실!

3. 형태학적 관계 무시
   "play", "plays", "played", "playing"
   -> 모두 다른 토큰으로 처리
   -> "play"라는 공통 의미가 공유되지 않음
```

### 4.7.2 문자 수준은 어떨까?

반대로 한 글자씩 토큰화하면?

```
[문자 수준 토큰화]

"Hello" -> ["H", "e", "l", "l", "o"]

장점: 어휘 크기가 매우 작음 (영어: 26개 + 특수문자)
단점: 시퀀스가 너무 길어짐
      "Hello world" -> 11개 토큰 (공백 포함)
      -> 계산 비용 증가, 장거리 의존성 학습 어려움
```

### 4.7.3 서브워드 토큰화: 최적의 균형점

**서브워드 토큰화(Subword Tokenization)** 는
단어와 문자 사이의 최적 지점을 찾습니다:

```
[서브워드 토큰화의 균형]

문자 수준  <------------|------------>  단어 수준
                        ^
                   서브워드 수준
                   (BPE, WordPiece)

자주 쓰는 단어:  "the"     -> ["the"]        (그대로 유지)
드문 단어:      "unhappily" -> ["un", "happi", "ly"]  (분할)
미등록어:       "ChatGPT"  -> ["Chat", "G", "PT"]     (처리 가능!)
```

### 4.7.4 현대 LLM들의 토큰화 전략

```
모델                 토큰화 방식        어휘 크기
--------------------------------------------------
GPT-4               BPE               ~100,000
Claude               BPE (추정)        ~100,000
BERT                 WordPiece         30,522
T5                   SentencePiece     32,000
LLaMA                SentencePiece     32,000
LLaMA 2              BPE               32,000
Gemini               SentencePiece     256,000
```

대부분의 최신 LLM이 BPE 또는 SentencePiece를 사용합니다.
이는 BPE가 가진 실용적 장점 때문입니다:

1. **구현이 단순합니다** - 빈도 기반 병합만으로 동작
2. **어떤 텍스트든 처리 가능합니다** - 미등록어가 원칙적으로 없음
3. **어휘 크기를 자유롭게 조절할 수 있습니다** - 병합 횟수로 제어
4. **다국어 처리에 유리합니다** - 바이트 수준에서 시작하므로

## 4.8 이 기초가 LLM 이해에 왜 중요한가

지금까지 배운 내용이 현대 LLM과 어떻게 연결되는지 정리하겠습니다:

```
[NLP 기초 -> LLM 연결 지도]

토큰화 (BPE)
  └─> LLM의 입력 전처리 단계
      - API 비용이 토큰 수에 비례하는 이유
      - 한국어가 영어보다 토큰을 많이 쓰는 이유
      - 최대 컨텍스트 길이가 토큰 단위인 이유

임베딩
  └─> LLM의 첫 번째 레이어
      - 입력 토큰이 벡터로 변환되는 과정
      - RAG에서 유사도 검색이 가능한 이유
      - 의미 검색(Semantic Search)의 원리

Seq2Seq / Encoder-Decoder
  └─> LLM 구조의 역사적 기원
      - GPT는 Decoder만 사용 (Decoder-only)
      - BERT는 Encoder만 사용 (Encoder-only)
      - T5는 Encoder-Decoder 모두 사용

Attention
  └─> Transformer의 핵심 구성 요소
      - Self-Attention으로 발전
      - LLM이 긴 문맥을 처리할 수 있는 이유
      - "Attention is All You Need"의 직접적 배경
```

## 4.9 핵심 요약

```
1. 컴퓨터는 텍스트를 직접 처리할 수 없다 -> 숫자로 변환해야 한다

2. 토큰화(Tokenization)는 텍스트를 의미 있는 조각으로 나눈다
   - BPE: 빈도 기반 서브워드 병합 (GPT, Claude)
   - WordPiece: 우도 기반 서브워드 병합 (BERT)
   - SentencePiece: 언어 독립적 토큰화 (T5, LLaMA)

3. 임베딩(Embedding)은 단어를 의미를 담은 벡터로 변환한다
   - Word2Vec: 주변 단어 예측 기반
   - GloVe: 전역 동시출현 통계 기반
   - "King - Man + Woman = Queen"이 가능한 이유

4. 전통적 방법(BoW, TF-IDF)은 단어 순서를 무시하는 한계가 있다

5. Seq2Seq와 Encoder-Decoder 구조는 가변 길이 변환 문제를 해결했다

6. Attention 메커니즘은 "중요한 부분에 집중"하는 능력을 부여했다
   -> Transformer와 현대 LLM의 직접적 기반

7. 서브워드 토큰화(BPE)는 어휘 크기와 표현력의 최적 균형을 제공한다
```
