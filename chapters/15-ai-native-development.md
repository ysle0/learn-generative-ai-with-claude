## 1. Vibe Coding — 자연어로 코딩하는 시대

### 1.1 Vibe Coding이란

**Vibe Coding**은 Tesla AI 디렉터 출신 Andrej Karpathy가 2025년 초 제안한 용어입니다.
핵심 아이디어는 간단합니다.

> "You describe the vibe, AI writes the code."
> (분위기를 설명하면 AI가 코드를 작성한다.)

전통적 개발에서는 개발자가 모든 코드를 한 줄씩 직접 작성했습니다.
Vibe Coding에서는 개발자가 **원하는 결과를 자연어로 설명**하고,
AI가 그에 맞는 코드를 생성합니다.

```
+---------------------------------------------------------------+
|                전통적 개발 방식                                  |
|                                                               |
|   개발자 --> [코드 작성] --> [테스트] --> [디버깅] --> 완성       |
|                                                               |
+---------------------------------------------------------------+
|                Vibe Coding 방식                                 |
|                                                               |
|   개발자 --> [자연어 설명] --> AI가 코드 생성 --> [검토/수정]     |
|       ^                                             |         |
|       |______________ 피드백 루프 ___________________|         |
|                                                               |
+---------------------------------------------------------------+
```

### 1.2 실제 Vibe Coding 예시: Claude Code에서

Claude Code에서 Vibe Coding을 하는 모습을 살펴보겠습니다.

```bash
# 터미널에서 Claude Code 실행 후 자연어로 요청
$ claude

> 사용자 인증 API를 만들어줘. Express.js로, JWT 토큰 방식이고,
> 이메일/비밀번호 로그인이야. 비밀번호는 bcrypt로 해싱하고,
> 토큰 만료는 24시간으로 설정해줘.
```

AI가 라우터, 미들웨어, 유틸리티 함수를 한 번에 생성합니다.
여기서 중요한 것은 **결과물의 "분위기(vibe)"를 명확히 전달**하는 것입니다.

### 1.3 Vibe Coding이 잘 작동하는 경우

| 상황 | 이유 |
|------|------|
| 프로토타이핑 / MVP | 빠른 속도가 정확도보다 중요 |
| 표준적인 CRUD API | 패턴이 잘 확립되어 있음 |
| UI 컴포넌트 생성 | 시각적 결과를 자연어로 설명하기 쉬움 |
| 설정 파일 작성 | 반복적이고 문서화가 잘 되어 있음 |
| 데이터 변환 스크립트 | 입력/출력 형식만 명확하면 됨 |

### 1.4 Vibe Coding이 위험한 경우

| 상황 | 이유 |
|------|------|
| 분산 시스템의 동시성 처리 | 미묘한 경쟁 조건(race condition)을 자연어로 완벽히 설명하기 어려움 |
| 암호화/보안 로직 | 작은 실수가 치명적 보안 취약점으로 이어짐 |
| 성능 최적화 코드 | 하드웨어 특성과 측정 데이터가 필요 |
| 레거시 시스템 연동 | AI가 모르는 내부 규칙이 많음 |

### 1.5 반복과 피드백 루프의 중요성

Vibe Coding의 핵심은 **한 번에 완벽한 코드를 기대하지 않는 것**입니다.

```
+-------------------------------------------------------------------+
|              Vibe Coding 피드백 루프                                |
|                                                                   |
|   [1단계]  대략적 설명  -->  AI가 초안 생성                         |
|       |                                                           |
|   [2단계]  결과 확인    -->  부족한 부분 발견                       |
|       |                                                           |
|   [3단계]  구체적 수정 요청  -->  AI가 개선                         |
|       |                                                           |
|   [4단계]  엣지 케이스 추가 요청  -->  AI가 보완                    |
|       |                                                           |
|   [5단계]  완성된 코드 최종 검토                                    |
+-------------------------------------------------------------------+
```

실전 팁: Claude Code에서는 `/clear`로 컨텍스트를 정리한 뒤
이전 대화에서 발견한 문제를 **구체적으로** 다시 설명하면 더 좋은 결과를 얻습니다.

## 2. Prompt-Driven Development (PDD)

### 2.1 프롬프트가 곧 명세서다

전통적 개발에서는 기획서(PRD)를 받고 개발자가 설계하고 구현합니다.
PDD에서는 **프롬프트 자체가 명세(Specification)** 역할을 합니다.

```
+-------------------------------------------------------------------+
|          전통 개발                PDD                               |
|                                                                   |
|   기획서(PRD)                프롬프트(Prompt)                       |
|       |                         |                                 |
|   설계 문서                     |  (프롬프트에 설계 포함)            |
|       |                         |                                 |
|   개발자가 구현              AI가 구현                              |
|       |                         |                                 |
|   코드 리뷰                  사람이 검토                            |
|       |                         |                                 |
|   테스트                     테스트 실행                            |
+-------------------------------------------------------------------+
```

### 2.2 좋은 프롬프트 명세의 구조

AI에게 좋은 구현을 얻으려면 프롬프트에 이 요소들이 포함되어야 합니다.

```markdown
## 좋은 PDD 프롬프트 템플릿

### 목적 (What & Why)
- 무엇을 만드는가
- 왜 필요한가

### 입력/출력 (Interface)
- 함수 시그니처 또는 API 엔드포인트
- 입력 데이터의 형태와 예시
- 기대하는 출력의 형태와 예시

### 제약 조건 (Constraints)
- 사용할 라이브러리/프레임워크
- 성능 요구사항
- 호환성 요구사항

### 엣지 케이스 (Edge Cases)
- 빈 입력이 들어오면?
- 잘못된 형식이면?
- 매우 큰 데이터면?
```

### 2.3 실전 PDD 워크플로우: Kilo Code 예시

Kilo Code에서 PDD를 적용하는 구체적 흐름입니다.

```bash
# 1단계: 명세 프롬프트 작성
"다음 조건으로 주문 할인 계산 함수를 구현해줘:
- 입력: { items: CartItem[], couponCode?: string, memberTier: 'bronze'|'silver'|'gold' }
- 출력: { originalTotal: number, discount: number, finalTotal: number }
- 규칙:
  - 10만원 이상이면 5% 할인
  - gold 회원은 추가 10% 할인
  - silver 회원은 추가 5% 할인
  - 쿠폰이 있으면 쿠폰 할인 추가 적용 (중복 할인 가능)
  - 최종 금액이 0 미만이면 0으로 처리
- TypeScript로 작성, 순수 함수로 구현"

# 2단계: AI가 구현한 코드 검토

# 3단계: 부족한 부분을 추가 프롬프트로 보완
"쿠폰 코드 유효성 검증 로직도 추가해줘.
유효하지 않은 쿠폰이면 할인 없이 계산하고,
couponValid: false 필드를 출력에 추가해줘."
```

### 2.4 반복적 정제 워크플로우

PDD의 효과를 극대화하는 핵심은 **점진적 정제(Iterative Refinement)** 입니다.

```
+-------------------------------------------------------------------+
|              PDD 반복 정제 사이클                                    |
|                                                                   |
|   Prompt v1  -- AI 생성 -->  Code v1  -- 검토 -->  피드백          |
|       |                                               |           |
|   Prompt v2  <---------- 피드백 반영 ----------------+            |
|       |                                                           |
|   Prompt v2  -- AI 생성 -->  Code v2  -- 검토 -->  피드백          |
|       |                                               |           |
|   Prompt v3  <---------- 피드백 반영 ----------------+            |
|       |                                                           |
|       v                                                           |
|   최종 프롬프트를 문서로 보관 (향후 유사 기능 개발에 재활용)          |
+-------------------------------------------------------------------+
```

프롬프트를 버전 관리하면 **같은 기능을 다시 만들 때** 재사용할 수 있습니다.
프로젝트의 `prompts/` 디렉토리에 검증된 프롬프트를 저장해 두는 팀도 있습니다.

## 3. AI-Assisted TDD

### 3.1 테스트 먼저, 구현은 AI에게

전통적 TDD(Test-Driven Development)에서는 사람이 테스트와 구현 모두 작성합니다.
AI-Assisted TDD에서는 역할을 분담합니다.

```
+-------------------------------------------------------------------+
|                    AI-Assisted TDD 역할 분담                        |
|                                                                   |
|   사람의 역할:                  AI의 역할:                          |
|   - 테스트 케이스 설계          - 테스트를 통과하는 구현 작성         |
|   - 엣지 케이스 정의            - 리팩토링 제안                      |
|   - 비즈니스 로직 검증          - 추가 테스트 케이스 제안             |
|   - 최종 코드 승인              - 코드 최적화                        |
+-------------------------------------------------------------------+
```

### 3.2 실전 예시: Claude Code로 AI-Assisted TDD

```bash
# 1단계: 사람이 테스트를 먼저 작성
$ claude

> 아래 테스트 파일을 만들어줘. 구현은 아직 하지 마.
>
> tests/calculateShipping.test.ts
> - 기본 배송비는 3000원
> - 주문 금액이 50000원 이상이면 무료 배송
> - 제주도/도서산간이면 추가 3000원
> - 무게가 20kg 초과면 추가 5000원
> - 여러 조건이 동시에 적용될 수 있음
```

AI가 생성한 테스트 파일:

```typescript
// tests/calculateShipping.test.ts
describe('calculateShipping', () => {
  it('기본 배송비는 3000원이다', () => {
    const result = calculateShipping({
      orderAmount: 10000,
      region: 'mainland',
      weightKg: 5
    });
    expect(result).toBe(3000);
  });

  it('50000원 이상이면 무료 배송이다', () => {
    const result = calculateShipping({
      orderAmount: 50000,
      region: 'mainland',
      weightKg: 5
    });
    expect(result).toBe(0);
  });

  it('제주도는 추가 3000원이다', () => {
    const result = calculateShipping({
      orderAmount: 10000,
      region: 'jeju',
      weightKg: 5
    });
    expect(result).toBe(6000);  // 3000 + 3000
  });

  // ... 더 많은 테스트 케이스
});
```

```bash
# 2단계: AI에게 구현을 요청
> 이 테스트를 모두 통과하는 calculateShipping 함수를 구현해줘.
> src/utils/calculateShipping.ts에 작성해줘.

# 3단계: 테스트 실행으로 검증
> npm test -- calculateShipping 실행해줘
```

### 3.3 테스트 스위트가 진실의 원천(Source of Truth)

AI-Assisted TDD에서 **테스트 스위트는 코드의 정확성을 보장하는 안전망**입니다.

```
+-------------------------------------------------------------------+
|              테스트 = AI 코드의 안전망                               |
|                                                                   |
|   AI가 잘못된 코드 생성  -->  테스트 실패  -->  즉시 발견            |
|                                                                   |
|   AI가 리팩토링 제안    -->  테스트 통과  -->  안전하게 수용          |
|                                                                   |
|   AI가 최적화 시도      -->  테스트 실패  -->  동작 변경 감지         |
|                                                                   |
|   핵심: 테스트가 있으면 AI 코드를 "신뢰하되 검증"할 수 있다          |
+-------------------------------------------------------------------+
```

이 방식의 가장 큰 장점은 **AI가 생성한 코드의 정확성을 자동으로 검증**할 수 있다는 것입니다.
사람이 모든 코드를 눈으로 읽지 않아도, 테스트가 통과하면 일정 수준의 신뢰를 확보합니다.

## 4. Human-in-the-Loop — 사람의 검증이 필수인 이유

### 4.1 AI 코드를 맹목적으로 수용하지 마라

AI가 생성한 코드는 **대부분 올바르게 보이지만, 미묘한 결함을 포함**할 수 있습니다.

실제 사례를 보겠습니다.

```javascript
// AI가 생성한 코드 (겉보기에 문제 없음)
async function getUserData(userId) {
  const user = await db.query(`SELECT * FROM users WHERE id = ${userId}`);
  return user;
}
```

이 코드의 문제점이 보이시나요? **SQL Injection 취약점**이 있습니다.
AI는 문법적으로 올바르고, 기능적으로 동작하는 코드를 생성했지만,
보안 관점에서는 심각한 결함이 있습니다.

```javascript
// 올바른 구현
async function getUserData(userId) {
  const user = await db.query('SELECT * FROM users WHERE id = $1', [userId]);
  return user;
}
```

### 4.2 "이해하지 못하는 코드"의 위험

```
+-------------------------------------------------------------------+
|           코드 이해도에 따른 위험 수준                               |
|                                                                   |
|   이해도 높음  |████████████|  위험 낮음 - 유지보수 가능             |
|   이해도 중간  |████████    |  주의 필요 - 학습 후 수용              |
|   이해도 낮음  |████        |  위험 높음 - 반드시 학습 필요           |
|   이해 못함    |██          |  매우 위험 - 수용 금지                  |
|                                                                   |
|   원칙: 설명할 수 없는 코드는 커밋하지 않는다                        |
+-------------------------------------------------------------------+
```

### 4.3 Human-in-the-Loop 체크리스트

AI가 생성한 코드를 커밋하기 전, 다음을 확인하십시오.

```
[ ] 코드의 의도를 내가 한 문장으로 설명할 수 있는가?
[ ] 각 함수가 무엇을 하는지 이해하는가?
[ ] 엣지 케이스가 적절히 처리되는가?
[ ] 보안 취약점이 없는가? (입력 검증, SQL Injection, XSS 등)
[ ] 에러 처리가 적절한가?
[ ] 기존 코드 스타일과 일관성이 있는가?
[ ] 불필요한 의존성이 추가되지 않았는가?
[ ] 테스트가 존재하고 통과하는가?
```

### 4.4 실전 워크플로우: Claude Code에서의 검증

```bash
# Claude Code에서 코드 생성 후 검토 프로세스

# 1. 생성된 코드의 diff 확인
$ git diff

# 2. AI에게 설명 요청
> 방금 생성한 코드에서 가장 주의해야 할 부분이 어디야?
> 보안 관점에서 취약점이 있을 수 있는 곳을 알려줘.

# 3. 테스트 실행
> npm test 실행해줘

# 4. 이해가 안 되는 부분 질문
> 이 정규표현식이 정확히 어떤 패턴을 매칭하는지 설명해줘:
> /^(?=.*[A-Z])(?=.*[a-z])(?=.*\d)(?=.*[@$!%*?&])[A-Za-z\d@$!%*?&]{8,}$/

# 5. 확인 후 커밋
$ git add -A && git commit -m "feat: add user authentication"
```

## 5. AI Pair Programming

### 5.1 새로운 형태의 페어 프로그래밍

전통적 페어 프로그래밍에서 두 명의 개발자가 Driver(코드 작성)와
Navigator(방향 제시) 역할을 번갈아 수행했습니다.
AI Pair Programming에서는 **사람과 AI가 이 역할을 나눕니다**.

```
+-------------------------------------------------------------------+
|              AI Pair Programming 모드                               |
|                                                                   |
|   모드 A: AI가 Driver, 사람이 Navigator                             |
|   +----------------------------+                                   |
|   |  사람: "인증 미들웨어 만들어"  |                                 |
|   |  AI: [코드 작성]              |                                 |
|   |  사람: "에러 처리 추가해"      |                                 |
|   |  AI: [코드 수정]              |                                 |
|   +----------------------------+                                   |
|   적합: 보일러플레이트, 표준 패턴, 빠른 프로토타이핑                  |
|                                                                   |
|   모드 B: 사람이 Driver, AI가 Navigator                             |
|   +----------------------------+                                   |
|   |  사람: [핵심 로직 직접 작성]   |                                 |
|   |  AI: "여기 null 체크 필요해요" |                                 |
|   |  사람: [수정]                  |                                 |
|   |  AI: "이 알고리즘 O(n²)이에요" |                                 |
|   +----------------------------+                                   |
|   적합: 복잡한 비즈니스 로직, 알고리즘, 성능 최적화                   |
|                                                                   |
+-------------------------------------------------------------------+
```

### 5.2 언제 AI에게 주도권을 줄 것인가

```
+-------------------------------------------------------------------+
|                   AI 주도 vs 사람 주도 판단 기준                     |
|                                                                   |
|   AI에게 맡기기 좋은 작업:             사람이 직접 해야 하는 작업:    |
|   - 파일 구조 생성(scaffolding)       - 핵심 비즈니스 규칙 설계     |
|   - 테스트 코드 작성                   - 아키텍처 결정               |
|   - API 클라이언트 코드                - 보안 관련 코드 최종 검토    |
|   - 타입 정의/인터페이스               - 성능 병목 구간 최적화       |
|   - 문서화/주석 추가                   - 장애 대응 코드              |
|   - 리팩토링 제안                      - 데이터 마이그레이션 설계    |
+-------------------------------------------------------------------+
```

### 5.3 효과적인 AI Pair Programming 패턴

```bash
# 패턴 1: 점진적 구체화 (Progressive Specification)
> "사용자 프로필 페이지를 만들어줘"           # 큰 그림
> "프로필 사진 업로드 기능을 추가해줘"         # 기능 추가
> "이미지 리사이징은 sharp 라이브러리 써줘"    # 구현 디테일

# 패턴 2: 샌드위치 방식 (사람-AI-사람)
# 사람: 인터페이스/타입 정의
# AI: 구현
# 사람: 리뷰 및 수정

# 패턴 3: 탐색적 코딩 (Exploratory Coding)
> "이 문제를 해결하는 방법 3가지를 제안해줘, 각각의 장단점과 함께"
# 사람이 방법을 선택한 후
> "2번 방법으로 구현해줘"
```

## 6. AI Code Review와 품질 관리

### 6.1 AI로 AI 생성 코드를 리뷰하기

AI가 생성한 코드를 다른 AI(또는 같은 AI의 새 세션)로 리뷰하는 것은
효과적인 품질 관리 기법입니다.

```bash
# Claude Code에서 코드 리뷰 요청
> 방금 작성한 코드를 리뷰해줘. 특히 다음 관점에서:
> 1. 보안 취약점
> 2. 성능 문제
> 3. 에러 처리 누락
> 4. 타입 안전성
> 5. 테스트 커버리지 부족한 부분
```

### 6.2 자동화된 가드레일(Guardrails) 구축

AI 생성 코드의 품질을 유지하기 위해 **자동화된 검증 파이프라인**이 필요합니다.

```
+-------------------------------------------------------------------+
|              AI 코드 품질 가드레일                                   |
|                                                                   |
|   AI가 코드 생성                                                   |
|       |                                                           |
|       v                                                           |
|   [린터(ESLint/Prettier)] -- 스타일/문법 검증                      |
|       |                                                           |
|       v                                                           |
|   [타입 검사(TypeScript)] -- 타입 안전성 검증                       |
|       |                                                           |
|       v                                                           |
|   [단위 테스트(Jest/Vitest)] -- 기능 정확성 검증                    |
|       |                                                           |
|       v                                                           |
|   [통합 테스트] -- 시스템 전체 동작 검증                             |
|       |                                                           |
|       v                                                           |
|   [보안 스캔(Snyk/npm audit)] -- 보안 취약점 검증                   |
|       |                                                           |
|       v                                                           |
|   사람의 최종 리뷰                                                  |
+-------------------------------------------------------------------+
```

### 6.3 CI/CD에 통합하기

```yaml
# .github/workflows/ai-code-quality.yml 예시
name: AI Code Quality Check
on: [push, pull_request]
jobs:
  quality-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run lint          # 코드 스타일 검증
      - run: npm run type-check    # 타입 안전성 검증
      - run: npm test              # 전체 테스트 실행
      - run: npm audit             # 보안 취약점 검사
```

AI가 코드를 생성했든 사람이 직접 작성했든, **같은 품질 기준을 적용**해야 합니다.
오히려 AI 생성 코드에는 더 엄격한 기준을 적용하는 팀도 있습니다.

### 7.1 판단 매트릭스

```
|                  |  (설정 파일,      |  (내부 툴,         |          |
|                  |   보일러플레이트)  |   스크립트)        |          |

|                     낮음                높음                        |

```

### 7.2 구체적 가이드라인

**AI에게 맡기세요 (보일러플레이트)**

```bash
# 이런 작업은 AI가 더 빠르고 정확합니다
> Express 라우터 보일러플레이트 만들어줘
> TypeScript 인터페이스를 JSON 스키마에서 생성해줘
> 이 컴포넌트에 Storybook 스토리 추가해줘
> .gitignore 파일 만들어줘 (Node.js 프로젝트)
> Docker 설정 파일 만들어줘
```

**사람이 모든 줄을 이해해야 합니다 (핵심 비즈니스 로직)**

```bash
# 이런 코드는 AI가 생성하더라도 반드시 한 줄씩 이해하세요
- 결제 금액 계산 로직
- 사용자 권한 검증 로직
- 데이터 정합성 검증 규칙
- 외부 API 연동에서의 재시도/롤백 로직
```

**추가 검증이 필요합니다 (보안 관련 코드)**

```bash
# 보안 관련 코드는 AI 생성 후 추가 검증을 거쳐야 합니다
- 입력 검증 및 새니타이징(sanitizing)
- 인증/인가(authentication/authorization) 로직
- 암호화 관련 코드
- 파일 업로드 처리
- 외부 입력을 받는 모든 엔드포인트
```

## 8. AI 친화적 프로젝트 구조

### 8.1 CLAUDE.md — AI에게 프로젝트를 설명하는 파일

Claude Code는 프로젝트 루트의 `CLAUDE.md` 파일을 자동으로 읽어
프로젝트의 컨텍스트를 이해합니다.

```markdown
# CLAUDE.md 예시

## 프로젝트 개요
이커머스 백엔드 API 서버. Express.js + TypeScript + PostgreSQL.

## 디렉토리 구조
- src/routes/     - API 라우터
- src/services/   - 비즈니스 로직
- src/models/     - 데이터베이스 모델 (Prisma)
- src/middleware/  - Express 미들웨어
- tests/          - 테스트 파일 (Jest)

## 코드 컨벤션
- 함수명: camelCase
- 파일명: kebab-case
- 에러 처리: AppError 클래스 사용
- 모든 API 응답은 { success, data, error } 형태

## 빌드 & 테스트
- npm run dev: 개발 서버 실행
- npm test: 전체 테스트 실행
- npm run build: 프로덕션 빌드

## 중요한 규칙
- DB 쿼리는 반드시 Prisma ORM 사용 (raw query 금지)
- 환경 변수는 src/config/env.ts에서 관리
- 모든 라우트에 인증 미들웨어 필수
```

### 8.2 다른 AI 도구의 프로젝트 설정 파일

| 도구 | 설정 파일 | 용도 |
|------|-----------|------|
| Claude Code | `CLAUDE.md` | 프로젝트 컨텍스트, 규칙, 빌드 명령어 |
| Cursor | `.cursorrules` | 코드 스타일, 프로젝트 규칙 |
| 범용 | `system-prompt.md` | AI 도구에 공통 적용할 지시사항 |
| Kilo Code | `.kilocode/rules` | 프로젝트 규칙 및 컨텍스트 설정 |

### 8.3 AI 친화적 프로젝트 구조 원칙

```
+-------------------------------------------------------------------+
|              AI 친화적 프로젝트 구조 체크리스트                       |
|                                                                   |
|   [구조]                                                           |
|   [ ] 명확한 디렉토리 구조와 네이밍 규칙                             |
|   [ ] 각 디렉토리에 README 또는 index 파일 존재                     |
|   [ ] 관심사 분리 (한 파일이 한 가지 역할)                           |
|                                                                   |
|   [문서화]                                                         |
|   [ ] CLAUDE.md (또는 해당 AI 도구의 설정 파일) 존재                |
|   [ ] API 엔드포인트 문서화                                         |
|   [ ] 타입 정의가 명확 (TypeScript, JSDoc)                          |
|   [ ] 환경 변수 목록과 설명                                         |
|                                                                   |
|   [테스트]                                                         |
|   [ ] 테스트 파일이 소스 파일과 대응                                 |
|   [ ] 테스트 실행 명령어가 간단                                     |
|   [ ] 테스트 데이터/픽스처가 정리되어 있음                           |
|                                                                   |
|   [의존성]                                                         |
|   [ ] package.json의 scripts 섹션이 정리됨                         |
|   [ ] 필요한 의존성이 명확히 선언됨                                  |
+-------------------------------------------------------------------+
```

### 8.4 모노레포 vs 멀티레포: AI 관점에서

```
+-------------------------------------------------------------------+
|              모노레포 (Monorepo)                                    |
|                                                                   |
|   장점:                                                            |
|   - AI가 전체 프로젝트 컨텍스트를 한 번에 파악 가능                  |
|   - 공유 코드의 변경 영향 범위를 AI가 추적 가능                      |
|   - CLAUDE.md 하나로 전체 프로젝트 설명 가능                        |
|                                                                   |
|   단점:                                                            |
|   - 컨텍스트 윈도우(Context Window) 제한에 걸릴 수 있음              |
|   - AI가 관련 없는 코드에 혼란을 느낄 수 있음                        |
|                                                                   |
+-------------------------------------------------------------------+
|              멀티레포 (Multi-repo)                                  |
|                                                                   |
|   장점:                                                            |
|   - 각 레포가 작아서 AI가 전체를 이해하기 쉬움                       |
|   - 명확한 경계로 AI가 범위를 벗어난 변경을 하지 않음                |
|                                                                   |
|   단점:                                                            |
|   - 여러 레포에 걸친 변경을 AI에게 한 번에 요청하기 어려움            |
|   - 레포 간 인터페이스 변경 시 AI가 다른 레포 영향을 모름             |
|                                                                   |
+-------------------------------------------------------------------+
|                                                                   |
|   실용적 조언:                                                     |
|   AI 도구를 적극 활용한다면, 관련 코드를 가까이 두는 모노레포가       |
|   일반적으로 유리합니다. 단, 각 패키지/서비스에 개별 CLAUDE.md를     |
|   두어 AI가 해당 영역에 집중하도록 안내하세요.                       |
+-------------------------------------------------------------------+
```

## 9. 정리: AI 네이티브 개발의 핵심 원칙

```
+===================================================================+
|              AI 네이티브 개발 5대 원칙                               |
|                                                                   |
|   1. 신뢰하되 검증하라 (Trust but Verify)                           |
|      AI 코드를 수용하되, 반드시 이해하고 테스트하라                   |
|                                                                   |
|   2. 테스트가 안전망이다 (Tests are Your Safety Net)                |
|      AI가 코드를 작성하기 전에 테스트를 먼저 만들어라                 |
|                                                                   |
|   3. 프롬프트를 설계하라 (Design Your Prompts)                      |
|      좋은 프롬프트는 좋은 설계 문서와 같다                           |
|                                                                   |
|   4. 점진적으로 진행하라 (Iterate Incrementally)                    |
|      한 번에 완벽한 결과를 기대하지 말고, 반복 정제하라               |
|                                                                   |
|   5. AI의 한계를 알라 (Know AI's Limits)                            |
|      보안, 비즈니스 핵심 로직, 아키텍처 결정은 사람의 영역이다        |
|                                                                   |
+===================================================================+
```
