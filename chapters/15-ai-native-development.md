## 1. Vibe Coding — 자연어로 코딩하는 시대

### 1.1 Vibe Coding이란

**Vibe Coding**은 Tesla AI 디렉터 출신 Andrej Karpathy가 2025년 초 제안한 용어입니다.

> "You describe the vibe, AI writes the code."
> (분위기를 설명하면 AI가 코드를 작성한다.)

개발자가 **원하는 결과를 자연어로 설명**하면, AI가 그에 맞는 코드를 생성합니다.

```
+----------------------------------------------------------------+
|   전통적 개발:  개발자 --> [코드 작성] --> [테스트] --> 완성      |
+----------------------------------------------------------------+
|   Vibe Coding:  개발자 --> [자연어 설명] --> AI 코드 생성        |
|                    ^                            |               |
|                    |______ 피드백 루프 __________|               |
+----------------------------------------------------------------+
```

Claude Code에서의 예시:

```bash
$ claude
> 사용자 인증 API를 만들어줘. Express.js로, JWT 토큰 방식이고,
> 이메일/비밀번호 로그인이야. bcrypt 해싱, 토큰 만료 24시간.
```

### 1.2 잘 작동하는 경우 vs 위험한 경우

| 잘 작동하는 경우 | 위험한 경우 |
|-----------------|------------|
| 프로토타이핑 / MVP | 분산 시스템의 동시성 처리 |
| 표준 CRUD API | 암호화/보안 로직 |
| UI 컴포넌트 생성 | 성능 최적화 코드 |
| 설정 파일 / 데이터 변환 | 레거시 시스템 연동 |

### 1.3 반복과 피드백 루프의 중요성

Vibe Coding의 핵심은 **한 번에 완벽한 코드를 기대하지 않는 것**입니다.

```
[1단계] 대략적 설명       -->  AI가 초안 생성
[2단계] 결과 확인          -->  부족한 부분 발견
[3단계] 구체적 수정 요청   -->  AI가 개선
[4단계] 엣지 케이스 추가   -->  AI가 보완
[5단계] 완성된 코드 최종 검토
```

실전 팁: Claude Code에서 `/clear`로 컨텍스트를 정리한 뒤, 발견한 문제를
**구체적으로** 다시 설명하면 더 좋은 결과를 얻습니다.

## 2. Prompt-Driven Development (PDD)

### 2.1 프롬프트가 곧 명세서다

PDD에서는 **프롬프트 자체가 명세(Specification)** 역할을 합니다.

```
전통 개발:  기획서(PRD) --> 설계 문서 --> 개발자가 구현 --> 코드 리뷰
PDD:       프롬프트(Prompt) ----------> AI가 구현 -----> 사람이 검토
```

### 2.2 좋은 프롬프트 명세의 구조

```markdown
## PDD 프롬프트 템플릿

### 목적 (What & Why)
- 무엇을 만드는가, 왜 필요한가

### 입력/출력 (Interface)
- 함수 시그니처, 입력 데이터 형태와 예시, 기대 출력

### 제약 조건 (Constraints)
- 라이브러리/프레임워크, 성능/호환성 요구사항

### 엣지 케이스 (Edge Cases)
- 빈 입력, 잘못된 형식, 대용량 데이터 처리
```

### 2.3 실전 PDD 워크플로우: Kilo Code 예시

```bash
# 1단계: 명세 프롬프트 작성
"다음 조건으로 주문 할인 계산 함수를 구현해줘:
- 입력: { items: CartItem[], couponCode?: string, memberTier: 'bronze'|'silver'|'gold' }
- 출력: { originalTotal: number, discount: number, finalTotal: number }
- 규칙:
  - 10만원 이상 5% 할인, gold +10%, silver +5%
  - 쿠폰 중복 할인 가능, 최종 금액 최소 0원
- TypeScript, 순수 함수로 구현"

# 2단계: AI 구현 결과 검토

# 3단계: 추가 프롬프트로 보완
"쿠폰 유효성 검증 로직도 추가해줘. 무효 쿠폰이면 couponValid: false 반환."
```

### 2.4 반복적 정제 워크플로우

```
Prompt v1 --> AI 생성 --> Code v1 --> 검토 --> 피드백
                                                |
Prompt v2 <-------- 피드백 반영 ----------------+
    |
Prompt v2 --> AI 생성 --> Code v2 --> 검토 --> 피드백
                                                |
최종 프롬프트를 문서로 보관 (향후 재활용) <------+
```

프로젝트의 `prompts/` 디렉토리에 검증된 프롬프트를 저장해 두는 팀도 있습니다.

## 3. AI-Assisted TDD

### 3.1 테스트 먼저, 구현은 AI에게

AI-Assisted TDD에서는 사람과 AI가 역할을 분담합니다.

```
+---------------------------------------------------------------+
|  사람의 역할:                  AI의 역할:                       |
|  - 테스트 케이스 설계          - 테스트를 통과하는 구현 작성     |
|  - 엣지 케이스 정의            - 리팩토링 제안                  |
|  - 비즈니스 로직 검증          - 추가 테스트 케이스 제안         |
|  - 최종 코드 승인              - 코드 최적화                    |
+---------------------------------------------------------------+
```

### 3.2 실전 예시: Claude Code로 AI-Assisted TDD

```bash
# 1단계: 테스트 먼저 작성 요청 (구현은 아직 하지 않음)
$ claude
> tests/calculateShipping.test.ts 테스트만 만들어줘:
> - 기본 배송비 3000원
> - 50000원 이상 무료 배송
> - 제주도/도서산간 추가 3000원
> - 20kg 초과 추가 5000원
```

AI가 생성한 테스트:

```typescript
describe('calculateShipping', () => {
  it('기본 배송비는 3000원이다', () => {
    expect(calculateShipping({ orderAmount: 10000, region: 'mainland', weightKg: 5 }))
      .toBe(3000);
  });

  it('50000원 이상이면 무료 배송이다', () => {
    expect(calculateShipping({ orderAmount: 50000, region: 'mainland', weightKg: 5 }))
      .toBe(0);
  });

  it('제주도는 추가 3000원이다', () => {
    expect(calculateShipping({ orderAmount: 10000, region: 'jeju', weightKg: 5 }))
      .toBe(6000);
  });
});
```

```bash
# 2단계: 구현 요청 --> 3단계: 테스트 실행으로 검증
> 이 테스트를 통과하는 함수를 구현하고, npm test 실행해줘
```

### 3.3 테스트가 AI 코드의 안전망이다

```
AI가 잘못된 코드 생성  -->  테스트 실패  -->  즉시 발견
AI가 리팩토링 제안     -->  테스트 통과  -->  안전하게 수용
AI가 최적화 시도       -->  테스트 실패  -->  동작 변경 감지
```

테스트가 있으면 AI 코드를 **"신뢰하되 검증(Trust but Verify)"** 할 수 있습니다.

## 4. Human-in-the-Loop — 사람의 검증이 필수인 이유

### 4.1 AI 코드를 맹목적으로 수용하지 마라

AI 생성 코드에는 **겉보기에 멀쩡하지만 미묘한 결함**이 숨어 있을 수 있습니다.

```javascript
// AI가 생성한 코드 (SQL Injection 취약점)
async function getUserData(userId) {
  const user = await db.query(`SELECT * FROM users WHERE id = ${userId}`);
  return user;
}

// 올바른 구현 (Parameterized Query)
async function getUserData(userId) {
  const user = await db.query('SELECT * FROM users WHERE id = $1', [userId]);
  return user;
}
```

### 4.2 코드 이해도와 위험 수준

```
이해도 높음  |████████████|  위험 낮음 - 유지보수 가능
이해도 중간  |████████    |  주의 필요 - 학습 후 수용
이해도 낮음  |████        |  위험 높음 - 반드시 학습 필요
이해 못함    |██          |  매우 위험 - 수용 금지

원칙: 설명할 수 없는 코드는 커밋하지 않는다
```

### 4.3 커밋 전 체크리스트

```
[ ] 코드의 의도를 한 문장으로 설명할 수 있는가?
[ ] 각 함수가 무엇을 하는지 이해하는가?
[ ] 보안 취약점이 없는가? (SQL Injection, XSS 등)
[ ] 에러 처리가 적절한가?
[ ] 기존 코드 스타일과 일관성이 있는가?
[ ] 테스트가 존재하고 통과하는가?
```

### 4.4 Claude Code에서의 검증 워크플로우

```bash
# 1. diff 확인
$ git diff

# 2. AI에게 위험 요소 질문
> 방금 생성한 코드에서 보안 관점으로 취약점이 있을 수 있는 곳을 알려줘.

# 3. 이해 안 되는 부분 질문
> 이 정규표현식이 어떤 패턴을 매칭하는지 설명해줘

# 4. 테스트 실행 후 커밋
> npm test 실행해줘
```

## 5. AI Pair Programming

### 5.1 Driver/Navigator 역할 분담

```
+----------------------------------------------------------------+
|  모드 A: AI = Driver, 사람 = Navigator                          |
|  사람: "인증 미들웨어 만들어" --> AI: [코드 작성]                |
|  사람: "에러 처리 추가해"     --> AI: [코드 수정]                |
|  적합: 보일러플레이트, 표준 패턴, 빠른 프로토타이핑              |
+----------------------------------------------------------------+
|  모드 B: 사람 = Driver, AI = Navigator                          |
|  사람: [핵심 로직 직접 작성]  --> AI: "null 체크 필요합니다"     |
|  사람: [수정]                 --> AI: "이 알고리즘은 O(n²)입니다" |
|  적합: 복잡한 비즈니스 로직, 알고리즘, 성능 최적화               |
+----------------------------------------------------------------+
```

### 5.2 효과적인 AI Pair Programming 패턴

```bash
# 패턴 1: 점진적 구체화
> "사용자 프로필 페이지를 만들어줘"           # 큰 그림
> "프로필 사진 업로드 기능을 추가해줘"         # 기능 추가
> "이미지 리사이징은 sharp 라이브러리 써줘"    # 구현 디테일

# 패턴 2: 샌드위치 방식 (사람-AI-사람)
# 사람: 인터페이스/타입 정의  -->  AI: 구현  -->  사람: 리뷰 및 수정

# 패턴 3: 탐색적 코딩
> "이 문제를 해결하는 방법 3가지를 장단점과 함께 제안해줘"
# 사람이 선택 후
> "2번 방법으로 구현해줘"
```

## 6. AI Code Review와 품질 관리

### 6.1 AI로 AI 생성 코드 리뷰하기

```bash
# Claude Code에서 리뷰 요청
> 방금 작성한 코드를 리뷰해줘:
> 1. 보안 취약점  2. 성능 문제  3. 에러 처리 누락
> 4. 타입 안전성  5. 테스트 커버리지 부족한 부분
```

### 6.2 자동화된 가드레일 구축

```
AI가 코드 생성
    |
    v
[린터(ESLint/Prettier)]      -- 스타일/문법 검증
    |
    v
[타입 검사(TypeScript)]      -- 타입 안전성 검증
    |
    v
[단위 테스트(Jest/Vitest)]   -- 기능 정확성 검증
    |
    v
[보안 스캔(Snyk/npm audit)]  -- 보안 취약점 검증
    |
    v
사람의 최종 리뷰
```

### 6.3 CI/CD에 통합하기

```yaml
# .github/workflows/ai-code-quality.yml
name: AI Code Quality Check
on: [push, pull_request]
jobs:
  quality-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run lint
      - run: npm run type-check
      - run: npm test
      - run: npm audit
```

AI가 생성했든 사람이 작성했든, **같은 품질 기준을 적용**해야 합니다.

## 7. AI를 쓸 때 vs 직접 코딩할 때

### 7.1 판단 매트릭스

```
            |      구현 복잡도 낮음      |     구현 복잡도 높음       |
 -----------+--------------------------+--------------------------+
 비즈니스    | AI + 사람 검토            | 사람이 직접 작성           |
 중요도 높음 | (보안 테스트 포함)         | (인증/결제 핵심 로직)      |
 -----------+--------------------------+--------------------------+
 비즈니스    | AI에게 맡기기             | AI + 가벼운 검토           |
 중요도 낮음 | (설정 파일, 보일러플레이트) | (내부 툴, 스크립트)        |
 -----------+--------------------------+--------------------------+
```

### 7.2 구체적 가이드라인

**AI에게 맡기세요** (보일러플레이트): 라우터 생성, 타입 정의, Storybook 스토리,
.gitignore, Docker 설정 파일 등

**모든 줄을 이해하세요** (핵심 비즈니스 로직): 결제 금액 계산, 권한 검증,
데이터 정합성 규칙, 재시도/롤백 로직 등

**추가 검증 필수** (보안 관련 코드): 입력 새니타이징(sanitizing), 인증/인가,
암호화, 파일 업로드, 외부 입력을 받는 엔드포인트 등

## 8. AI 친화적 프로젝트 구조

### 8.1 CLAUDE.md — AI에게 프로젝트를 설명하는 파일

Claude Code는 프로젝트 루트의 `CLAUDE.md`를 자동으로 읽어 컨텍스트를 이해합니다.

```markdown
# CLAUDE.md 예시

## 프로젝트 개요
이커머스 백엔드 API. Express.js + TypeScript + PostgreSQL.

## 디렉토리 구조
- src/routes/ - API 라우터
- src/services/ - 비즈니스 로직
- src/models/ - 데이터베이스 모델 (Prisma)
- tests/ - 테스트 파일 (Jest)

## 코드 컨벤션
- 함수명: camelCase, 파일명: kebab-case
- 에러 처리: AppError 클래스 사용
- API 응답: { success, data, error } 형태

## 빌드 & 테스트
- npm run dev / npm test / npm run build

## 중요한 규칙
- DB 쿼리는 Prisma ORM만 사용 (raw query 금지)
- 모든 라우트에 인증 미들웨어 필수
```

### 8.2 AI 도구별 프로젝트 설정 파일

| 도구 | 설정 파일 | 용도 |
|------|-----------|------|
| Claude Code | `CLAUDE.md` | 프로젝트 컨텍스트, 규칙, 빌드 명령어 |
| Cursor | `.cursorrules` | 코드 스타일, 프로젝트 규칙 |
| Kilo Code | `.kilocode/rules` | 프로젝트 규칙 및 컨텍스트 설정 |
| 범용 | `system-prompt.md` | AI 도구 공통 지시사항 |

### 8.3 AI 친화적 프로젝트 구조 체크리스트

```
[구조]  명확한 디렉토리 네이밍 / 관심사 분리 / 한 파일 한 역할
[문서]  CLAUDE.md 존재 / API 문서화 / 타입 정의 명확 / 환경 변수 설명
[테스트] 소스-테스트 파일 대응 / 실행 명령어 단순 / 픽스처 정리
[의존성] package.json scripts 정리 / 의존성 명확 선언
```

### 8.4 모노레포 vs 멀티레포: AI 관점

```
+----------------------------------------------------------------+
|  모노레포 (Monorepo)                                            |
|  장점: AI가 전체 컨텍스트 파악, 공유 코드 변경 추적 가능          |
|  단점: 컨텍스트 윈도우 제한, AI가 관련 없는 코드에 혼란           |
+----------------------------------------------------------------+
|  멀티레포 (Multi-repo)                                          |
|  장점: 각 레포가 작아 AI 이해 용이, 명확한 경계                  |
|  단점: 여러 레포 걸친 변경 어려움, 레포 간 영향 파악 불가         |
+----------------------------------------------------------------+
|  실용적 조언: AI 활용 시 모노레포가 일반적으로 유리.              |
|  단, 각 패키지에 개별 CLAUDE.md를 두어 영역 집중 안내.           |
+----------------------------------------------------------------+
```

## 9. 정리: AI 네이티브 개발의 핵심 원칙

```
+================================================================+
|              AI 네이티브 개발 5대 원칙                            |
|                                                                |
|  1. 신뢰하되 검증하라 (Trust but Verify)                        |
|     AI 코드를 수용하되, 반드시 이해하고 테스트하라                |
|                                                                |
|  2. 테스트가 안전망이다 (Tests are Your Safety Net)              |
|     AI가 코드를 작성하기 전에 테스트를 먼저 만들어라              |
|                                                                |
|  3. 프롬프트를 설계하라 (Design Your Prompts)                   |
|     좋은 프롬프트는 좋은 설계 문서와 같다                        |
|                                                                |
|  4. 점진적으로 진행하라 (Iterate Incrementally)                  |
|     한 번에 완벽한 결과를 기대하지 말고, 반복 정제하라            |
|                                                                |
|  5. AI의 한계를 알라 (Know AI's Limits)                         |
|     보안, 핵심 비즈니스 로직, 아키텍처 결정은 사람의 영역이다     |
|                                                                |
+================================================================+
```
