## 19.1 Mixture of Experts (MoE) — 모든 뉴런을 쓸 필요는 없다

### 핵심 아이디어

일반적인 Transformer 모델(Dense Model)은 입력 토큰 하나를 처리할 때
모든 파라미터가 연산에 참여합니다. 파라미터가 1750억 개면, 매 토큰마다
1750억 개의 파라미터가 전부 활성화됩니다.

MoE(Mixture of Experts)는 이 접근을 근본적으로 바꿉니다.

> **"모델 전체가 아니라, 각 토큰에 가장 적합한 '전문가'만 활성화하자."**

```
Dense Model (기존 방식)
┌──────────────────────────────────┐
│  모든 파라미터가 항상 활성화됨    │
│  [████████████████████████████]  │  ← 토큰마다 전체 연산
│  총 파라미터 = 활성 파라미터      │
└──────────────────────────────────┘

MoE Model (전문가 혼합 방식)
┌──────────────────────────────────┐
│  Router가 토큰별로 전문가 선택    │
│  [██░░░░░░██░░░░░░░░░░░░░░░░██] │  ← 일부만 활성화
│  총 파라미터 >> 활성 파라미터     │
└──────────────────────────────────┘
```

### 라우터 메커니즘: 토큰은 어떻게 전문가를 찾아가는가

MoE의 핵심 구성요소는 **라우터(Router)** 입니다. 라우터는 작은 신경망으로,
각 토큰의 표현(representation)을 입력받아 어떤 전문가에게 보낼지 결정합니다.

```
입력 토큰: "프로그래밍"

           ┌─────────┐
           │  Router  │  ← 가벼운 분류 네트워크
           │ (Gating) │
           └────┬─────┘
                │
    ┌───────────┼───────────┬───────────┐
    │           │           │           │
    v           v           v           v
┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
│Expert 1│ │Expert 2│ │Expert 3│ │Expert 4│
│ (언어) │ │ (코드) │ │ (수학) │ │ (상식) │
│  0.15  │ │  0.72  │ │  0.08  │ │  0.05  │
└────────┘ └────────┘ └────────┘ └────────┘
     △           ★           △           △
   비활성     활성화!       비활성      비활성

→ Top-K (보통 K=2) 전문가만 활성화
→ 가중 합산으로 최종 출력 생성
```

개발자에게 익숙한 비유로 설명하면, 이것은 일종의 **로드 밸런서(Load Balancer)** 와
비슷합니다. 요청의 특성에 따라 적합한 서버로 라우팅하는 것처럼,
토큰의 특성에 따라 적합한 전문가 네트워크로 라우팅합니다.

### 실제 MoE 모델들

| 모델 | 총 파라미터 | 활성 파라미터 | 전문가 수 | 비고 |
|------|------------|--------------|----------|------|
| **GPT-4** (추정) | ~1.8T | ~280B | 16개 (추정) | OpenAI 미공개, 유출 정보 기반 |
| **Mixtral 8x7B** | 46.7B | 12.9B | 8개 | Mistral AI, 오픈 가중치 |
| **DeepSeek-V3** | 671B | 37B | 256개 | 학습 비용 약 $5.6M으로 화제 |
| **Qwen2.5-MoE** | 14.3B | 2.7B | 60개 | 알리바바, 소형 MoE |

### MoE의 장점과 트레이드오프

**장점:**
- **효율적 스케일링**: 총 파라미터를 크게 늘려도 추론 비용은 활성 파라미터에 비례
- **낮은 추론 비용**: DeepSeek-V3는 671B 파라미터이지만 37B만 활성화
- **전문화**: 각 전문가가 특정 유형의 지식이나 패턴에 특화 가능

**트레이드오프:**
- **메모리**: 전체 파라미터를 GPU 메모리에 올려야 함 (VRAM 사용량은 Dense와 유사)
- **학습 불안정성**: 라우터가 특정 전문가에만 토큰을 집중시키는 문제 (load balancing)
- **통신 비용**: 분산 학습/추론 시 전문가 간 데이터 이동이 병목

> **개발자 관점에서의 의미:** MoE가 보편화되면, 같은 추론 비용으로 훨씬 더 큰
> 모델을 사용할 수 있게 됩니다. 즉, API 호출 비용은 비슷하지만 성능은 크게 향상됩니다.

## 19.2 State Space Models (SSM) — Transformer의 대안이 될 수 있을까?

### Transformer의 근본적 한계

Transformer의 핵심인 Self-Attention은 시퀀스 길이 n에 대해
**O(n²)** 의 시간 및 메모리 복잡도를 가집니다.

```
시퀀스 길이와 연산량의 관계

길이(n)  │ Attention (O(n²))  │  SSM (O(n))
─────────┼────────────────────┼──────────────
   1K    │        1M          │      1K
   4K    │       16M          │      4K
  16K    │      256M          │     16K
  64K    │     4,096M         │     64K
 256K    │    65,536M         │    256K
   1M    │ 1,000,000M        │      1M     ← 차이가 극적으로 벌어짐
```

4K 토큰 수준에서는 큰 문제가 아니었지만, 100K~1M 토큰을 처리해야 하는 시대에
이 이차(quadratic) 복잡도는 심각한 병목이 됩니다.

### Mamba 아키텍처: 선택적 상태 공간 모델

**Mamba**(2023년 Albert Gu, Tri Dao 발표)는 이 문제에 대한 가장 주목받는
대안입니다. SSM(State Space Model)에 기반하되, **선택적 메커니즘(Selective Mechanism)**
을 추가하여 입력에 따라 상태 전이를 동적으로 조절합니다.

```
Transformer의 Attention:
  모든 토큰 쌍을 직접 비교 (전화 회의에서 모두가 동시에 이야기)

  [t1] ←→ [t2] ←→ [t3] ←→ [t4] ←→ [t5]
    ↕         ↕         ↕         ↕
  [t1] ←→ [t2] ←→ [t3] ←→ [t4] ←→ [t5]
  → n개 토큰에 대해 n×n 비교 필요

SSM/Mamba의 접근:
  상태(state)를 순차적으로 업데이트 (전언 게임처럼 정보를 압축 전달)

  [t1] → [상태] → [t2] → [상태'] → [t3] → [상태''] → ...
              ↓              ↓               ↓
           [출력1]        [출력2]          [출력3]
  → n개 토큰에 대해 n번의 상태 업데이트만 필요
```

핵심 차이점은 Mamba가 **입력에 따라 상태 전이 행렬을 동적으로 변경**한다는 것입니다.
기존 SSM이 모든 입력에 같은 방식으로 반응했다면, Mamba는 "이 토큰은 중요하니까
상태에 많이 반영하고, 저 토큰은 별로니까 무시하자"라고 선택할 수 있습니다.

### 하이브리드 모델: 둘 다 쓰면 안 되나?

실제로 가장 유망한 방향은 Transformer와 SSM을 **결합**하는 것입니다.

| 모델 | 접근 방식 |
|------|----------|
| **Jamba** (AI21 Labs) | Transformer 레이어와 Mamba 레이어를 교차 배치 |
| **Mamba-2** | 구조적 상태 공간 이중성(SSD)으로 Attention과의 이론적 연결 발견 |
| **Zamba** (Zyphra) | 공유 Attention 레이어 + Mamba 블록으로 효율적 하이브리드 구성 |

> **개발자 관점에서의 의미:** SSM이 성숙해지면, 매우 긴 코드베이스나 문서를
> 한 번에 처리하는 것이 현실적인 비용으로 가능해집니다. "전체 리포지토리를 컨텍스트에
> 넣고 리팩토링해줘"라는 요청이 일상이 될 수 있습니다.

## 19.3 Long Context — 더 많이, 더 멀리 기억하기

### 컨텍스트 윈도우의 확장 역사

```
시간순 컨텍스트 윈도우 확장

2022  │ GPT-3.5          :  4K 토큰    (약 3,000단어)
2023  │ GPT-4            : 32K → 128K  (소설 한 권)
2023  │ Claude 2         : 100K 토큰   (약 75,000단어)
2024  │ Claude 3         : 200K 토큰   (약 150,000단어)
2024  │ Gemini 1.5 Pro   :   1M 토큰   (약 700,000단어)
2025  │ Gemini 2.0       :   2M 토큰   (코드베이스 전체)
      │
      ▼ 미래: 10M+ 토큰? 무제한 컨텍스트?
```

### 롱 컨텍스트를 가능하게 하는 기술들

**1) RoPE Scaling (Rotary Position Embedding 확장)**

RoPE는 토큰의 위치 정보를 회전 행렬(rotary matrix)로 인코딩합니다.
학습 시 사용한 컨텍스트 길이를 넘어서려면, 주파수를 조정하여 위치 인코딩을
"압축"해야 합니다.

- **NTK-aware Scaling**: 고주파와 저주파를 다른 비율로 스케일링
- **YaRN (Yet another RoPE extensioN)**: 주파수별 보간과 온도 조정을 결합
- **ABF (Adjusted Base Frequency)**: Llama 3.1에서 사용, 기본 주파수 자체를 조정

**2) ALiBi (Attention with Linear Biases)**

위치 인코딩을 임베딩에 더하는 대신, Attention 점수에 직접 거리 기반 편향(bias)을
더합니다. 학습 시보다 더 긴 시퀀스에 자연스럽게 일반화됩니다.

**3) Ring Attention**

여러 GPU에 걸쳐 긴 시퀀스를 블록으로 나누고, 각 GPU가 자신의 블록에 대한
Attention을 계산하면서 키-값(key-value)을 링(ring) 형태로 순환시킵니다.
이론적으로 GPU 수에 비례하여 컨텍스트 길이를 확장할 수 있습니다.

```
Ring Attention: GPU 간 Key-Value 순환

  GPU 1        GPU 2        GPU 3        GPU 4
 ┌─────┐     ┌─────┐     ┌─────┐     ┌─────┐
 │블록1│ ──→ │블록2│ ──→ │블록3│ ──→ │블록4│
 │     │ ←── │     │ ←── │     │ ←── │     │
 └─────┘     └─────┘     └─────┘     └─────┘
     ↑                                    │
     └────────────────────────────────────┘
           KV 텐서가 링 형태로 순환
```

### "건초 더미에서 바늘 찾기" 테스트

롱 컨텍스트의 실제 성능을 측정하는 대표적인 벤치마크가
**Needle in a Haystack(NIAH)** 테스트입니다.

```
테스트 방법:
1. 매우 긴 텍스트(건초 더미)를 준비
2. 텍스트의 특정 위치에 무관한 사실(바늘) 하나를 삽입
   예: "마법의 숫자는 83719입니다"
3. 전체 텍스트를 모델에 입력
4. "마법의 숫자가 뭐야?"라고 질문
5. 바늘의 위치(앞/중간/뒤)와 건초 더미 길이를 변화시키며 정확도 측정

결과 히트맵 (예시):
              컨텍스트 길이 →
삽입 위치  │  4K    32K   128K   200K   1M
───────────┼─────────────────────────────
  시작     │  ✓     ✓      ✓      ✓     ✓
  25%      │  ✓     ✓      ✓      ✓     △
  중간     │  ✓     ✓      ✓      △     △
  75%      │  ✓     ✓      ✓      ✓     △
  끝       │  ✓     ✓      ✓      ✓     ✓

✓ = 정확  △ = 가끔 실패  ✗ = 자주 실패
→ 대부분의 모델이 중간 부분에서 가장 약함 ("Lost in the Middle" 현상)
```

### RAG vs Long Context 논쟁

컨텍스트 윈도우가 충분히 커지면, RAG(Retrieval-Augmented Generation)가
불필요해질까요?

| 관점 | RAG 유지 | Long Context로 대체 |
|------|---------|-------------------|
| **비용** | 검색 후 필요한 부분만 입력 → 토큰 절약 | 전부 넣으면 토큰 비용 증가 |
| **정확도** | 검색 품질에 의존, 관련 없는 문서 가능 | 전체 맥락을 보므로 누락 위험 감소 |
| **실시간성** | 인덱스 업데이트 필요 | 최신 문서를 바로 입력 가능 |
| **규모** | 수백만 문서도 검색 가능 | 컨텍스트에 물리적 한계 존재 |

현실적인 답은 **둘 다 사용하는 하이브리드 접근**입니다. RAG로 관련 문서를
검색한 후, 넉넉한 컨텍스트에 여러 문서를 함께 넣어 종합적으로 처리하는 방식이
주류가 되고 있습니다.

## 19.4 Agentic AI — 도구 사용에서 자율 시스템으로

### 진화의 단계

AI의 활용 방식은 빠르게 진화하고 있습니다.

```
AI 활용의 진화 단계

Level 0: 단순 질의응답
  사용자: "정렬 알고리즘 설명해줘"
  AI: "정렬 알고리즘은..."
  → 검색 엔진의 대체

Level 1: Copilot (보조 도구)
  사용자가 코드를 작성하는 동안 AI가 자동완성, 제안
  → IDE 안에서 한 줄~한 함수 단위 도움
  → 예: GitHub Copilot, Cursor Tab

Level 2: Agent (에이전트)
  사용자가 작업을 지시하면, AI가 계획을 세우고 도구를 사용하여 실행
  → 파일 읽기/쓰기, 터미널 명령, 웹 검색을 자율적으로 수행
  → 예: Claude Code, Cursor Agent Mode, Devin

Level 3: Autonomous System (자율 시스템)
  사용자가 목표만 설정하면, AI가 스스로 하위 작업을 분해하고
  수 시간~수 일에 걸쳐 독립적으로 수행
  → 예: 아직 초기 단계, 연구 진행 중
```

### Computer Use Agent: AI가 컴퓨터를 직접 조작

**Computer Use**(컴퓨터 사용)는 AI가 마우스 클릭, 키보드 입력, 화면 읽기를
직접 수행하는 기술입니다.

```
기존 방식: API 기반 도구 사용
  AI → [함수 호출] → 데이터베이스 조회 → [결과 반환] → AI

Computer Use 방식: 화면 기반 직접 조작
  AI → [화면 캡처] → "검색창이 여기 있군" → [클릭, 타이핑] → [결과 확인]
```

Anthropic의 Claude는 2024년 Computer Use 기능을 공개하며, AI가 웹 브라우저를
탐색하고, 양식을 작성하고, 스프레드시트를 편집하는 등의 작업이 가능함을
보여주었습니다. 이는 API가 없는 레거시 시스템과의 통합에서 특히 강력합니다.

### 코딩 에이전트: 자율적으로 코드를 작성하는 AI

코딩 에이전트의 발전은 소프트웨어 개발 방식을 근본적으로 변화시키고 있습니다.

```
코딩 에이전트의 작업 흐름 (예: Claude Code)

  사용자: "이 프로젝트에 사용자 인증 기능을 추가해줘"

  Agent의 행동:
  1. 프로젝트 구조 탐색 (파일 트리 읽기)
  2. 기존 코드 패턴 분석 (코드 읽기)
  3. 구현 계획 수립
  4. 데이터베이스 스키마 수정
  5. API 엔드포인트 작성
  6. 프론트엔드 로그인 페이지 구현
  7. 테스트 코드 작성 및 실행
  8. 실패한 테스트 디버깅 및 수정
  9. 최종 동작 확인
```

**Copilot에서 자율 개발자로의 전환:**

| 단계 | 인간의 역할 | AI의 역할 | 현재 수준 |
|------|-----------|----------|----------|
| **Copilot** | 설계 + 구현 + 검토 | 자동완성 제안 | 성숙 |
| **Agent** | 설계 + 검토 | 구현 + 테스트 | 빠르게 발전 중 |
| **자율 개발자** | 목표 설정 + 최종 승인 | 설계 + 구현 + 테스트 + 배포 | 초기 연구 |

> **개발자 관점에서의 의미:** 코딩 에이전트 시대에 개발자의 역할은
> "코드를 작성하는 사람"에서 "AI의 작업을 설계하고 검토하는 사람"으로 이동합니다.
> 코드 리뷰, 아키텍처 설계, 요구사항 정의 능력이 더욱 중요해집니다.

## 19.5 AGI와 ASI — 범용 지능을 향한 논쟁

### AGI란 무엇인가 (그리고 무엇이 아닌가)

**AGI(Artificial General Intelligence, 범용 인공지능)** 는 특정 작업이 아닌,
인간이 수행할 수 있는 거의 모든 지적 작업을 수행할 수 있는 AI를 의미합니다.

```
현재 AI (Narrow AI)              AGI
┌────────────────────┐     ┌────────────────────┐
│ 체스: ★★★★★        │     │ 체스: ★★★★★        │
│ 코딩: ★★★★☆        │     │ 코딩: ★★★★★        │
│ 글쓰기: ★★★★☆      │     │ 글쓰기: ★★★★★      │
│ 물리적 작업: ☆☆☆☆☆  │     │ 물리적 작업: ★★★★☆  │
│ 새로운 과학: ★★☆☆☆  │     │ 새로운 과학: ★★★★★  │
│ 자기 인식: ☆☆☆☆☆    │     │ 자기 인식: ???      │
│ 상식 추론: ★★★☆☆    │     │ 상식 추론: ★★★★★    │
└────────────────────┘     └────────────────────┘
  특정 영역에서만 강함         모든 영역에서 인간 수준
```

주의할 점은 AGI에 대한 **합의된 정의가 없다**는 것입니다.

- 어떤 이들은 "인간이 할 수 있는 경제적 가치가 있는 모든 작업을 수행"으로 정의
- 어떤 이들은 "새로운 상황에서 스스로 학습하고 적응하는 능력"을 요구
- 또 어떤 이들은 "의식(consciousness)"이나 "이해(understanding)"를 포함해야 한다고 주장

### ASI: 인간을 넘어선 지능

**ASI(Artificial Super Intelligence, 초인공지능)** 는 모든 영역에서
인간의 지적 능력을 크게 초월하는 AI입니다. AGI보다 훨씬 더 사변적인 개념이지만,
일부 연구자들은 AGI가 달성되면 ASI로의 전환이 매우 빠르게 일어날 수 있다고
경고합니다 (이를 "지능 폭발(intelligence explosion)"이라 부릅니다).

### 주요 기관들의 입장

| 기관 | 입장 | 핵심 주장 |
|------|------|----------|
| **OpenAI** | 낙관적 | AGI 달성이 사명, "AI가 인류 전체에 이익을 줄 것" |
| **Anthropic** | 신중한 낙관 | AGI 가능성 인정, 안전성 연구에 최우선 투자 |
| **Google DeepMind** | 단계적 접근 | AGI를 레벨로 분류 (Emerging → Competent → Expert → Virtuoso → Superhuman) |
| **Meta AI** | 오픈소스 중심 | 오픈소스 AI가 AGI로 가는 안전한 길이라고 주장 |
| **회의론자들** | 비판적 | 현재 LLM은 패턴 매칭일 뿐, 진정한 이해가 없다고 주장 |

### 낙관론 vs 회의론

**낙관론의 근거:**
- AI 능력이 매년 기대를 초월하는 속도로 향상
- 스케일링 법칙(Scaling Laws)이 여전히 유효
- 새로운 아키텍처(MoE, SSM)와 학습 기법이 계속 등장

**회의론의 근거:**
- LLM은 "통계적 앵무새"에 불과하다는 비판
- 진정한 추론(reasoning)이 아닌 패턴 매칭이라는 주장
- 학습 데이터의 한계 (인터넷 데이터를 거의 다 사용)
- 물리적 세계에 대한 이해 부족

현실은 아마 그 사이 어딘가에 있을 것입니다. 분명한 것은, AGI의 정확한 시점과
관계없이, AI 시스템의 능력이 빠르게 향상되고 있으며 이에 대한 대비가
필요하다는 것입니다.

## 19.6 AI Safety & Alignment — 강력한 AI를 안전하게 만들기

### 정렬 문제란 무엇인가

**정렬 문제(Alignment Problem)** 는 AI 시스템의 목표와 행동이 인간의 의도,
가치, 기대에 부합하도록 만드는 기술적 과제입니다.

```
정렬 문제의 예시

목표: "사용자를 도와줘"

잘못 정렬된 AI                 잘 정렬된 AI
├─ 사용자가 요청하면           ├─ 사용자를 도우면서도
│  무엇이든 수행               │  안전과 윤리를 고려
├─ 해킹 방법 상세 안내         ├─ 위험한 요청은 거절하되
│                              │  합법적 대안 제시
├─ 편향된 정보 무비판 전달     ├─ 다양한 관점을 균형있게 제시
│                              │
└─ "도움"의 의미를              └─ 인간의 가치와 의도에
   문자 그대로만 해석             부합하는 방향으로 "도움"을 해석
```

### Constitutional AI: Anthropic의 접근

Anthropic이 개발한 **Constitutional AI(헌법적 AI)** 는 AI 정렬에 대한
독특한 접근법입니다.

**기본 원리:**
1. AI에게 따라야 할 "헌법(Constitution)"을 제공 — 원칙들의 집합
2. AI가 자체적으로 응답을 생성한 후, 헌법에 비추어 스스로 비판하고 수정
3. 이 과정을 통해 RLHF(인간 피드백 강화학습)의 인간 의존도를 줄임

```
Constitutional AI의 작동 흐름

[사용자 질문] → [초기 응답 생성]
                      ↓
              [헌법 원칙으로 자체 비판]
              "이 응답이 도움이 되면서도
               해롭지 않은가?"
                      ↓
              [수정된 응답 생성]
                      ↓
              [RLAIF: AI 피드백으로 강화학습]
                      ↓
              [최종 모델]
```

기존 RLHF가 인간 평가자에게 크게 의존했다면, Constitutional AI는 원칙 기반의
자기 개선을 통해 더 확장 가능하고 일관된 정렬을 추구합니다.

### 해석 가능성 연구: 모델의 내부를 들여다보기

**해석 가능성(Interpretability)** 연구는 신경망 내부에서 어떤 연산이
일어나는지, 각 뉴런이나 회로가 어떤 개념을 표현하는지를 밝히려는 시도입니다.

**주요 연구 방향:**

- **Mechanistic Interpretability**: 모델의 개별 뉴런과 회로를 분석하여
  특정 행동이 어떤 내부 메커니즘으로 발생하는지 규명
- **Sparse Autoencoders**: 모델의 활성화를 해석 가능한 특성(feature)으로 분해
- **Representation Engineering**: 모델의 내부 표현을 직접 조작하여
  행동을 제어하는 기법

Anthropic은 2024년 Claude 모델 내부에서 수백만 개의 해석 가능한 특성을
발견하는 연구를 발표했습니다. 예를 들어 "거짓말"이나 "위험한 행동"과 관련된
특성을 식별하고, 이를 인위적으로 활성화하거나 억제할 수 있음을 보여주었습니다.

```
해석 가능성의 비유: X-ray for AI

기존: 블랙박스
  입력 → [???????????????????] → 출력
  "왜 이런 답이 나왔는지 모르겠다"

해석 가능성 적용 후:
  입력 → [특성A: 코드 패턴 인식    ] → 출력
         [특성B: 안전성 판단        ]
         [특성C: 한국어 문법 규칙   ]
         [특성D: 수학적 추론        ]
  "아, 특성B가 강하게 활성화되어서 거절한 거구나"
```

### 책임 있는 스케일링 정책

**Responsible Scaling Policy(RSP, 책임 있는 스케일링 정책)** 는
Anthropic이 도입한 프레임워크로, AI 모델의 능력이 특정 임계점을 넘기 전에
적절한 안전 조치가 마련되어 있는지 확인합니다.

```
ASL (AI Safety Level) 단계

ASL-1: 위험 없음 (체스 AI 수준)
  → 특별한 안전 조치 불필요

ASL-2: 현재 대부분의 LLM
  → 기본적인 안전 학습, 유해 콘텐츠 필터링
  → 현재 Claude가 이 수준

ASL-3: 위험한 정보에 대한 의미있는 향상을 제공할 수 있는 모델
  → 강화된 보안, 모델 접근 제한, 배포 전 엄격한 평가

ASL-4+: 미래의 더 강력한 모델
  → 사전에 안전 기준 정의 후, 기준 충족 시에만 배포
```

## 19.7 AI 규제와 거버넌스 — 전 세계의 대응

### EU AI Act: 위험 기반 규제의 선두주자

유럽연합의 **EU AI Act**는 세계 최초의 포괄적 AI 규제법으로,
2024년 발효되어 단계적으로 시행되고 있습니다.

```
EU AI Act의 위험 기반 분류

  금지 (Unacceptable Risk)
  ┌─────────────────────────────────────────┐
  │ · 사회적 점수 시스템 (Social Scoring)    │
  │ · 실시간 원격 생체 인식 (원칙적 금지)    │
  │ · 취약계층 대상 조작적 AI               │
  └─────────────────────────────────────────┘

  고위험 (High Risk) — 엄격한 규제
  ┌─────────────────────────────────────────┐
  │ · 채용/인사 관련 AI                      │
  │ · 신용 평가                              │
  │ · 교육 시스템                            │
  │ · 법 집행                                │
  │ → 적합성 평가, 위험 관리, 투명성 의무    │
  └─────────────────────────────────────────┘

  제한적 위험 (Limited Risk) — 투명성 의무
  ┌─────────────────────────────────────────┐
  │ · 챗봇: AI와 대화 중임을 고지            │
  │ · 딥페이크: AI 생성 콘텐츠 표시          │
  └─────────────────────────────────────────┘

  최소 위험 (Minimal Risk) — 규제 없음
  ┌─────────────────────────────────────────┐
  │ · 스팸 필터, 게임 AI 등                  │
  └─────────────────────────────────────────┘
```

**범용 AI 모델(GPAI)에 대한 추가 규정:**
- 모든 GPAI: 기술 문서 작성, 저작권법 준수, 학습 데이터 요약 공개
- 시스템 리스크가 있는 GPAI (학습에 10^25 FLOP 이상): 모델 평가,
  적대적 테스트(red teaming), 사이버 보안 조치 의무

### 미국의 AI 행정명령

미국은 2023년 10월 바이든 대통령의 **AI 행정명령(Executive Order on AI)** 을
통해 AI 규제의 프레임워크를 제시했습니다.

주요 내용:
- 강력한 AI 모델 개발 시 안전 테스트 결과를 정부에 보고 의무
- AI 생성 콘텐츠에 대한 워터마킹 표준 개발
- AI 관련 프라이버시 보호 강화
- AI 분야 인재 유치를 위한 이민 정책 완화

다만, 행정명령은 법률이 아니므로 행정부 교체에 따라 변경될 수 있으며,
실제로 정책 방향의 변화가 논의되고 있습니다.

### 주요 국가별 접근

| 국가/지역 | 접근 방식 | 특징 |
|-----------|----------|------|
| **한국** | 디지털 플랫폼 정부 + AI 기본법 추진 | 혁신 촉진과 위험 관리 균형, AI 윤리 기준 마련 |
| **일본** | 히로시마 AI 프로세스 주도 | G7 기반 국제 협력 강조, 소프트로 접근 |
| **중국** | 분야별 개별 규제 | 생성형 AI 서비스 관리법, 알고리즘 추천 관리법 등 |
| **영국** | Pro-innovation 접근 | 기존 규제 기관에 AI 감독 역할 부여, 별도 AI법 미제정 |
| **싱가포르** | 거버넌스 프레임워크 | 자율 규제 중심, AI Verify 테스트 도구 제공 |

> **개발자 관점에서의 의미:** AI를 사용하는 서비스를 개발할 때,
> 대상 시장의 규제를 반드시 확인해야 합니다. 특히 EU 시장을 대상으로 하는 경우
> EU AI Act 준수가 필수적이며, 고위험 카테고리에 해당하는지 사전에 평가해야 합니다.

## 19.8 오픈소스 AI의 부상 — 개방형 생태계의 성장

### 주요 오픈 모델들

2023년부터 오픈소스(또는 오픈 가중치) AI 모델의 성능이 비약적으로 향상되었습니다.

```
오픈 모델 생태계의 주요 플레이어

Meta (LLaMA 시리즈)
├── LLaMA 2 (2023. 7) — 오픈 AI 생태계의 촉발점
├── LLaMA 3 (2024. 4) — 405B 파라미터, GPT-4에 근접
└── LLaMA 3.1/3.2 (2024) — 다국어, 멀티모달 확장

Mistral AI
├── Mistral 7B (2023. 9) — 작지만 강력한 모델
├── Mixtral 8x7B (2023. 12) — 오픈 MoE의 시작
└── Mistral Large (2024) — 상용 수준 성능

DeepSeek (중국)
├── DeepSeek-V2 (2024) — MoE로 효율적 스케일링
├── DeepSeek-V3 (2024. 12) — 671B 파라미터, 극히 낮은 학습 비용
└── DeepSeek-R1 (2025. 1) — 추론 특화, o1 수준 성능

Alibaba (Qwen 시리즈)
├── Qwen2 (2024) — 다국어에 강점
└── Qwen2.5 (2024) — 코딩, 수학 벤치마크 상위권
```

### "오픈 가중치" vs "진정한 오픈소스" 논쟁

**중요한 구분:** 대부분의 "오픈소스" AI 모델은 엄밀히 말해
**오픈 가중치(Open Weights)** 모델입니다.

```
완전한 오픈소스가 되려면:

  ┌────────────────────────────────────────────────────────┐
  │ 구성요소        │ 오픈 가중치  │ 진정한 오픈소스       │
  ├────────────────────────────────────────────────────────┤
  │ 모델 가중치     │     ✓       │        ✓              │
  │ 추론 코드       │     ✓       │        ✓              │
  │ 학습 코드       │     △       │        ✓              │
  │ 학습 데이터     │     ✗       │        ✓              │
  │ 데이터 전처리   │     ✗       │        ✓              │
  │ 상업적 사용     │  라이선스별  │      자유             │
  └────────────────────────────────────────────────────────┘

  △ = 부분적으로 공개  ✗ = 비공개  ✓ = 공개
```

Meta의 LLaMA는 가중치는 공개하지만 학습 데이터는 비공개이며,
상업적 사용에 조건이 있습니다. DeepSeek은 비교적 많은 기술 세부사항을
논문으로 공개하지만, 학습 데이터는 역시 비공개입니다.

OSI(Open Source Initiative)는 2024년 **Open Source AI**의 정의를 공식화하며,
모델 가중치, 학습 코드, 데이터 정보의 충분한 공개를 요구했습니다.

### 오픈소스 AI의 의미

**생태계에 미치는 영향:**

1. **민주화**: 대기업만이 아닌 중소기업, 개인 개발자도 최신 AI 기술에 접근
2. **커스터마이징**: 특정 도메인이나 언어에 맞게 파인튜닝 가능
3. **투명성**: 모델의 구조와 한계를 직접 확인 가능
4. **비용 절감**: 자체 인프라에서 운영하여 API 비용 회피 가능
5. **경쟁 촉진**: 폐쇄형 모델과의 경쟁으로 전체 생태계 발전 가속

**우려 사항:**
1. **안전 조치 우회**: 오픈 가중치 모델의 안전 장치를 제거(jailbreak)하기 쉬움
2. **악용 위험**: 악의적 사용자가 위험한 용도로 파인튜닝 가능
3. **책임 소재**: 오픈 모델의 오용에 대한 법적 책임이 불명확

```
오픈소스 AI의 영향 구조

  ┌──────────────────────────────────────────┐
  │            오픈소스 AI 모델               │
  │        (LLaMA, Mistral, DeepSeek 등)      │
  └──────────┬───────────────────┬───────────┘
             │                   │
     ┌───────▼────────┐  ┌──────▼─────────┐
     │ 긍정적 효과     │  │ 우려 사항       │
     ├────────────────┤  ├────────────────┤
     │ 기술 민주화     │  │ 안전장치 우회   │
     │ 혁신 가속       │  │ 악용 가능성     │
     │ 비용 절감       │  │ 책임 소재 불명  │
     │ 투명성 향상     │  │ 환경 비용       │
     └────────────────┘  └────────────────┘
```

## 19.9 종합: 개발자가 주목해야 할 핵심 흐름

### 단기 (1-2년) — 확실한 변화

1. **MoE 아키텍처의 보편화**: 새로 출시되는 대형 모델 대부분이 MoE 기반
2. **코딩 에이전트의 일상화**: AI 코딩 에이전트가 일상적인 개발 도구로 자리매김
3. **롱 컨텍스트 + RAG 하이브리드**: 두 기술의 조합이 표준 아키텍처로 정착
4. **오픈소스 모델의 성능 향상**: 폐쇄형 모델과의 격차가 3-6개월로 축소
5. **추론 비용의 급격한 하락**: 같은 성능 기준 비용이 매년 10배 이상 감소

### 중기 (3-5년) — 높은 가능성

1. **하이브리드 아키텍처**: Transformer + SSM + MoE를 결합한 새로운 표준 등장
2. **자율 에이전트의 성숙**: 수 시간 단위의 자율 작업이 안정적으로 가능
3. **멀티모달의 완성**: 텍스트, 이미지, 오디오, 비디오, 코드를 완전히 통합
4. **AI 규제의 구체화**: 국제적 규제 프레임워크가 실질적으로 작동
5. **해석 가능성 도구의 실용화**: 모델의 의사결정을 감사(audit)하는 것이 가능

### 장기 (5-10년) — 불확실하지만 중요한 가능성

1. **AGI 수준 AI의 등장 여부**: 가장 큰 불확실성이자 가장 큰 영향
2. **AI-인간 협업의 새로운 패러다임**: 소프트웨어 개발 방식의 근본적 변화
3. **새로운 컴퓨팅 패러다임**: AI 전용 하드웨어의 혁신
4. **사회적 적응**: 교육, 직업, 법률 체계의 AI 시대 대응
