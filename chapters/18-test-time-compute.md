## 1. 패러다임의 전환: 추론 시간에 더 많은 연산을 투입하다

### 1.1 훈련 연산 vs 추론 연산의 트레이드오프

2024년 이전까지 AI 성능 향상의 공식은 단순했습니다. "더 큰 모델을 더 많은 데이터로
더 오래 훈련시켜라." 이것이 훈련 스케일링 법칙(Training Scaling Law)이었습니다.

```
기존 패러다임:  [ 거대한 훈련 비용 ] --> [ 고정된 모델 ] --> 빠른 응답
               수천만 달러, 수개월       추론 시 연산 최소화

새로운 패러다임: [ 훈련된 모델 ] --> [ 추론 시 추가 연산 ] --> 더 나은 답
                                  "생각하는 시간"을 부여
```

개발자에게 익숙한 비유로, 기존 방식은 컴파일 시간(훈련)에 모든 최적화를 수행하는
AOT 컴파일이었고, 새로운 방식은 런타임에도 최적화를 수행하는 JIT 컴파일과 유사합니다.

### 1.2 "더 오래 생각하면 더 잘 답한다"

사람도 복잡한 문제에는 시간을 들여 생각합니다. 추론 시간 컴퓨팅도 동일한 원리입니다.

| 질문 유형 | 필요한 추론 수준 | 권장 모드 |
|-----------|-----------------|-----------|
| 사실 확인, 간단한 변환 | 낮음 | 일반 모드 (Fast) |
| 코드 리뷰, 논리적 분석 | 중간 | 일반 모드 또는 가벼운 추론 |
| 수학 증명, 복잡한 아키텍처 설계 | 높음 | 확장된 사고 (Extended Thinking) |
| 다단계 추론, 경쟁 프로그래밍 | 매우 높음 | 추론 특화 모델 (최대 예산) |

## 2. 연쇄 사고의 확장 (Chain-of-Thought at Scale)

### 2.1 단순 CoT에서 확장된 추론까지

2022년 Google의 Jason Wei 등이 발표한 연쇄 사고(Chain-of-Thought) 프롬프팅은
"단계별로 생각해 보세요(Let's think step by step)"라는 지시만으로
모델의 추론 성능을 크게 향상시켰습니다. 이것이 3세대에 걸쳐 진화했습니다.

| 세대 | 방식 | 추론 깊이 | 예시 |
|------|------|-----------|------|
| 1세대 | 직접 답변 (Direct Answer) | 없음 | GPT-3 기본 응답 |
| 2세대 | 프롬프트 유도 CoT | 수십 토큰 | "Let's think step by step" |
| 3세대 | 내재화된 확장 추론 | 수백~수만 토큰 | o1, Claude Extended Thinking, DeepSeek-R1 |

3세대에서는 사용자가 "단계별로"라고 지시하지 않아도 모델이 스스로 깊이 사고하며,
자기 검증, 역추적, 대안 탐색까지 수행합니다.

### 2.2 왜 풀이 과정을 보여주면 정확도가 올라가는가

LLM은 본질적으로 다음 토큰 예측기(next-token predictor)입니다.
"풀이 과정 없이 바로 정답만" 생성하면, 단 하나의 토큰으로 정답을 맞혀야 합니다.
이는 개발자에게 "디버깅 없이 버그 원인을 한 단어로 말하라"고 요구하는 것과 같습니다.

```
직접 답변:  입력 --> [블랙박스] --> 정답 토큰 1개

CoT 방식:   입력 --> [중간 추론 토큰들] --> [중간 추론 토큰들] --> 정답
                     각 단계가 다음        이전 단계를 컨텍스트로
                     단계의 맥락 제공       활용하여 정확한 추론
```

핵심 원리: 중간 추론 토큰들이 **작업 기억(working memory)** 역할을 수행합니다.
모델의 파라미터만으로 풀 수 없는 문제도, 추론 과정을 컨텍스트에 기록하면서
단계적으로 해결할 수 있게 됩니다.

## 3. Claude의 확장된 사고 (Extended Thinking)

### 3.1 작동 방식

Claude의 확장된 사고는 최종 응답 전에 내부적으로 긴 사고 과정을 거치는 기능입니다.

```
일반 모드:      [사용자 메시지] --> [응답 생성] --> [최종 응답]

Extended Thinking: [사용자 메시지] --> [thinking 블록] --> [응답 생성] --> [최종 응답]
                                      내부 추론 수행       추론 결과 바탕으로
                                      수백~수만 토큰       정제된 답변 생성
```

API에서는 다음과 같이 사용합니다.

```python
import anthropic

client = anthropic.Anthropic()
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    max_tokens=16000,
    thinking={
        "type": "enabled",
        "budget_tokens": 10000  # 사고에 사용할 최대 토큰 수
    },
    messages=[{
        "role": "user",
        "content": "이 분산 시스템 설계의 경쟁 조건을 모두 찾아주세요."
    }]
)

# 응답에는 thinking 블록과 text 블록이 포함됨
for block in response.content:
    if block.type == "thinking":
        print(f"[사고 과정] {block.thinking}")
    elif block.type == "text":
        print(f"[최종 답변] {block.text}")
```

### 3.2 사고 예산 (Thinking Budget): 모델이 얼마나 생각할지 제어하기

`budget_tokens`는 사고에 사용할 토큰 수의 **상한**입니다. 간단한 문제에는
예산을 다 쓰지 않고 조기에 마칩니다. CI/CD의 timeout 설정과 같은 개념입니다.

```
budget_tokens = 1,024   --> 간단한 정리, 빠른 판단
budget_tokens = 10,000  --> 중간 수준의 분석과 추론
budget_tokens = 32,000  --> 깊은 분석, 복잡한 문제 해결
budget_tokens = 128,000 --> 최대 수준의 사고 (고난도 문제)
```

### 3.3 언제 확장된 사고를 사용할 것인가

| 사용 사례 | 권장 모드 | 이유 |
|-----------|-----------|------|
| 간단한 질의응답, 번역 | 일반 모드 | 추가 추론 불필요, 비용 절약 |
| 텍스트 요약, 간단한 코드 생성 | 일반 모드 | 충분히 잘 수행됨 |
| 복잡한 코드 디버깅 | Extended Thinking | 여러 실행 경로 추적 필요 |
| 수학/논리 문제 풀이 | Extended Thinking | 단계적 추론이 정확도를 크게 향상 |
| 시스템 아키텍처 설계 | Extended Thinking | 트레이드오프 분석 필요 |

## 4. OpenAI o1 / o3 시리즈

### 4.1 추론 특화 모델의 등장

OpenAI의 o1(2024년 9월)과 o3(2025년 초)는 추론 시간 컴퓨팅을
모델 아키텍처와 훈련에 본격적으로 내재화한 모델입니다.

```
일반 모델 (GPT-4 등):
  프롬프트 --> [단일 순방향 패스] --> 응답 (고정된 연산량)

o1/o3 추론 모델:
  프롬프트 --> [내부 CoT 생성] --> [자기 검증] --> [재시도] --> 응답
              (가변적 연산량)    (답 검증)      (필요시 반복)
```

### 4.2 숨겨진 내부 추론 (Hidden Chain of Thought)

o1/o3의 특징적인 설계 결정은 내부 사고 과정을 사용자에게 **공개하지 않는다**는
점입니다. Claude Extended Thinking이 전체 사고 과정을 노출할 수 있는 것과 대조적으로,
o1/o3는 요약(summary)만 제공합니다.

### 4.3 벤치마크 성능 비교

| 벤치마크 | GPT-4o | o1 | o3 | 측정 항목 |
|----------|--------|-----|-----|-----------|
| AIME 2024 (수학) | 9.3% | 74.4% | 96.7% | 정답률 |
| GPQA Diamond (과학) | 49.9% | 77.3% | 87.7% | 정답률 |
| Codeforces (코딩) | 11th %ile | 89th %ile | 99th %ile | 백분위 |
| MATH-500 | 74.6% | 94.8% | 96.7% | 정답률 |
| SWE-bench Verified | 38.4% | 48.9% | 71.7% | 해결률 |

> **개발자 관점:** Codeforces 상위 11%에서 상위 1%까지의 도약은
> 추론 시간 컴퓨팅의 위력을 가장 극적으로 보여주는 수치입니다.

## 5. DeepSeek-R1: 오픈소스 추론 모델

### 5.1 왜 DeepSeek-R1이 중요한가

DeepSeek-R1(2025년 1월)은 MIT 라이선스의 오픈소스 추론 모델입니다.
이전까지 추론 특화 모델은 폐쇄형 기업의 전유물이었습니다.

```
2024년 9월: o1 출시 (폐쇄형, API만 제공)
2025년 1월: DeepSeek-R1 출시 (오픈소스, 가중치 공개)
  --> "추론 능력은 더 이상 폐쇄형 모델만의 특권이 아니다"
```

### 5.2 훈련 방법: 강화 학습으로 추론을 학습시키다 (RL for Reasoning)

DeepSeek-R1은 순수 강화 학습(RL)만으로 추론 능력을 학습시킬 수 있음을 보여주었습니다.

```
DeepSeek-R1 훈련 파이프라인:

  1단계: DeepSeek-V3 (기본 모델)
         |
  2단계: [순수 RL 훈련] -- 보상 함수: 정답 여부 + 형식 준수
         |
         v
         DeepSeek-R1-Zero
         --> 모델이 자발적으로 CoT, 자기 검증, 역추적 패턴을 "발명"
         |
  3단계: [SFT + RL 결합] -- 고품질 추론 데이터로 추가 미세 조정
         |
         v
         DeepSeek-R1 (최종 모델)
```

가장 주목할 점은 2단계입니다. 아무도 "단계별로 생각하라"고 가르치지 않았는데,
RL 보상 신호(정답 +1, 오답 -1)만으로 모델이 연쇄 사고, 자기 검증, 심지어
"잠깐, 다시 생각해 보자(Wait, let me reconsider)"와 같은 메타인지적 패턴까지
학습했습니다.

### 5.3 오픈소스 생태계에 미친 영향

| 항목 | 영향 |
|------|------|
| 모델 가중치 공개 | 누구나 로컬에서 추론 모델 실행 가능 |
| 증류(Distillation) 모델 | R1의 추론 능력을 소형 모델(1.5B~70B)로 전이 |
| 훈련 방법론 공개 | RL 기반 추론 훈련의 레시피를 커뮤니티에 제공 |
| 비용 절감 | 자체 인프라에서 추론 모델 운영 가능 |

## 6. 사고 예산과 비용 (Thinking Budget and Cost)

### 6.1 더 많은 사고 = 더 많은 토큰 = 더 많은 비용

```
일반 모드:        입력 500 --> 출력 1,000 토큰 --> 비용 = 기본

Extended Thinking: 입력 500 --> 사고 8,000 --> 출력 1,000 토큰 --> 비용 = 기본 + 사고 비용
```

### 6.2 비용 비교: 동일한 코드 리뷰 작업 기준

| 설정 | 사고 토큰 | 출력 토큰 | 상대 비용 | 품질 (복잡한 버그 탐지) |
|------|-----------|-----------|-----------|----------------------|
| 일반 모드 (사고 없음) | 0 | 1,000 | 1x (기준) | 보통 |
| 낮은 예산 (budget: 1,024) | ~800 | 1,200 | ~1.8x | 양호 |
| 중간 예산 (budget: 10,000) | ~6,000 | 1,500 | ~5x | 우수 |
| 높은 예산 (budget: 32,000) | ~20,000 | 2,000 | ~14x | 매우 우수 |
| 최대 예산 (budget: 128,000) | ~80,000 | 2,500 | ~50x+ | 최상 (수확 체감) |

> **핵심 통찰:** 비용은 사고 토큰에 선형적으로 증가하지만, 품질 향상은
> 일정 지점 이후 수확 체감(diminishing returns)을 보입니다.
> 대부분의 실무 작업에서 **중간 예산(10,000~32,000)** 이 비용 대비 최적입니다.

### 6.3 언제 사고에 투자할 것인가

```
의사결정 흐름:

  정확성이 중요한가?
  +--> No  --> 빠른 모델 (일반 모드). 예: 포맷 변환, 요약, 간단한 코드 생성
  +--> Yes --> 틀린 답의 비용이 큰가?
              +--> No  --> 중간 예산 Extended Thinking. 예: 코드 리뷰, 기술 문서
              +--> Yes --> 높은 예산 또는 추론 모델. 예: 보안 감사, 금융 로직 검증
```

## 7. 추론 스케일링 법칙 (Inference Scaling Law)

### 7.1 훈련 스케일링 법칙과의 병행

```
훈련 스케일링 법칙 (2020~):   성능 ~ f(모델 크기, 데이터, 훈련 연산)
추론 스케일링 법칙 (2024~):   성능 ~ g(추론 시간 연산량)
결합:                        최종 성능 ~ h(훈련 연산, 추론 연산)
```

### 7.2 성능 곡선과 수확 체감

```
성능 (정확도)
  ^
  |                         .............. (상한선)
  |                  ......
  |            .....
  |        ....                <-- 수확 체감 구간
  |      ..
  |    ..
  |   .                        <-- 급격한 향상 구간
  |  .
  | .
  +------------------------------------> 추론 시간 연산량
  0   1K   4K   16K   64K  256K (사고 토큰)
```

| 구간 | 사고 토큰 | 특성 | 전략 |
|------|-----------|------|------|
| 초기 | 0 ~ 1K | 성능이 급격히 향상 | 최소한의 사고라도 활성화 |
| 중반 | 1K ~ 16K | 안정적 향상, 비용 효율 양호 | 대부분의 작업에 적합 |
| 후반 | 16K ~ 128K+ | 수확 체감, 비용 급증 | 고난도 문제에만 선택적 사용 |

### 7.3 최적 배분: 큰 모델 vs 깊은 추론

```
시나리오 A: 큰 모델 + 빠른 추론   --> 대량 요청 처리 (검색 엔진, 챗봇)
시나리오 B: 작은 모델 + 깊은 추론  --> 소량의 고난도 작업 (수학, 코드 검증)
```

2024~2025년 연구에 따르면, 특정 난이도 이상의 문제에서는 시나리오 B가
더 비용 효율적입니다. 작은 모델이라도 충분히 "생각할 시간"을 주면
큰 모델의 즉답보다 나을 수 있습니다.

## 8. 개발자를 위한 실전 가이드

### 8.1 모델 선택 가이드

| 작업 유형 | 권장 모델/설정 |
|-----------|---------------|
| 빠른 응답, 단순 작업 (자동 완성, 번역) | 일반 모델 (Claude Sonnet, GPT-4o) |
| 정확성 중요, 중간 복잡도 (코드 리뷰, 설계) | 일반 모델 + Extended Thinking (4K~16K) |
| 최고 정확성, 고난도 (수학 증명, 보안 감사) | 추론 특화 모델 (o3, R1, budget 32K+) |
| 대량 배치, 비용 민감 (로그 분류, 태깅) | 경량 모델 (Claude Haiku, GPT-4o-mini) |

### 8.2 비용-효과 판단 프레임워크

```python
def should_use_extended_thinking(task):
    """추론 모델 사용 여부를 판단하는 의사결정 로직"""
    error_cost = estimate_error_cost(task)          # 오답의 비용
    accuracy_gain = estimate_accuracy_improvement(task)  # 정확도 향상폭
    thinking_cost = estimate_thinking_cost(task.complexity)  # 추론 비용

    benefit = error_cost * accuracy_gain  # 오답 감소로 인한 절감
    return benefit > thinking_cost        # 효과 > 비용이면 사용

# 예시:
# 프로덕션 보안 코드 리뷰: error_cost 높음 --> 사용
# 내부 Slack 봇 응답: error_cost 낮음 --> 미사용
# 금융 데이터 파싱: error_cost 매우 높음 --> 반드시 사용
```

### 8.3 Claude Code에서의 확장된 사고 활용

Claude Code는 작업 복잡도에 따라 내부적으로 확장된 사고를 활용합니다.

```
간단한 작업 (파일 생성, 간단한 수정)
  --> 일반 모드로 빠르게 처리

복잡한 작업 (멀티 파일 리팩토링, 아키텍처 변경)
  --> Extended Thinking 활성화
  --> 파일 간 의존성 분석 --> 변경 계획 수립 --> 실행

디버깅 (테스트 실패, 런타임 오류)
  --> Extended Thinking으로 깊은 추론
  --> 가능한 원인 열거 --> 각 원인 검증 --> 수정안 제시
```

## 10. 정리: 추론 시간 컴퓨팅의 의미

### 이 장에서 기억할 것

1. **추론 시간 컴퓨팅(Test-Time Compute)** 은 모델이 응답 생성 시점에
   추가 연산을 투입하여 답변의 질을 높이는 패러다임입니다.
   "훈련만 키우면 된다"는 기존 공식에 새로운 차원을 추가했습니다.

2. **연쇄 사고(CoT)의 확장**이 그 기반입니다. 중간 추론 토큰이
   작업 기억 역할을 수행하여 복잡한 문제를 단계적으로 해결합니다.

3. **Claude Extended Thinking**, **OpenAI o1/o3**, **DeepSeek-R1**은
   각각 투명성, 성능, 접근성에서 서로 다른 강점을 가진 추론 모델입니다.

4. **사고 예산(Thinking Budget)** 은 비용과 성능의 트레이드오프입니다.
   작업의 복잡도와 오답 비용에 맞게 배분하세요.

5. **추론 스케일링 법칙**에 따르면 작은 모델이라도 충분한 추론 시간을 주면
   큰 모델의 즉답을 능가할 수 있습니다.

6. **실무 선택 기준:** 단순하고 빈번한 작업에는 빠른 모델을,
   복잡하고 정확성이 중요한 작업에는 확장된 사고를 사용하세요.

> 계획 수립(planning), 자율적 실행(autonomous execution)까지 수행하는
